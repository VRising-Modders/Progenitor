# Progenitor layout facts (roadmap M4.1).
#
# Every number here is a byte offset, a native array stride or an enum value read out of the
# game's metadata, and every one of them is a wrong-memory write if it drifts on a game
# update. Before this file they were sixteen-odd literals scattered through src/ with a
# metadata citation in a comment and nothing checking them. Citations name the type and field;
# the generator refuses a citation that points at a file line instead.
#
# Grammar (tools/layoutgen/LayoutDeclaration.cs, docs/modules.md "Layout constants"):
#
#   layout v1                                required first directive
#   dump server | client                     which side's metadata the lines that follow resolve against
#   offset <Name> = <value> : <Type>.<Field>    [# citation]
#   size   <Name> = <value> : <Type>            [# citation]
#   enum   <Name> = <value> : <Enum>.<Member>   [# citation]
#   match  <Name> = <value> : /<regex>/ [in <Type>]  [# citation]
#
# <value> is the value the code was written and verified against, spelled the way the constant
# it replaced spelled it (decimal or 0x). The metadata is what the game says today. `--check` exits 2
# when the two disagree; it NEVER rewrites a value to match the metadata, because the declared number
# is the one that was tested and a silently-updated offset ships an unverified write.
#
# `size` is derived, not stated: the metadata gives field offsets and no sizes, so a size is the
# widest field extent rounded up to the widest field alignment (CLAUDE.md, "Native array element
# strides": for a buffer or blob element the stride comes from the metadata, never from sizeof and
# never from TypeManager). The generator refuses rather than guesses when any field width is
# unavailable.
#
# Regenerate after any edit:
#
#   dotnet run --project tools/layoutgen -- \
#     --declarations src/Progenitor.Core/Layout/layout.txt \
#     --out src/Progenitor.Core/Layout/Generated \
#     --dump-server <server metadata file> \
#     --build <build id>
#
# The metadata file comes from PROGENITOR_METADATA_DIR (default <workspace>\_tools\interop-dump,
# one folder per side); tools/deploy.ps1 finds it there. The server metadata is the authority for
# every line below. Each of these types is a ProjectM / Stunlock / Unity component present in both
# builds; where a value was first read from the client metadata the comment says so, and the
# offsets were confirmed against the server metadata.

layout v1
dump server

# ---- Abilities: forced cast (src/Progenitor.Core/Abilities/AbilityCast.cs) ---------------------
# ForceCastGroup is the game's own "cast this group now" inbox on the character's ability bar.
# The server's cast pipeline reads it, starts one cast and writes the field back to 0; that
# consume-and-clear is what makes a single int write a complete, non-repeating trigger, and it is
# measured, not assumed (castStartedCounter and serverCastCounter each advanced by exactly 1 with
# no input, and the field read back 0). A group that is not on the character's bar is consumed
# without starting (live 2026-09-25); ServerGameManager.ForceCastAbilityGroup starts those.
offset AbilityBarForceCastGroupOffset             = 0x34 : AbilityBar_Shared.ForceCastGroup
offset AbilityBarCastStartedCounterOffset         = 0x28 : AbilityBar_Shared.CastStartedCounter  # the read-back that proves a forced cast started
# The guid of the group currently being cast. AbilityCastStartedEvent entities live and die inside
# the frame that creates them, so a virtual system at AfterSimulation never sees one (measured: 0
# entities while the cast counter was advancing). Stable component state is the reliable seam.
offset AbilityBarCastGroupPrefabGuidOffset        = 0x54 : AbilityBar_Shared.CastGroupPrefabGuid
