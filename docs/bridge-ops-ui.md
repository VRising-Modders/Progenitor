# Bridge operations: Mods workspace UI

Operation reference for the [development bridge](bridge.md), part 3 of 5: the Mods workspace (`mods_ui`), the game menu, text fields and the date-time picker, and `setting`. Other parts: [core, entities and samples](bridge-ops.md), [players, world and capture](bridge-ops-player.md), [server info and join flow](bridge-ops-join.md), [input, install and session](bridge-ops-client.md). Part of the [development loop](dev-loop.md).

## `mods_ui`

Client, main thread. Focus-free Mods workspace (`status` / `open` / `close` / `back` / `select` / `search` / `scroll` / `widget_read` / `widget_click` / `native_tab` / `resolution` / `rects` / `window` / `dialog_choose`). With a dialog open, `widget_click label=…` clicks that dialog's button first; `dialog_choose {choice: yes|no|cancel|<caption>|<index>}` answers the open dialog even with the workspace closed ([ui.md](ui.md#the-games-popup-look-dialogs2)). `open` takes `args.site` = `main-menu` / `top-tab` / `shortcut` / `standalone`; in a world `shortcut` opens through the FullscreenMenu a few frames after the call returns (`detail.routedThroughMenu`), and `standalone` opens the window without that route. Refuses on the server. Contract: [`mods_ui` in api.md](api.md#dev-bridge-ops). Player and author workflow: [mods-menu.md](mods-menu.md). No MCP wrapper; use `call.mjs`.

**Bridge cost: light reads versus heavy ones.** Every `mods_ui` op used to wrap its result in the full workspace status before and after (`before` / `after`: entries, facts and the rest, about 90 ms on the main thread, the `readback-status` span). Polled once a second while a player was in game, that was a visible stutter every second (live 2026-09-30). The read-only ops that change nothing now skip it and report `before` / `after` as `{skipped: true, reason, open}`: `menu_tab_state`, `nav_state`, `rects`, `window`, `scene`, `tabs`, `perf`, `settings_places`, `restart` with `op` `read` (INSTALLRESTART1), and `keys` with `op` `read`, `conflict` or `conflict-read`. Pass `"withStatus": true` to get the full status with one of them. Every op that changes something (open, close, select, clicks, `keys` edits, `nav_back` / `nav_forward`, `native_tab`, …) keeps the readback, and `status` is the status itself. So: a light read is safe to poll while a player is in game; do not poll `status` or a changing op. `ModsMenu.StatusBuilds` counts full status builds (tests pin that the polled reads never build it).

### The game's full-screen menu (`menu` op)

**Live (2026-10-04, Steam client in game on the isolated test server, Core + Dev from branch feat/bridge-game-menu f60a7470, client generation 32):** `status` from gameplay read `menuOpen:false`; `close` with no menu answered `NoOp` (`no-menu`); `open tab:map` → `RaiseThenSelect`, menu on Map after 15 frames, repeated → `NoOp` (`already`); `close` → `Dismiss`, back to gameplay in 8 frames; `open tab:mods` → `OpenMods`, workspace open on MODS in 10 frames, log `shortcut opened through menu route=native raisedMenu=true reason=bridge:menu-open` then `settle re-selected MODS over native state=2 frame=0`; `close` with Mods open → `CloseWorkspaceThenDismiss`, log `close … reason=bridge:menu-close caller=ExecuteGameMenu`; the F10 recipe three times in a row: each first press raised the menu on MODS with the workspace open and no `native-tab` close, each second press logged `dismissed=true`. **Not live-verified:** title-screen answers, `open` with no tab (remembered tab), and status polling cost while playing.

GAMEMENU1. `mods_ui menu` with `args.op` reads and drives the game's own full-screen menu (the EMOTES … SYSTEM, MODS bar) without focus or OS input. **Source-checked, built and game-free tested (`GameMenuControlTests`); not live-verified.**

| Arguments | What it does |
|---|---|
| `{"action":"menu"}` | Unchanged: the read-only FullscreenMenu probe (graphics under the menu root). |
| `{"action":"menu","op":"status"}` | Reads `{inWorld, hudMenu, menuOpen, tab, tabState, workspaceOpen}`. A light read (no workspace status unless `withStatus`), safe to poll. |
| `{"action":"menu","op":"open"}` | Raises the menu with `HUDMenuManager.GoToMenu(FullscreenMenu)` on whatever tab the game picks. A no-op when it is already up. |
| `{"action":"menu","op":"open","tab":"map"}` | Raises the menu if needed, waits for its tab bar and its own tab pick, then runs the native tab's own click handler (`OuterTabEntry.OnPointerClick`, as `native_tab` does), at most 3 clicks. Tabs: `emotes`, `vampire-powers`, `spellbook`, `map`, `vblood`, `social`, `system` (case, spaces and dashes ignored; the game's enum names also work). A no-op when the menu is already on that tab with the workspace closed. Clicking a native tab while the workspace is open closes it as a player's click would. |
| `{"action":"menu","op":"open","tab":"mods"}` | The Mods shortcut's own route (`ModsMenu.ToggleFrom("bridge:menu-open")`, the F10 path): raises the menu when needed, opens the workspace on MODS and survives the menu's settle (F10SETTLE). A no-op when already open on MODS. Refused while the standalone window is open without the menu. |
| `{"action":"menu","op":"close"}` | Back to gameplay as Escape does: an open workspace is closed first with the logged reason `bridge:menu-close`, then the menu is dismissed with `HUDMenuManager.GoToMenu(None)` (the call the workspace's Escape handling makes). A no-op with `why: no-menu` when the menu is not up (a standalone Mods window is left alone). |

At the title screen every op answers that there is no game menu there: `open` fails with `why: title-screen…`, `close` is an `ok` no-op, and `status` reads `inWorld: false`.

**Verified reply.** `open` and `close` do not return `pending`. They poll each frame until the requested state has held for 8 frames, which is longer than the frames in which a raised menu picks its remembered tab. They give up after 180 frames with `ok: false` and the state they saw.

The reply's `detail` has these fields:
- `op`, `tab` and `step`: one of `Dismiss`, `CloseWorkspaceThenDismiss`, `Raise`, `RaiseThenSelect`, `Select`, `OpenMods` or `NoOp`.
- `handler`: the game call that was used.
- `menuBefore` and `menuAfter`: the status shape above.
- `framesWaited`, `clicks` and `clickResults`.
- `noop` and `why` on a no-op, and `readback: verified-after-frames`.

The usual workspace `before` / `after` status still wraps it.

**Recipe: the F10 raised-menu path end to end.** This replaces the user's Escape. Write each JSON to a file and call `node tools/mcp/call.mjs client <op> "@file"`.
1. `mods_ui {"action":"menu","op":"close"}`: plain gameplay. `detail.menuAfter.menuOpen=false` and `workspaceOpen=false`. If no menu was up, this is a no-op.
2. `keybind_press {"chord":"F10"}` (or `{"bind":"OpenSettingsPanel"}`): the real key dispatch. Expect `fired: 1`.
3. `mods_ui {"action":"menu","op":"status"}` after a second: `menuOpen=true`, `tab=mods`, `workspaceOpen=true`. Then `mods_ui {"action":"tabs"}`: `shortcutRoute.raisedMenu=true` and `shortcutRoute.settle.reselectsTotal` incremented when the menu tried its remembered tab. The log has `shortcut opened through menu route=native raisedMenu=true` and, when the menu picked another tab, `menu settle re-selected MODS …`.
4. `keybind_press {"chord":"F10"}` again: back to gameplay. `menu op=status` reads `menuOpen=false` and `workspaceOpen=false`, and the log has `shortcut closed to gameplay dismissed=true`.

Repeat 1–4 to check that the first press opens on MODS every time. `mods_ui {"action":"menu","op":"open","tab":"mods"}` takes the same route as step 2 without a keybind.

### Recipe: three homes

**Acceptance procedure — not run.** Three homes ([settings-organization.md](settings-organization.md#three-homes-2026-10-06), [mods-menu.md](mods-menu.md#where-progenitors-settings-are-drawn)). Build: Core and Dev from the branch, deployed to the Steam client (a Core and Dev hot swap; Bootstrap is unchanged) and to the isolated test server (Core: the lock list's group for the moved toggles). Only inside an authorized test session; never the live server. Read once per step (no polling). Write each request to a JSON file and call `node tools/mcp/call.mjs client mods_ui "@file"`; take each screenshot with `tools/observe.ps1` (focus-free).

New ops and readback used here:

- `mods_ui {"action":"select_tab","tab":"server"}` and `"tab":"preferences"` (`configuration` stays an alias).
- `mods_ui {"action":"section","group":"<caption or slug>","tab":"<optional>"}`: the left-list click. `widget_click` with `"pane":"list","label":"nav/<group>"` is the same click on the row.
- `mods_ui {"action":"drawer","group":"<caption or slug>","open":true|false}` (no `open`: toggle). `widget_click` with `"label":"drawer/<group>"` clicks the header.
- `widget_read`: a group heading's `page-section {title, group, drawer, open, count, key}` (a drawer adds `titleShown`, `chevron.shown` and `heading {chevronLeft, titleLeft, titleWidth, titleNeeds, …}`); a left-list row's `sectionNav {tab, group, slug, highlighted, jumped}`; the Server tab's `server-tab-head {state, title, line, canEdit, groups}` and, when empty, `server-tab-empty {state, line}`; the Preferences purpose line `preferences-purpose`.

`perFrame` defaults to 1 item a frame (typing, not one insert), at most 1,000. Every `field` readback is `{caption, length, hash, text (≤200 characters) or head/tail, caretBlock (the focus.caret block: line, column, lineCount, tmpLineCount, caretRect, fieldRect, checks.insideField …), scrollOffset, viewportMasked, textAboveViewport, textBelowViewport, drawsOutsideFrame, caretSource (tmp-lines | measured | stale), filter, characterLimit, inEditor}`; a multi-line field adds `lineBreaks` and `view {viewHeight, textAbove, textBelow, fraction (0 top … 1 end), atTop, atEnd, lineCount, firstVisibleLine, lastVisibleLine, visibleLines, firstVisibleChar, lastVisibleChar, viewHeld, caretOutOfView, readOnly, bar {visible, size, value, expectedValue, direction, agrees}}` (TEXTEXPAND1). The bar is synced to the text before it is read, so `value` describes this view. `direction` is `bottom-to-top`: `value = 1 − fraction`, so it is 1 at the top and 0 at the end. `expectedValue` is that mapping, and `agrees` compares it with the live `Scrollbar.value` (TEXTUNDO1 polish). Every `field` readback also has `undo {depth, redoDepth, totalChars, lastKind, maxEntries, maxChars, evicted, refused, lastClear, readOnly, undoApplied, redoApplied, ignoredReadOnly}` (TEXTUNDO1, [undo and redo](ui.md#undo-and-redo-textundo1)). `caretBlock` adds `caretHidden` (a read-only field) and `caretAlpha`. `type` and `paste` also report `rejected.readOnly`. A sample is read at a frame's drain and describes the frame before it; `outsideMs` (the game, uGUI/TMP layout and rendering) of a frame shows one sample later still. `worstHandler` names the type too (`NativeModsEntry.Tick`). `textDirtyBeforePump` counts frames where the focused field's TMP text was already marked for a new layout when the pump started (someone changed it since the last render); `textDirtyByPump` frames where the pump marked it. Layout rebuilds are not counted (no counter on this build).

**Safety.** Dev bridge only. `type`, `paste` and the `field_*` actions refuse with the workspace closed and `type` / `paste` refuse without a focused workspace field (`field_focus` first). One call at a time (the bridge's one-op gate); a second `type` while one runs is refused. Queued input and the test clipboard are cleared on completion, on error and when the gate abandons the call. No OS input is sent and no window focus is taken. A call stops after 20 s of game time and reports what it applied; set `PROGENITOR_CALL_TIMEOUT_MS=40000` for long `perf` or slow `type` calls.

**What this does not exercise.** The OS and IME → `Keyboard.onTextInput` hop into Bootstrap's queue, and TMP's own key handling (armed fields are read-only to TMP). After each Bootstrap change, one human keystroke check is still needed: type a few characters (an accented one on a non-US layout if possible) and confirm `mods_ui status` → `focus.textInput.proven` is true with no doubled characters.

## UI input without focus (BRIDGEUI1)

Status: **live-verified on the test client 2026-10-14** (Steam client, test server, bridge only: no OS input, the game window not focused; live passes 4 to 6), and game-free tested (`BridgeUiInputTests`, `tools/mcp/test/ui-tools.test.mjs`). Verified: `ui_input` hover with tooltips, click with Shift and Ctrl, right click, drag (with `keepDown` / `up` and no click after a drag), the wheel (several notches, one pump reading each), `focus`, `type`, `key` Enter and Escape (and same-key repeats, nothing left queued after Enter); the caret rules (a first click keeps the select-all and `type 40` gives `40`, a second click places the caret, Up / Down / Home / End by line in a multi-line field); a parked real cursor not feeding hover while leased; the lease ending; clicks on the game's own buttons (a `SimpleStunButton`: the castle heart's Upgrade); `nav` focus, press, hold and stick; `ui_read`; `display` set and restore with the registry and the window position restored; `screenshot` with `superSize 2`, a region crop, and `path` refused. **Not verified:** a native 4K capture (the monitor cannot show 3840x2160; `superSize 2` on 1920x1080 is the route), and whether `display set` ever writes the game's client settings (every observed run reported `settingsWritten: false`).

Four client ops drive and read the Progenitor UI kit for acceptance tests without OS input and without the game window's focus: `ui_input`, `ui_read`, `display` and `screenshot`, plus new `nav` actions ([`nav`](bridge-ops-client.md#nav): `hold`, `stick`, `focus`) and `widget_click` modifiers. MCP: `progenitor_ui_input`, `progenitor_ui_read`, `progenitor_nav`, `progenitor_display`, `progenitor_screenshot` (`tools/mcp/ui-tools.mjs`); or `node tools/mcp/call.mjs client <op> @args.json`.

**Why no focus is needed.** The device-level [`mouse`](bridge-ops-client.md#mouse) and [`key`](bridge-ops-client.md#key) ops queue Input System events. With the window in the background the Input System disables the mouse and keyboard and drops those events unless `background:true` changes `InputSettings.backgroundBehavior`, and even then a moved pointer is not always reported (live 2026-10-14: `positionReached false` unfocused), and the kit's wheel handler read `deltaY=0`. `ui_input` does not go through a device at all. Core's `UiSyntheticInput` holds a synthetic pointer (position, buttons, Shift and Ctrl, queued wheel notches), UI-layer key taps and navigation holds. While the bridge holds its lease, the kit's own reads take that state instead of the devices:

| Kit read | What it gets from the synthetic input |
|---|---|
| `SamplePointer` (hover gate, `HoverCapture`, the widgets' `ReadPointer`, the hovered panel, the chat box, the map) | The synthetic point, inside the window whatever the focus |
| `PrimaryPointerHeld`, the pump's click-to-focus and drag test | The synthetic left button |
| `HeldClickModifiers` (a click's multi-select meaning) | The synthetic Shift and Ctrl |
| The shown-input pump's wheel sample | One notch a sample (`notches: -3` is three readings of -120, never one -360), a zero between, so each is a 0 to non-zero edge: the wheel claims (`UiWheelClaims`), text areas, inner scroll blocks and the hovered panel take it in their usual precedence |
| The typed-key pump (`KeyEdgeTracker`) | Tapped keys held for their frames, with or without a keyboard device. An Escape tap goes through the framework's Escape hook (`Ui.PressEscapeForBridge`, the path Bootstrap's forwarder calls) at tap time, and only while a Progenitor panel is shown (when Bootstrap forwards a physical Escape), so dialog, capture, screen Back, inline edit and panel sweep precedence all run and nothing is left pending for a later panel (`tap.escapeHook`) |
| `SampleNav` | Held navigation buttons, the right stick, the arrow, Space and Enter taps; the synthetic pointer moving puts the focus marker away |

A per-frame driver sends the pointer events a real mouse produces to the objects under the synthetic point, found by the game's `EventSystem.RaycastAll`: enter and exit along the hovered chain (leaf first), down on the first object up the chain that takes a press, up and a click when the release is over the object that took the click (the input module's rule), and initialize-drag, begin-drag (past the event system's drag threshold), drag and end-drag on the drag handler. They are called on the components this UI uses: `EventTrigger` (every kit pointer watch, hover watch and slot trampoline), `Selectable` and its subclasses (buttons, toggles, scroll bars, sliders, text fields, the game's `SimpleStunButton`) and `ScrollRect`, and also to the game's own components that implement the pointer interfaces themselves (live 2026-10-14: the castle heart's Upgrade entry is a `GridSelectionEntry`, which is neither; its click was not taken). Those are found the way the input module's `ExecuteEvents` finds them: every component of the object is tested against the interface with `TryCast` (the IL2CPP class test), and its interface method runs. The game's `SimpleStunButton` gets its own pointer-click (its sound and submit routine), not only its `onClick`. The game's menu rows (`MenuButton`: the System menu's Resume, Options, Leave and the other rows built by a `MenuCollection`) take only the pointer's enter and exit and keep their `SimpleStunButton` in a field (`MenuButton.StunButton`, the button the game's `MenuCollection.ClickButton` invokes), which need not be on the hit object's parent chain; a click or `submit` that meets a `MenuButton` while walking up from the hit goes to that held button, and a row whose own `Interactable` is false is refused with that reason. Before this, a click on such a row only hovered it. **Not run live:** this routing is source-checked against the game's menu code and built; the live hierarchy of the System menu was not read. A click that is not taken says why in `ui_read state.events` (`not active`, `not interactable`: the game has the button disabled, for example while an upgrade's cost is not met). Right and middle clicks reach event triggers and the game's own handlers only, as in uGUI. A kit text field takes a press only through the kit's click-to-focus, never TMP's own pointer-down, and whether the field already had the keyboard is read before anything is dispatched, so a first click keeps the select-all (live 2026-10-14: TMP's pointer-down had taken the keyboard first, the caret went to 0 and `type 40` gave `4020`). A drag that starts on another object than the press releases the press there and is never a click, as the input module does. Nothing reads window focus.

**Only the synthetic pointer while leased.** The event system's input module turns the real cursor's position into enter, exit and hover even when the cursor does not move (live 2026-10-14: a parked cursor fed tooltips and the help markers' hover count during a run). While the lease is held the driver disables the event system's current input module, so hover comes only from the synthetic pointer; the module is enabled again when the lease ends (release, timeout, user activity, Core swap, Dev unload). The game's own pointer and controller handling of its UI is off for that time. Moving the real mouse still ends the lease.

**Frames.** Every step is counted in rendered frames (`Time.frameCount`), not in main-thread drains, because the kit samples once a frame. A tap of a key still held is queued after one released frame, so back-to-back taps (four Backspaces) are four presses.

**Caret.** The kit owns the caret of its fields. In a focused multi-line field, `key` `Up`, `Down`, `Home` and `End` move the owned caret by line (the text component's drawn lines, wrapping included, when its layout matches the text, else the line breaks); `Shift` extends the selection; `Ctrl+Home` and `Ctrl+End` keep the kit's whole-text moves. Elsewhere those keys go to the typed-key pump as before. The first click on a kit field focuses it and the kit selects its whole value on its next typed-key pass (as with the mouse, so `type` replaces it; the bridge places no caret while that select-all is pending); a left `click` on a field that already has the keyboard puts the caret at the clicked character (`TMP_TextUtilities.GetCursorIndexFromPosition`; skipped with a note in `ui_read state.events` when the layout does not match the text, for example with rich text).

**What it does not cover.** The game's own input (its actions, its pause menu, its camera) never sees these events: Escape through `ui_input` does not test whether the game's pause menu opens; use `key` with `background:true` for that. The wheel goes only to the kit's wheel handler, not to uGUI's scroll handlers (the kit sets `scrollSensitivity = 0`; uGUI's scroll is not its mover). Keys are UI-layer events for the kit's fields and Escape and Enter handling, never keybinds: press a bind with [`keybind_press`](bridge-ops-client.md#keybind_press). Enter and Escape take the kit's real paths: a synthetic Enter is a held key for the typed-key pump, so its Enter branch runs (a widget value box commits and gives up the keyboard through `ReleaseWidgetField`, with the key-burst hold; an external field submits; otherwise the dialog's Enter); only a plain kit single-line field, whose commit is TMP's own Enter on the OS queue, also gets the injected submit the `type` path uses. A synthetic Escape goes through the framework's Escape hook, so a table value box reverts and releases through its own Escape handler.

**Lease.** The first action takes a lease (`leaseMs`, default 30000, 500 to 300000); every later action renews it, so a hover stays while you read the tooltip. It ends on `release` (or `"release": true` on any action), at its time, when the player touches the real mouse or keyboard (`user-activity`: a held button or key, or the pointer moving more than 3 px), on a Core swap (`unload`) and on Dev unload. Ending lets go of every button (no click), sends the pointer's exits and drops queued notches, keys and the injected text the bridge queued; the log line is `Ui: synthetic input ended (<reason>).` A Core swap cannot send exits into the kit's dying objects, but a game control still held by the synthetic press gets its pointer-up first. `nav hold` and `nav stick` hold the same lease, so the player's activity or a release ends them too.

**Bounds.** Every action ends inside the bridge's 30 s cap for one op: `settleFrames` at most 60, `holdFrames` 120, `steps` 180, key `frames` 30, `type` text 400 characters (typed one a frame, or up to 4 a frame for long text so it takes at most about 120 frames), and a pointer action's whole timeline at most 300 frames. A wall-clock deadline of 25 s ends any action that the game's frame rate makes slower, with `ok false`. A failed, timed-out or abandoned action lets go of every button and modifier, drops queued wheel notches and drops the text it queued. A `wheel` with no Progenitor panel shown is refused at once (only the shown-input pump takes notches). Injected text and the Enter a `key Enter` queues for a plain field are owned by the op: if their field loses the keyboard first (a dialog's Enter, a close, another field), the driver drops them instead of typing them into the next field.

Client availability is still the caller's rule ([AGENTS.md](../AGENTS.md)): do not run these ops on a client someone is playing.

`mods_ui hover {label, cell}` dispatches only to cells declared as hover cells (chips, tab chips); for data table header cells, master-detail halves and any other control, hover with `ui_input`, which goes through the pointer path.

**Targets.** `row` (a cell row key, as `mods_ui widget_read` and `ui_read widget` show it) with an optional `cell`, or `panel` (a shown panel's title, see `ui_read panels`), or `x` and `y` in screen pixels with the origin at the bottom left (the Input System's convention, as `mouse`; `mods_ui click_at` uses the top-left client convention). `fx` and `fy` (0 to 1, default 0.5) pick the point inside the target's rect from its left and bottom; `dx` and `dy` add pixels. `ui_read {"what":"target", ...}` shows the point before you act.

### `display`

| Arguments | Does |
|---|---|
| `{"action":"status"}` | `before`: the window now (`width`, `height`, `mode`, and `window {focused, foreground, windowFound, rect}`), the `monitor`, and the game's saved graphics fields `settingsResolution` and `settingsWindowMode`. `set` and `restore` reply with the same block as `afterCall` (right after the game's call) and `after` (once the window settled), plus `focusBefore`, `focusNow` (the same `{focused, foreground, windowFound}` reading) and `foregroundGivenBack`. `focused` is the engine's own window focus; `foreground` whether the game's window (found by its engine window class, not the process's first window, which can be the BepInEx console) is the desktop's foreground window, null when the window was not found. `baseline`: a pending set's way back (`pending`, the window and settings it returns to, `settingsWritten`, `settingsFileWritten`, `file`). |

Waits up to 90 frames for the window to take it. `ok` is true only when the window matches the request (`after`); a window the monitor cannot hold is `ok false`. `mode`: `windowed` (default), `fullscreenwindow`, `maximized`. **Whether `set` writes the user's settings.** It was not determined offline. Each `set` measures it: `settingsWritten` (the game's in-memory `ClientSettings.GraphicSettings.Resolution` / `WindowMode` changed) and `settingsFileWritten` (the client settings file's size or write time changed). Both are kept in the baseline, and `restore` undoes what was written. Every set observed live on 2026-10-14 reported `settingsWritten: false` and `settingsFileWritten: false`, so no run has shown the game write them; that it never does is not verified.

**The window's focus.** A windowed resolution change can activate and raise the game's window (live 2026-10-14: `focused` went from false to true after a set). When the game did not have the foreground before the call, the op gives the foreground back to the window that had it and puts the game's window behind it, without activating it (`foregroundGivenBack`), right after the call and on every frame while it waits. Window management only; no input is sent. The focus reading was verified live 2026-10-14; a give-back has not been observed (the observed sets did not take the foreground).

**The engine's remembered window.** The engine keeps the windowed size, position and full-screen mode in the user's registry, `HKEY_CURRENT_USER\Software\Stunlock Studios\VRising`, values named `Screenmanager …` (live 2026-10-14: they changed to 2560x1440 at 0,0 after a set). The first `set` records those values and the window's top-left on the desktop in the baseline; `restore` (and the restore on Dev unload) moves the window back to that top-left when the baseline was windowed and writes those values back, and only those (`restored.position`, `restored.registry`). Verified live 2026-10-14: the `Screenmanager` values and the window position came back after `restore`.

**Restored without a `restore`.** Dev unload, which also runs on every Core swap, restores a pending baseline (`Dev display restore on unload: …`). It cannot read the window back there; a baseline it could not apply stays on disk, and `display status` shows it pending for `restore`.

**A baseline left by a run that died.** When the process ended between `set` and `restore` (a crash, a kill), the baseline file stays (live 2026-10-14). Each `set` also records the test setting it asked for. A few seconds after the next Dev load the pending baseline is checked: when the window is still exactly that test setting it is restored (`Dev display restore of an earlier run's pending set …`); when it is anything else (the user or the game has set the window since) the baseline is deleted and logged (`Dev display: discarded a baseline an earlier run left pending (…); nothing was resized.`), so a load never resizes a window by surprise. Extra game instances that share the BepInEx config do not run the check. Not live-verified (it needs a process that dies mid-test).

**4K on a smaller monitor.** A window cannot be larger than the monitor that shows it (5120x1440 cannot host a 3840x2160 window), and the kit's overlay canvases are not drawn by a camera, so they cannot be rendered offscreen into a larger target without changing every canvas's render mode, which this op does not do. What works: the kit and the game's scaler size the UI from the screen at a fixed aspect ratio, so a 1920x1080 or 2560x1440 window has the same layout in canvas units as 3840x2160. Set a 16:9 window that fits, check layout there, and take `screenshot {"superSize":2}` on 1920x1080 for a 3840x2160 image. That checks clipping, overlap and layout at 16:9; it does not check how a 4K display's pixel density looks, which needs a 4K display.

### `screenshot`

`{"superSize":1, "name":"table-1080.png", "rect":{"x":0,"y":0,"w":800,"h":600} | "row":"…","cell":"…" | "panel":"…", "pad":8}`. `ScreenCapture.CaptureScreenshot`: the game writes the frame it renders, UI included, at the end of the frame. No focus is needed (a minimized window renders nothing, and the op then fails after 300 frames). Files go only to `BepInEx/progenitor-shots`: `name` is a plain file name (letters, digits, `-`, `_`, `.`, ending in `.png`; no folder, no `..`), default the UTC time, and an existing file is never replaced or deleted (`-2`, `-3`, … is added instead). `path` is refused. `superSize` 1 to 4 renders that frame at a multiple of the window's size, at most 7680x4320 pixels in all; verified live 2026-10-14 with `superSize 2` (the reply's `width` and `height` are read from the file). It writes files on the client's machine, so it takes a bridge queue slot like an input op. A region (a rect in screen pixels with the origin at the bottom left, or a row, cell or panel, plus `pad`) is cropped from the file into `<name>-region.png` (`region {path, x, y, width, height}`). For the whole window from outside the game, [observe.ps1](observe-capture.md) remains the other focus-free option.
