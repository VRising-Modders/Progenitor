# Progenitor roadmap

**Reviewed 2026-09-10 against source, offline tests and internal reviews R86 and R87.** The framework foundations are usable; the complete product is not done. The 2026-09-10 batch is **implemented offline** in this tree: nothing from it is in a reviewed candidate, and none of it is live-accepted. M2–M4 contain qualified historical work alongside unfinished acceptance gates. M5 has a useful offline catalog and five researched recipes, not a complete asset-loading browser.

This is the current status and scope. [The specification](spec.html) describes intended behavior; [the API reference](api.md) documents individual contracts. Detailed investigations and the previous roadmap are kept in the internal research notes. Item numbers are retained for existing references.

| Status | Meaning |
|---|---|
| **Done (scoped)** | The stated scope has supporting verification. Limits in the row still apply; this is not a guarantee for every asset/build. |
| **Partial** | Useful implementation or verified subcases exist, but the full item has unfinished work. |
| **Implemented; qualification open** | Code exists; the stated acceptance evidence is incomplete. |
| **Planned / research** | Design or investigation exists, but no qualified implementation of the intended feature. |
| **Blocked / gated** | A known failure or prerequisite prevents qualification or release. |

Verification and version-control state are separate. Much recent work is uncommitted; a passing test does not imply a commit, deployment, live verification or release readiness. Historical evidence qualifies its recorded build/path. This review inspected source and saved evidence; it did not run the game or requalify every historical feature on today's tree.

## Current priorities

**Material sources (P3, `ctx.MaterialSource`) — experimental and opt-in; live-verified on the isolated test rig on 2026-10-14 for craft, build, the per-item fallback, the reserve, provider faults, a shortfall between check and payment, disable, the client resend, unload and a server Core swap; other screens reading the same count are not live-verified:** one provider decides which containers pay for building, workstation crafting, crafting from the Character window on a plot, item repair and castle heart upgrades (Repair and Upgrade live-verified on the test rig 2026-10-14; a claim staying vanilla and the client's equipped-repair path not; Character window crafting live-verified on the test rig 2026-10-14 except the client's own craft click), and the totals the player sees follow it (a repair cost in an item tooltip keeps the game's own count), through opt-in Bootstrap seams (`[Materials] NativeSeams`, client and server restart). One game operation is one transaction (the provider is asked once at the game's own check; every line is validated against what the check saw, then taken; a line short at payment follows the game's own shortfall behavior), items the provider leaves to the game behave exactly as vanilla on both sides, and the client applies a view only for the local character at its plot and in its own operation. Procedure and test plugin: [Shared Resources Test](../samples/Progenitor.SharedResourcesTest/README.md). Remaining: other screens, the claim case, the Character window crafting click and short cases, the repair tooltip display (needs a new hook), and a production sharing policy (the consumer's). [Module page](modules.md#material-sources).

**Next: auto-update (M6, decided 2026-10-08) — phases 1 and 2 (the client) built and game-free tested, verified live in part; phases 3 and 4 (the server) built on a branch, game-free tested, verified live in part; Progenitor's own updates designed.** Progenitor and the mods it installed update themselves from Thunderstore on the client (at the title screen, through the kept-versions store so a server that needs the old version still gets it) and on an unattended server (hot updates live, restart updates at the next start or, opted in, when the server is empty, with rollback, an optional pre-update backup and an audit log). No new polling: client checks reuse existing index reads. Phase 1 is client detection, the update list with **Update all**, and the pre-join prompt; phase 2 applies updates automatically at the title screen, with **Roll back**, a failed list and a short line under MODS. [Design and decisions (2026-10-09)](auto-update.md).

## M1. Usable for us

**Done for the original foundation scope:** events, system hooks, ECS access, commands, handshake/networking, prefab registry, persistence/config/localization, plugin reload, Dev bridge/MCP, test launch/connect tooling, basic unit control and chat. Historical two-client broadcast and castle-plot reads have evidence. This does not certify arbitrary NPC lifecycles, complete placement rules, all reload scenarios or production save safety.

**Command routing and chat-command coexistence — MVP implemented offline; independently reviewed (internal review R87); live coexistence unverified.** Root-level dot shortcuts plus a qualified fallback (configurable framework root, default `p`, stable mod identifier) are in Core. Administrators can disable, rename or assign shortcuts. Progenitor conflicts no longer silently replace: unresolved shorts are disabled while qualified routes remain. Permissions, ordinary chat, server authority and owned unload/swap cleanup are preserved in offline tests. No other chat-command framework is a dependency, and mods built on one need not migrate. Cross-framework collision checks are **unavailable**, not passed. Live gate: exactly-once command/help/conflict checks with another chat-command framework installed. Not in a candidate.

**UI-first mod authoring — product direction.** Encourage mod authors to use Progenitor's client UI for everyday player interactions, discoverable actions and settings when the client runtime is available. Commands remain supported for shortcuts, administration, automation and applicable server-only workflows with unmodified clients. Examples should demonstrate UI and command entry points sharing the same underlying operation and server-side permission checks. This is guidance, not a mandatory client installation or a requirement to build a screen for every command; UI availability never grants authority.

**Command routing follow-ons — future enhancements, outside MVP.** A unified help interface, richer autocomplete and coordinated client-local/server discovery. Add only through supported integration surfaces and evidenced consumer needs; no universal compatibility claim.

## High-priority post-MVP work

- **Best-effort save recovery — research and feasibility first.** Investigate extracting recoverable vanilla state into a separate recovered save/world: characters and ownership, castle placements and structures, character/container inventories, and journal/quest progression. Preserve the original unchanged and report preserved, omitted and uninterpretable data. A vanilla prefab identity does not prove its saved components or linked entities are unmodified or valid. Attempt restoration of missing dependencies before salvage; do not silently discard unknown mod data or promise complete reconstruction. Acceptance requires inspection of recovered relationships and a successful load, save and reload on disposable copies. This is high priority after MVP, not an initial-release gate or a current implementation assignment. Full extraction/reconstruction remains unproven. Review causes of save failure and prevention opportunities alongside this work; existing safeguards retain their current scoped status.

- **Coordinated Core hot swap while hosting a private game (planned, not started; requested 2026-10-06).** Today a client hosting a private game refuses a Core swap: the hosted child runs its own copied `progenitor-core\Progenitor.dll`, so swapping only the client would leave the two on different Core builds ([knowledge note](../knowledge/notes/hosted-game-refuses-core-swap.md)). Plan: stage the same Core image for both processes, swap the hosted child first (it serves the world), then the client, and re-run the handshake so the client and the child agree on the new generation before play continues. Open questions: how the client hands the staged image to the child's copy without a junction (the R11 rule against promoting through the client's folder), what the child does with connected guests during its swap, and the refusal and rollback when either side cannot swap. Acceptance: one `deploy` while hosting swaps both, `reload_status` on both reports the new generation, the handshake answers `ok` again, and a guest stays connected or is told why not.

## Optional future features — outside the initial release

- **Server-declared client-mod policy (PvP fairness tags):** nice to have; stretch goal for a later release, no implementation assignment. Plugins would declare an advantage category (cosmetic, quality of life, information the base game hides, automation or input such as [input leases](input.md)); a community server would state a policy (for example "PvP: cosmetic and quality of life only"); the handshake would report and enforce it, and the Mods workspace would tell the player before joining which mods to turn off. Today client-only plugins are not reported to the server at all, which is the gap this closes. Labels are self-declared, so this is a rules-and-courtesy system for honest players and server admins, not anti-cheat, and must be documented as such. **Not "official-friendly":** official servers run EasyAntiCheat, which Progenitor does not support ([spec](spec.html) non-goals), so no tag makes a modded client suitable for them. Any input or automation API should carry the automation label from the start.

- **Custom playable areas:** nice to have for a later release; feasibility unproven, no implementation assignment or MVP/release gate. Investigate teleport-accessed arenas or dungeons first, potentially reusing existing playable space. Extending the main map by changing terrain and adding connecting roads is a separate, larger possibility. Dracula's transition is a research lead, not evidence of a reusable zone system. Any future feasibility test must establish destination loading, collision/navigation, multiplayer visibility, safe return, reconnect and save/reload behavior before claiming support.

## Not adopted

- A separate mod loader: BepInEx remains the loader; Progenitor provides framework services.
- Game bytecode mixins: IL2CPP requires the supported Harmony/native seams instead.
- A standalone renderer/browser as the first asset-preview implementation: use the game's rendering and owned in-game preview path first.
