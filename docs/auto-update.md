# Auto-update: Progenitor and installed mods (design)

**Status: phases 1 and 2 (the client: detection, the update list, the pre-join prompt, Automatic mode, Roll back, the failed list, the line under MODS) built and game-free tested; verified live in part on the Steam client ([Phase 1 as built](#phase-1-as-built), [Phase 2 as built](#phase-2-as-built)). Phases 3 and 4 (the server: detection, Notify and Automatic, the admin notice, Restart now, Restart when empty, the pre-update backup, the Server tab **Updates** group) built on branch `feat/auto-update-phase3`, game-free tested and verified live in part on the isolated test server ([Phase 3 as built](#phase-3-as-built)). Phase 5 (Progenitor updates itself) built and game-free tested; verified live in part ([Phase 5 as built](#phase-5-as-built)). Since 2026-10-20 Progenitor's own releases come from a signed release list on GitHub instead of the Thunderstore index: built and game-free tested, not verified live ([Release list](#release-list-github)).** Decided 2026-10-08: "auto-update for the client and server ... Yes, this is next"; the decisions of 2026-10-09 are folded in ([Decisions](#decisions-2026-10-09)). It is milestone M6 in the [roadmap](roadmap.md#m6-auto-update-next). Names in the sections for phases 2 to 5 are proposals.

Progenitor already installs, updates by hand, keeps versions and hot-loads mods. Auto-update adds one thing: **it decides, on its own schedule, to run the update the player or admin could have pressed**, through the same pipeline, and records why. It adds no new downloader, no new installer and no new trust path.

## What it reuses

| Piece | Today | Role in auto-update |
|---|---|---|
| Thunderstore index read (`CatalogFetcher`, `progenitor-cache/index.json`) | Read by the Install tab (30 min on open), the join screens (10 min), the server's install-window availability (`ServerPackageAvailability`) and remote installs. The Thunderstore traffic work (TSTRAFFIC1, merged) makes every read conditional (`If-Modified-Since`, a 304 has no body), gzip-compressed, and adds per-owner failure backoff. | The only source of "a newer version exists". The v1 index already lists every version of every package, so finding updates needs **no per-package request**. |
| Install ledger (`BepInEx/progenitor-install.json`, `ServerInstallLedger`) | Every file Progenitor wrote, with `package:<key>@<version>`, plugin id, route and sha256. | Defines **what Progenitor manages**. Only ledger rows are ever auto-updated. |
| `InstalledState` | Already computes `UpdateAvailable` per listing. | The candidate list. |
| Install pipeline (`DownloadAndInspectAsync`, `PlanWithDependenciesAsync`, `ExecuteWithDependencies`, `InstallLog`) | Download with size cap, inspection (declared sha256, `progenitor.json`), admission (`TrustedHotLoadable` → `progenitor-reload/`, else `progenitor-pending/`). | Runs every auto-update unchanged. |
| Kept versions (`ModVersionStore`, `progenitor-versions/`, JOINFLOW4) | Parks a replaced copy, swaps it back by journal, picks the version a server needs at the handshake. Client only. | The client's update and rollback path. The old version stays on disk, so a server that needs it still gets it with no download. |
| Pending-restart bar (INSTALLRESTART1) | Counts client changes that load at the next start; **Restart now / Restart and rejoin**. | Shows restart-needed client updates. Never pressed for the player. |
| Remote installs (REMOTEINST1) | The server downloads from Thunderstore itself, checks host, community, version and size, hot-loads or stages, and writes `progenitor-remote-install.log`. | The server's update path and the model for its audit log. |
| Stop request and launch record (F20, F30, `ServerProcessControl`) | A server saves the world, then quits. | The only way a server applies restart-needed updates before its host restarts it, and only when the operator opts in. |
| Scheduled backups (BACKUPNOW1, [world-restore.md](world-restore.md#backups-back-up-now-and-the-schedule)) | Consistent world copy while the server runs; kinds `manual` and `scheduled`, each kept by `BackupKeepCount` / `BackupKeepDays`. | The optional **pre-update** backup, a new kind with its own keep count ([Rollback](#rollback-1)). |
| Server re-signed catalog, JOINNOTICE, install window | A changed required-mod list reaches players in the world as a notice; a join with a missing or outdated mod is held open while they install it from Thunderstore. | How players follow a server update: they fix it where they are. |
| Core swap and Bootstrap `.next` ([hot-reload.md](hot-reload.md#swap-core-and-confirm-completion)) | Core hot-swaps when the protocol matches; Bootstrap's staged DLL takes effect at the next launch. | Progenitor's own update. |

## Terms

- **Managed by Progenitor.** A package with a ledger row whose `source` is `package:<Namespace-Name>@<version>` from the Thunderstore index, whose file is still on disk with the ledgered sha256. Not managed: anything loaded from `BepInEx/plugins` without a ledger row, anything another tool installed (MANAGED1 "Managed elsewhere"), and anything whose bytes changed after Progenitor wrote them. A package from the dev Thunderstore stand-in (`[Install] DevThunderstoreUrl`, [test-rig.md](test-rig.md#local-thunderstore-dev-only)) or from `[Install] LocalIndexPath` is managed **while that key is set** (both are cfg-only test configuration; the live tests use the stand-in: [decision 10](#decisions-2026-10-09)); a local test source (`LocalTestSource`) never is.
- **Update.** A newer version of the **same package** (same Thunderstore namespace and name) in the index. Never a different package, never a downgrade.
- **Hot update.** The planner's `ApplyNow` route: the new image is admitted (`TrustedHotLoadable` or a qualification record) and the old one can be unloaded (`HotLoadTrust.CanUnloadHot`). Everything else is a **restart update**.
- **Apply window.** A moment when applying cannot disturb a join or a session (defined per side below).

## Checks: when Progenitor looks for updates

Rule: **an update check is an index read that would have happened anyway, or one conditional request at a moment that already exists.** No timer polls on the client. The server has one operator-configured cadence, because nobody opens a menu on an unattended server.

| Side | When it checks | Cost |
|---|---|---|
| Client | Every index read the Install tab and the join screens already make (unchanged intervals: 30 min, 10 min). The update pass runs on the body they already have. | Zero extra requests. |
| Client | At start, on the **cached** index body (`progenitor-cache/index.json`) when one is on disk, so the badge is right before any read. | No request. |
| Client | **Once per game start**, at the first title screen, only when the cached index is older than 6 hours. Not in phase 1 ([still open](#still-open)). | One conditional request per session, normally a 304 with no body. |
| Server | At start, once the world has loaded, and then every `[AutoUpdate] CheckHours` (default 6, minimum 1, maximum 168). A read by any other owner (install window, remote install) within the interval counts as the check. Phase 3 ([still open](#still-open)). | Four conditional requests a day by default, normally 304s. |
| Both | **Check now** in the settings (below). | One request; refused while the owner is in failure backoff, with the time it resumes. |

The update pass runs on the cached body after every successful read, so a 304 still finds updates published since the body was cached by another owner. The pass is pure (index, ledger, settings and state in; a plan out) and runs off the main thread.

A new owner `auto-update` joins the TSTRAFFIC1 log lines and failure backoff (3 failures in a row pause automatic checks for 5 minutes, doubling to 60). Downloads happen only for an update that will be applied, at most two at a time, inside `[Install] MaxDownloadMB`.

## Which version is chosen

For each managed package, newest first, the first version that passes every rule:

1. It is newer than the installed version (`InstalledState.IsNewer`) and active in the index (not deprecated or removed).
2. Its download is `https` on Thunderstore's hosts and the listing is in the V Rising community (the remote-install checks, `NotThunderstore`, `not-v-rising`). A package the index flags NSFW is skipped while `[Mods] ShowNsfwContent` is off.
3. It is not pinned below it (per-mod **Keep this version**, or a server `Pins` entry) and not in this side's **failed versions** (below).
4. Its major version equals the installed one, unless major updates are set to Automatic (client default **Notify**, [decision 1](#decisions-2026-10-09)). A blocked major update shows as **Notify**, marked **major**.
5. Its dependencies are satisfiable without installing a package that is not installed yet. An update that needs a **new** package is never applied unattended: it is offered with the package named, and **asks first** ([decision 3](#decisions-2026-10-09)). Updating an already managed dependency is part of the same plan, dependencies first.
6. When the current game update is known (`CatalogUpdateTags`), a version tagged for another game update is skipped with that reason. Unknown hides nothing, as in the Install tab.
7. A version whose `Progenitor` dependency is newer than the running Progenitor waits for Progenitor's own update (below) and is applied after it.
8. When `BepInEx/config/progenitor-allow.txt` exists (the hash allowlist), a version whose installable DLL hash is not listed is **Notify** only. The allowlist is never edited.

## Settings: three modes per scope

Every scope (all mods, one mod, Progenitor itself, on each side) has one of three modes:

| Mode | Behavior |
|---|---|
| **Automatic** | Download, verify and apply in the next apply window. |
| **Notify** | Show that an update exists (Install tab state, a notice, the Server tab status, the log). Apply nothing. |
| **Off** | No notice, no download. The Install tab still shows **Update** as today. |

A per-mod choice overrides the global one (Preferences › Updates › **Update mods**; the mod page captions following it **Default (…)**). **Keep this version** is a pin ([decision 9](#decisions-2026-10-09)): Off for that mod, plus the version store's `preferred` set to it so a join swap does not drift it. A pinned mod is not counted in the badge, not listed as an update, not offered by the pre-join prompt and skipped by **Update all**; its row in the update list reads `Kept at 1.2.0 · 1.3.0 available` with **Unpin**.

## Client

### Where updates show

- **The line under MODS** (decisions of 2026-10-09, replacing the phase 1 badge). A subtitle centered under the title screen's MODS entry, cloned from the game's own subtitle under CONTINUE (`MenuButton.AdditionalText`: its font, size, color, letter spacing and upper case), short and generic, never a mod or a version. In this order: `1 UPDATE AVAILABLE` / `N UPDATES AVAILABLE` (updates waiting for the player: Notify, a major version, a new dependency; pinned mods and failed versions are not counted), else `1 MOD UPDATED` / `N MODS UPDATED` (automatic updates since the Mods window was last opened), else `UPDATE FAILED` / `N UPDATES FAILED`; no line at all otherwise and while **Update mods** is Off. The updated and failed counts add up across passes and last until the Mods window opens (else the session). While the line shows, the MODS row takes CONTINUE's row height and caption placement, and the list (top-aligned) is lifted by a third of the extra height so the gaps under RISING and above the icons shrink alike; hidden, the row and the list are exactly as attached. An optional accent-red dot before the line exists as an option (off; `auto_update subtitle_dot`). The names, versions and reasons are on the Install tab (the update list and the line `Updated automatically at 14:05: …`) and on the mod's page. The in-game MODS tab has no subtitle.
- **While connected**, **Update** and **Update all** leave a mod the server checks at another version (its live handshake rows) alone; its row reads `… · not now: the server you are on needs 1.0.0` with no **Update** button.
- **Update list.** On the Install tab (Simple and Advanced), under the restart bar and above the column header, while N > 0 or a mod is kept: a band `Updates · Checked 14:05 · 2 updates` with **Update all**, then up to four rows (`… more not shown` in the band past that): `ChatSkin 1.2.0 → 1.3.0`, `BroaderMap 1.4.2 → 2.0.0 · major`, `… · needs ExampleCommandFramework (not installed)`, each with **Update** and **Keep 1.2.0** (the pin). Kept mods follow, muted (`ChatSkin kept at 1.2.0 · 1.3.0 available`), with **Unpin**. The rows are pinned rows, not list rows, so the list's scroll and icon window are unchanged.
- **Update all** ([decision 7](#decisions-2026-10-09)), and a row's **Update**. Each package is downloaded, inspected and planned with its dependencies (off the main thread) first; then one confirmation lists every update (`from → to`, `major`, the first lines of the new version's `CHANGELOG.md` read from the downloaded package, so no extra request, `also installs X` for each new mod the plan would install, and `cannot update: <reason>` for a refusal). **Update** (one) or **Update all** writes each package in turn through the Install tab's own pipeline (`PlanWithDependenciesAsync`, `ExecuteWithDependencies`: planned again right before its write, dependencies first, to the client); **Cancel** writes nothing and releases the downloads. The result dialog says `ChatSkin 1.3.0 loaded now. BroaderMap 2.0.2 loads at the next start.` A refusal stops nothing else.
- **Mod page.** Under the kept-versions line: **Updates** (the per-mod dropdown), **Roll back to 1.2.0** when an older version is kept ([Rollback](#rollback)), and the versions that failed to load with **Clear failed versions**. Built in phase 2.

### Pre-join prompt

Decided 2026-10-09 ([decision 2](#decisions-2026-10-09)), on by default, `[AutoUpdate] PromptBeforeJoin`.

When the player joins a server (the Join Game browser's join, Direct Connect, a rejoin from the title screen, the bridge's `connect`; not hosting a private game) and at least one installed, managed, unpinned mod has an update that server accepts, Progenitor holds the join and shows one dialog: `Mod updates are available` · `ChatSkin 1.2.0 → 1.3.0, BroaderMap 2.0.1 → 2.0.2.` with **Update first**, **Join anyway** and **Cancel** (Escape). Built as a slot-routed prefix on `GameHelper.LaunchGame(GameConnect)`, the one call every client join ends in: it returns false to hold the launch and keeps the `GameConnect`, which is launched again unchanged after the answer. It fails open: anything it cannot read lets the join through. The decisions are a game-free state machine (`PreJoinFlow`): a join stays held only while one of its dialogs is open or its update runs. A dialog that goes away without an answer (another dialog took the screen, its panel was hidden, Core unloaded: `UiDialog.OnDropped`) releases the hold, and a new launch that finds a hold with neither replaces it, so a join can never stay blocked. A held join dropped by a Core reload is logged (`a held join was dropped because Core is reloading; join again`). A join through the game's password view (`LaunchPasswordProtectedGame`) is not held in phase 1.

- **The server's version wins.** Before a connect the client cannot ask the server, so each handshake request is remembered per dialed server (`BepInEx/config/progenitor-server-requirements.json`: mod id, version and rule, the 32 newest servers), keyed by transport: `steamipv4://<address>:<port>` (or `lidgren://…`) for an address join, `steamp2p://<steam id>` and `eosp2p://<id>` for a peer-to-peer one. An update is offered only when the remembered rule on any of the package's plugins accepts its newest version (Exact: that version; Minor: same major.minor; None, or a mod the server does not check: any); otherwise it is listed as `Not offered: ChatSkin (this server needs 1.2.0)`. Without range data (below) an update is never offered past the version that server required at its last handshake. A server joined for the first time is not known yet, so every update is offered and the join flow's own version handling applies at the handshake, as before. The version store keeps both versions.
- **Ranges and the server's match (mod compatibility C3; [design](mod-compatibility.md#tie-in-with-auto-update)).** For an update of a mod to V, with the server's remembered version S, the prompt predicts the server's join evaluation (`ServerVersionCheck`):
  - V equal to S always passes.
  - When the server's **match** is known, it decides alone: `exact` offers only S and never anything newer (`Not offered: ChatSkin (this server requires exactly 1.2.0)`); `minor` needs S's major.minor (`… requires 1.2.x`); `at-least` needs S or newer; `any` accepts anything. The match comes from the server's signed catalog (`ManifestMod.Match`: an admin's per-mod rule, or the strict mode). Without it, **Exact version for all** or **Same minor for all** come from the server's mode: the latest signed catalog's `matching` when it carried one (a catalog re-signed after an admin's change), else the join's request bits (`MatchExact`, `MatchSameMinor`), read through the rule bytes the server rewrote for the mode and any per-mod rule.
  - Otherwise the ranges decide. When V is newer than S, V's own range must include S (`1.4.0 works with any 1.4.x version, not this server's 1.2.0`). A newer version whose range includes the server's version is offered even when the server's attribute rule was Exact. When V is older, the server's range (`ManifestMod.Peers`) must include V.
  - V's range is its effective range from its verified inspection (`effectivePeers` in `progenitor-cache/verified/…`, [mod-manifest.md](mod-manifest.md#package-inspection-compatibilitypeers-mod-compatibility-c3)). A version that was never inspected, or a server range that is not known, falls back to the cap above. Ranges decide only once the server's catalog has given that mod's facts (`peers`): before that (a first join, a server older than C3) the request's rule byte is the only evidence, so the cap above applies. An exact match compares the version strings, as the server does (`1.2.0+abc` is not `1.2.0+def`). A remembered match is reused only while the next request carries the same rule byte and mode.
  - The remembered requirements gain per-server `matching` (`exact` or `minor`) and per-mod `peers` and `match` in `progenitor-server-requirements.json`. These are written when the request is seen (the mode) and when a verified catalog arrives (`peers`, `match`; kept across the next request while the version is the same). Older files load as before.
  - The prompt offers only the newest version (it does not search for an older one that passes). The same evaluation gives the connected Install tab its `not now: the server you are on requires exactly 1.0.0`. It also picks the kept copy at the handshake (`ModVersionSelect.PickFor` with `KeptCopyRanges`): a copy passes when the evaluation does, with the loaded build's declaration, else the copy's verified inspection, as its range. So a newer kept or active copy that vouches for the server is not swapped out. With no range data that choice is today's.
  - Source-checked and game-free tested (`PreJoinRangeTests`), not live-verified.
- **Update first** runs the same runner as **Update all** on the offered mods without a second confirmation (the prompt named them). An update that would install a mod the player does not have still asks first (decision 3); **Cancel** there returns to the prompt and never connects. A hot update is waited for until the reloader reports the new image (its sha256) loaded for that plugin, at most 15 s, then the held join is launched; past that the player is asked **Join anyway** / **Cancel**. An update that needs a restart asks `This update needs a restart` with the result line and **Restart and join** (the restart bar's restart with this server as the rejoin target; only for an address join without a password) / **Join with the current version** / **Cancel**. A failure asks `Not every update was applied` with the reasons and **Join anyway** / **Cancel**. Nothing sends the player back to the server list.
- **Join anyway** joins at once. The prompt is not shown again for the same server and the same versions this session.
- The prompt never holds a join that the install window would hold anyway: a mod the server requires and the player lacks is the install window's job, unchanged.

### Apply window

An automatic client update is applied only when **all** hold: no client world, no join in progress (the join screens closed, no Thunderstore batch, no reconnect, no rejoin record fresh), no hosted private game, no Core swap in flight, and the version store's own "nothing of the join runs" gate is open (the same gate it uses to restore the player's version on leaving). In practice: at the title screen, and right after leaving a server once the version store has restored the player's versions.

**In a world nothing is applied**, even a hot update. The connected server judged the loaded versions at the handshake; swapping one mid-session is "swapped the version of a required client mod" under the client mod policy, which warns or disconnects ([client-mod-policy.md](client-mod-policy.md#what-happens-mid-session)). In a world the client may download and verify an update so that leaving applies it at once; it writes nothing into a load folder.

### Applying

- **Hot update.** Through the version store, as a swap: the active copy is parked in `progenitor-versions/` (journal first, read back), then the new copy is written in place under the same file name, so the reloader unloads and loads it in one scan. The update waits for the reloader to report the new plugin loaded (`LoadedPluginNames`, at most 15 s).
- **Restart update.** The active copy is parked with a `.uninstall` marker; the new copy goes to `progenitor-pending/` and is ledgered `pending`, exactly as Use version's restart route. The pending-restart bar counts it (`2 mods load after a restart`). Progenitor never restarts the game for an update; the player presses the bar or simply plays on, and the next start applies it.
- **Result.** No dialog: the line under MODS counts what was updated or failed ([Where updates show](#where-updates-show)); the full sentence (`ChatSkin 1.3.0 is installed and loads now. BroaderMap 2.0.1 loads at the next start.`) is on the Install tab and in the log. A batch with nothing applied shows nothing.

### Connected to a server that needs another version

- A mod whose active copy was **placed for a server** (`active.forServer`) is never auto-updated while placed; the update applies to the player's own line after the version store restores it on leaving.
- After an update the previous version stays kept as the player's own copy (`userInstalled`), protected from eviction while it is the newest kept copy that is not active. At the next join to a server with an **Exact** (or **Minor**) rule for the old version, `ModVersionSelect` picks the kept copy at the handshake: no download, no restart for hot mods.
- If the kept copy was evicted (bounds: 3 copies, 128 MiB), the join screens install the server's version from Thunderstore as today, and the version store keeps the updated copy as the player's preferred one.
- An auto-update never changes `preferred` to an older version and never overrides **Keep this version**.

### Rollback

**Mod files, always** ([decision 8](#decisions-2026-10-09)). Every update, by hand or automatic, leaves the previous version in the version store (`progenitor-versions/`), protected from eviction while it is the newest kept copy that is not active. The mod's page shows **Roll back to 1.2.0**, which swaps it back through the version store (hot when both copies hot-load, else at the next start) and pins the mod at that version until the player unpins it, so the update is not re-offered at once.

**Automatic rollback after a failed load** uses the same copy. A hot update whose plugin does not load within 15 s, or whose load logs an exception from the reloader, is swapped back through the version store (the parked copy returns now). A restart update whose plugin is absent from the loaded set after the next start is swapped back the same way (now when the old copy hot-loads, else queued for the following start, and the bar says why). Either way the version goes into the failed list (`progenitor-auto-update.json` → `failed[<key>] = [version, reason, utc]`): it is never retried; the next newer version is. The line under MODS reads `UPDATE FAILED`; the Install tab and the log say `BroaderMap 2.0.1 failed to load and was rolled back to 2.0.0. It won't be tried again automatically.`, and the mod's page lists the version with **Clear failed versions** (after which it is tried again).

## Server

The server runs unattended: no admin needs to be logged in. Everything below runs on the server's own Core, with the server's own Thunderstore fetch.

### Applying

Each plan is split by what the update touches:

| Update | Players online | Server empty |
|---|---|---|
| **Server-only, hot** | Applied now: the new image replaces the old in `progenitor-reload/` under the same file name (the old one backed up first, below). | Applied now. |
| **Both-sided (clients need it)**, hot | Held. Applying it re-signs the catalog and changes a requirement under players in the world. | Applied now (no player is affected; joiners get the install window). |
| **Restart update** (any side) | Staged in `progenitor-pending/` with the old file marked `.uninstall`, ledgered `pending`. | Staged, then applied by the restart rule. |
| **Progenitor Core**, protocol unchanged | Held. A Core swap reloads every consumer plugin. | Core swap (below). |
| **Progenitor Bootstrap**, or a protocol change | Staged as `.next`. | Applied by the restart rule. |

"Empty" means no connected `User` for `EmptyMinutes`. Hot applies while empty re-check that nobody connected before the write.

### Restart rule

- **At the next start (default in every mode).** Staged updates wait for whatever restarts the server next (a host's daily restart, an admin's **Save and stop**, a crash). The Server tab status and every admin's Install tab say `2 server updates apply at the next restart`. Progenitor never stops the server under this rule.
- **Restart when empty** (`RestartWhenEmpty`, opt-in, off by default: [decision 4](#decisions-2026-10-09)). The server applies restart-needed updates at the first moment no players are online, after the quiet period (`EmptyMinutes`, default 5, counted from the last disconnect). At that moment the server re-checks that nobody is connected or joining, then:
  1. takes the pre-update world backup when **Back up the world before updating** is on ([Rollback](#rollback-1)); a failed backup cancels this restart and logs it;
  2. writes the apply journal (below);
  3. saves and quits through the stop request's server path (`TriggerSave`, `ModSave.SaveAll`, quit), so Bootstrap promotes `.next` files and the next start promotes `progenitor-pending/`.

  A player who connects during the quiet period restarts the count. A restart cancelled by a failed save or a failed backup is retried at the next empty moment, never in a loop.
- **Admin notice** ([decision 7](#decisions-2026-10-09)). Admins online get a Progenitor notice when server updates are waiting (`3 updates waiting for a restart`) and when updates were applied (`ChatSkin 1.3.0 applied live`), once per batch, with **View** (the Server tab's Updates group) and, while restart updates wait, **Restart now**.
- **Restart now** warns players first: a System chat line and the Progenitor notice, `The server restarts in 5 minutes to update mods: ChatSkin, BroaderMap.`, again at 1 minute, then steps 1 to 3 above. Nobody online skips the wait. An admin can cancel during the warning.

### Rollback

- **Mod files, always** ([decision 8](#decisions-2026-10-09)). Before the write the old file is copied to `BepInEx/progenitor-updates/rollback/<plugin id>/<version>/` with its ledger row, and the Server tab's Updates group lists the previous version of each updated mod with **Roll back** (hot when both copies hot-load, else at the next start; the mod is then pinned at that version). Kept for the last 3 versions per plugin and deleted once a newer version has run for 7 days.
- **Hot route, automatic.** If the reloader does not report the new plugin within 15 s, or reports a load failure, the old file is written back (same file name, so the reloader loads it), the ledger row restored, and the version added to the failed list.
- **Restart route, automatic.** `BepInEx/progenitor-updates/journal.json` lists each staged file, its backup and the expected plugin id and version, written before the quit. After the next start, once the world has loaded, Core checks the loaded set: each update that did not load is reverted (the backup back to `progenitor-reload/` when it hot-loads, else to `progenitor-pending/` with the bad file marked, for the next restart), and the version goes into the failed list.
- **Pre-update world backup (opt-in, off by default:** [decision 5](#decisions-2026-10-09)**).** With **Back up the world before updating** on, the server takes one world backup per update batch, before the batch's first write, through the BACKUPNOW1 path. It is a new backup kind, **pre-update**, kept by its own count (`PreUpdateBackupKeep`, default 2) and counted only among pre-update backups, so it never evicts a manual or scheduled backup and `BackupKeepCount` / `BackupKeepDays` do not count it. It is skipped when any backup of any kind is newer than `PreUpdateBackupSkipHours` (default 6), and the audit line says which backup stands in for it. It is listed in the existing Backups dialog under its own heading, **Backups made before an update**, each entry labeled with the mods it preceded (`Before update · ChatSkin 1.3.0, BroaderMap 2.0.2`), and restores like any other entry ([world-restore.md](world-restore.md)).
- **Start loop.** A Core or Bootstrap update that keeps the server from reaching a loaded world cannot be undone by Core. Bootstrap counts starts in the journal and, on the second start in a row without Core's "world loaded" mark, restores the journal's Core and Bootstrap backups before loading Core (a Bootstrap change, phase 5).

### Audit trail

One line per step in the BepInEx log and in `BepInEx/progenitor-auto-update.log` (rolled to `.1` past 1 MiB), the format of `progenitor-remote-install.log`:

```
AutoUpdate <utc> op=<check|plan|download|apply|stage|restart|rollback|skip> package=<Namespace-Name> from=<v> to=<v> route=<hot|restart|held> result=<ok|failed(<reason>)|skipped(<reason>)> detail="…" files=[…]
```

A check that finds nothing writes one `op=check result=ok detail="no updates (N managed packages)"` line. Admin setting changes stay in `progenitor-settings.log`. The Server tab status row shows the last check, what is held and why, and the last five results; the bridge op `auto_update` (`status`, `check`, `plan`, `apply`, `history`) reads the same on either side.

### What players do after a server update

Applying a both-sided update re-signs the server's catalog with the new required version:

- **Players in the world** (only possible when a hot apply that found the server empty raced a join): the JOINNOTICE `This server's mods changed.` with **View mods**. A requirement changed mid-session never disconnects anyone ([client-mod-policy.md](client-mod-policy.md#what-happens-mid-session)); the notice's line points at **Install Mods**, where the player updates in place.
- **Players joining** with the old version: the server's `ServerPackageAvailability` already knows the new version is on Thunderstore (the same index read), so the join is held in the install window and the join screens install it; a hot mod loads and the join continues with no rejoin. A restart-only client mod gets **Restart and rejoin**. Nobody is sent to the join screen to fix something they can fix where they are.
- **Clients with Automatic updates** usually already have the new version, or get it at the next title screen.

## Progenitor itself

**Progenitor ships from GitHub Releases** (decided 2026-10-20, after Thunderstore declined to host it). It updates itself from its own signed release list on the repository's GitHub Pages site, not from the Thunderstore index ([Release list](#release-list-github)). Mods still come from Thunderstore.

The release zip `Progenitor-<version>.zip` holds the real `BepInEx/` tree: `BepInEx/plugins/Progenitor.Bootstrap.dll`, `BepInEx/patchers/Progenitor.Preloader.dll`, Core's folder `BepInEx/progenitor-core/` (`Progenitor.dll` and its address tables) and, since this change, the self-install record `BepInEx/progenitor-self-install.json`. The Thunderstore-layout zip (`packaging/thunderstore`, also attached to the release) packs Core's folder as `BepInEx/patchers/progenitor-files.zip`, which the preloader unpacks into `BepInEx/progenitor-core` at the next start whenever the archive changed (mod managers place only `plugins` and `patchers` files); it carries no record. Self-update reads only Bootstrap, Core and the tables, from either layout (`SelfImageReader`); it does not install or update the preloader. Its own listings are hidden from the Install tab; auto-update is the way it updates in place.

- **Date versions; protocols decide what is breaking** (decided 2026-10-09). Progenitor's version is `<year>.<month>.<build>` ([versioning.md](versioning.md)), for example `2026.10.143`. The year and month carry no meaning for updates: December to January can be a small change and a release within one month can be breaking. A Progenitor release is **breaking** only when it changes a compatibility protocol: the Bootstrap protocol (`CoreLayout.ProtocolVersion` / `BootstrapLink.ProtocolVersion`, currently 5) or the handshake protocol (`Handshake.ProtocolVersion`, currently 2), as read from the release's own images. Same protocols: a normal update, following **Update Progenitor** (`[AutoUpdate] Progenitor`: Automatic on a client, Notify on a server). A protocol change: notify only, and a click installs it by the restart route a new Bootstrap protocol needs. **Major versions** (`[AutoUpdate] MajorVersions`) applies to mods only, never to Progenitor.

- **Managed or not.** Progenitor updates itself only when its files match its self-install record (or a ledger `framework` row). A release zip carries that record, so an unmodified release extracted into the game folder is managed from its first start and follows **Update Progenitor** with no extra step. Changed files (the record no longer names them) and a mod-manager install only notify. A copy with no record (a zip from before releases carried one, which includes 2026.10.162) notifies; one click on **Update** installs a release through the normal path, and the record that click writes makes it managed from then on ([Release list](#release-list-github)).
- **Never on a development build.** A Core or Bootstrap whose version has a sub-release (`2026.10.12.3`, [versioning.md](versioning.md)), or a process with the Dev bridge loaded, never updates itself, so development deploys and test rigs are never overwritten.
- **Core.** The new `Progenitor.dll` is written as `progenitor-core/Progenitor.dll.next` with its address tables. Its `CoreLayout.ProtocolVersion` is read from the image's metadata before anything is staged. With the running Bootstrap's protocol, the update requests a Core swap in an apply window (client: the title screen; server: empty) and confirms it as [hot-reload.md](hot-reload.md#swap-core-and-confirm-completion) requires: not in flight, the expected image active, `lastReload.outcome` `ok`. A refused or restored-old-generation swap is a failed version. `[Reload] WatchCore` is not used.
- **Bootstrap.** The new `Progenitor.Bootstrap.dll` is staged as `.next`; Bootstrap promotes it at quit and it takes effect at the next launch. A protocol change stages both and swaps nothing live. The client's pending-restart bar counts it as `Progenitor update`; the server applies it by its restart rule.
- **Order.** Progenitor first, then mods that need the newer Progenitor, in the same pass when Progenitor applied hot, else after the restart.
- **Wire compatibility** between a client and a server on different Progenitor releases is the handshake's job, unchanged. Progenitor's own versions are not kept in the version store, and Progenitor never downgrades itself to match a server. Mod compatibility C4 (decided 2026-10-09; built 2026-10-10, game-free tested, verified live in part the same day): under a server's **Exact version for all** setting, the join screens' **Use Progenitor X** places the server's Core for that server only (a kept copy, else its GitHub release from the release list, checked against the server's sha256), automatic Progenitor updates wait while it is placed, and the player's own Core and self-install record come back after leaving ([mod-compatibility.md, C4 as built](mod-compatibility.md#c4-as-built)).

### Phase 5 as built

AUTOUPDATE5 (M6.5). Source-checked and game-free tested (`SelfUpdateTests`, `BootHealthTests`); the live result is at the end of this section. **Bootstrap changed** (the start-loop guard and `BootIdentity`): restart each process after deploying it. `CoreLayout.ProtocolVersion` is unchanged (5).

**Decisions, chosen 2026-10-09 from the design's recommendations and confirmed the same day:**

1. **Update Progenitor** defaults to **Automatic** on a client and **Notify** on a server.
2. A development build (a sub-release version on Core or Bootstrap) and any process with the Dev bridge loaded never update themselves; they only report (the Install tab row and `auto_update self_status`). The cfg-only key `[AutoUpdate] SelfUpdateDevOverride = true` lifts this for a live test only; it is never set on a player's install.
3. A Progenitor with no self-install record that a mod manager installed (a `manifest.json` beside Bootstrap, or an r2modman or Gale profile path) only notifies: `update it where you installed it`. One installed by hand is not **Automatic** either, but the Install tab's **Update** installs a release and records it, after which it is managed.
4. A release that changes a protocol only notifies (decided 2026-10-09, replacing "a major version (another year) only notifies"). Progenitor's versions are dates, so a new year with the same protocols is a normal update. [Protocol changes](#protocol-changes-notify-only) below.
5. Two starts in a row without the healthy mark restore the previous copy at the third start.

How an update is written (by hand, before a join and automatically alike): when the version store holds the mod's active copy in `progenitor-reload` and the update is one DLL with no new package, the approved image (approval recomputed, zip and image re-hashed) is kept as a copy in the store and swapped in. The old copy is parked (journal first) and the new one written under the same file name, so the reloader unloads and loads it in one scan. When the image is not hot-loadable, or the old copy cannot be unloaded (`ctx.UnsafeHarmony`, dependents, a retiring generation), it is queued in `progenitor-pending` with the old copy marked, and the pending-restart bar counts it. A hot update is waited for, then judged (`LoadCheck`, below); a failed or timed-out load is swapped back to the previous version. Everything else (companions, a new dependency, no active copy in the reload folder) takes the phase 1 install route, except that it is refused while the store has a version of the mod queued for the next start (it would put a second pending copy beside it).

The window during an automatic pass: the window is checked when a pass starts and again on the main thread in the same step as each write (the store's swap or the install route's write). When it closed meanwhile (a join started, a world loaded), the write is not made, the update reads `deferred`, it is not a failure and it is tried again at the next window. A join launched while an update is being downloaded or written waits for it (the pre-join gate holds it, at most 60 s, then decides as usual), and **Update first** waits for a running pass instead of failing. A copy placed for a server (`active.forServer`) is never updated while placed.

What the load check detects (`Install/LoadCheck.cs`; the wait is 15 s, pushed back while the loader is busy with a Core swap or another reload, at most 120 s):

| Case | Detected as | Then |
|---|---|---|
| A Progenitor plugin whose `OnLoad` threw | failed (Core's registry reads `Failed` for the new image) | rolled back, the version goes into the failed list |
| Any plugin whose load threw in the reloader (a plain BepInEx plugin included) | failed (the reloader's record `BepInEx/<stem>.delta-state`, written after the write, says `loaded=0` with the exception) | rolled back, failed list |
| The new image loaded, and registered (`Loaded`, or turned off / dormant) or a plain plugin | loaded | kept |
| Loaded by the reloader but not registered yet, or still the old image | waiting | waited for; at the deadline rolled back **without** the failed list (tried again next session) |
| No Bootstrap snapshot (an older Bootstrap) and no reloader record | unknown | kept, reported "whether it loaded could not be checked"; never counted as loaded |
| A plugin that loads and misbehaves later, or swallows its own load exception | not detected | — |

The start check (restart updates, after the next start): each check names the exact image (sha256) it queued and is judged only on that image. Still queued with it: wait for a later start. The queue changed, or another copy is in place (a Roll back, a Cancel install, another install), or the queued copy is gone: dropped silently, nothing rolled back or listed. Otherwise the load check above: loaded, done; failed, rolled back and listed; not loaded, rolled back and tried again next session; unknown, dropped. Paths that replace or cancel a queue also drop its check (the mod page's **Roll back**, a cancelled queue).

Superseding a pending copy (phase 1 open issue 1): a newer update over a store-queued one replaces the pending file and its ledger row (`Requeue`, journaled like a swap: the journal first, then the new image moved over the queued file under the same name, then the books and the manifest; a crash before the move undoes it at Core start, after it finishes it, and there is never a second pending copy of the plugin); a pending copy another install wrote for the same package is replaced when Progenitor's install ledger names it as that package's pending row with those bytes (`PendingSupersede`, also in `InstallStaging`); anything else in the way is still refused. A queued update whose pending copy a Cancel install removes is dropped within two seconds (the old copy's removal marker goes and its ledger row comes back), so the next start never leaves the player without the mod.

`[Install] DevThunderstoreUrl` (phase 1 open issue 3): every two seconds, at the title screen and in a world (INSTALLERR1), and on every Install-tab build, the index URL the catalog was built for is compared with the setting's; on a change the catalog, its refresher and the Install tab are rebuilt and one check is made. The loopback and developer-tree rule is unchanged.

The pre-join prompt follows Automatic mode: what Automatic already applied is not offered (there is nothing to offer), and a version in the failed list is held back (`… failed to load before`). The server's remembered requirement still caps the offer, and the version store keeps the older copy to swap in at a join that requires it.

Limits: the game-start check is still open (an update is found only by an index read the client makes anyway; `auto_update check` makes one by hand); the Install tab drawer has no per-mod dropdown; kept copies of updates are the player's own and are never evicted by the store's bounds, so many updates of one mod accumulate (`join_ui` versions `forget` deletes one); a download or inspection failure, a deferred write and a load timeout skip that version for the session only, and only a load that threw is remembered; the notice lives in memory (a Core reload forgets it). `progenitor-auto-update.json` is written under one lock, atomically; a file that does not parse is moved aside (`.bad-<utc>`) and logged, never written over. Bootstrap's start-time promotion was not changed: it still promotes whatever is in `progenitor-pending`; Core keeps one pending copy per queued plugin (the in-place requeue, the install route's refusal), so a second copy can only come from outside Progenitor.

What differs from the design above:

- **Cadence.** The server checks once its world has loaded, then every `CheckHours` (default 6, the design's recommendation; the cadence question was still open). Restart when empty then waits for the next quiet period (not counted as a failure); Restart now falls back to its warned countdown.
- **Clients need it, read from the update too.** An update is server-only only when the new version's `progenitor.json` declares `side: server` and the running copy is not required at the handshake or by the client mod policy. A new version that declares both sides or nothing, or an old copy that failed to load, is held while players are online.
- **The countdown owns the server.** No check or apply pass starts while a Restart now countdown or a restart runs (Check now answers `a restart countdown is running`); a restart waits for a pass that started before it. The apply journal entry is written before the version store's write and dropped again unless the update was staged.
- **A reload ends a countdown out loud.** A Core hot swap or shutdown during the countdown cancels it and tells the players in chat and the admins on the notice (`The restart is cancelled: Progenitor reloaded. Updates still wait for a restart.`); the next generation does not resume it.

- **Check now is locked with the group** (`updates` in `[ServerSettings] LockedInGame`).
- **Admin edits write one cfg line.** An admin-channel edit (and the bridge's `auto_update set`) sets the value in memory with BepInEx's save-on-set held off and rewrites only that key's line in the server's `progenitor.cfg`, atomically, so hand edits of other keys made while the server runs survive.
- **Older Progenitor ignores pre-update backups.** They carry their own sidecar name (`progenitor-backup.pre-update.json`), so an older Bootstrap or Core never lists them, never counts them into the restore chain's keep count (where they would prune before-restore backups) and never deletes them ([world-restore.md](world-restore.md#pre-update-backups)).

## Safety rules

1. **Thunderstore, or the developer's local stand-in.** Every update comes from the V Rising community index over `https` on Thunderstore's hosts, or, in a developer tree only, from the loopback dev Thunderstore (`[Install] DevThunderstoreUrl`) or `[Install] LocalIndexPath` (cfg-only test configuration, [decision 10](#decisions-2026-10-09)). Local test sources and client relays never feed updates.
2. **Verified bytes.** The downloaded zip's size must equal the listing's; inspection checks the declared sha256 of the installable DLL; admission decides hot or restart as for a manual install. A failure is logged and the version is not retried until a newer one appears.
3. **Only what Progenitor manages.** No file outside a ledger row is touched. Managed-elsewhere mods, `BepInEx/plugins` mods and changed files are reported (**Notify** at most) and never written.
4. **No unasked new packages, no downgrades, no package switches.** An update that needs a mod that is not installed asks first and names it ([decision 3](#decisions-2026-10-09)).
5. **Pins and exclusions win** over every global mode, the badge, the update list, **Update all** and the pre-join prompt.
6. **The server's required version wins** at a join: the pre-join prompt never offers a version past it.
7. **The hash allowlist wins:** with `progenitor-allow.txt` present, only listed hashes apply.
8. **Backoff and memory.** Index failures back off per owner; a version that failed to download, inspect or load is remembered per side and skipped.
9. **No forced restarts.** The client never restarts itself; the server restarts only when an admin presses **Restart now** (after warnings) or under the opt-in **Restart when empty**, with nobody online.
10. **The live-server fence holds.** Every process operation keeps the existing fences (full-path matching, the forbidden live-server folder).
11. **Every action is logged** with the package, versions, route and reason.

## Decisions (2026-10-09)

Answers to the design's open questions, 2026-10-09.

**Progenitor's own version is a date (decided 2026-10-09).** Progenitor's version is `<year>.<month>.<build>`; major/minor does not fit it. A Progenitor update counts as breaking only when a protocol changes (the Bootstrap protocol, the handshake protocol, or any other compatibility protocol constant phase 5 reads from the package images). Same protocols: a normal update following `[AutoUpdate] Progenitor`. A protocol change: notify only, with the restart route a Bootstrap protocol change needs. **Major versions** stays a mods-only setting. [Progenitor itself](#progenitor-itself).

1. **Defaults.** Clients: **Automatic** for mods, **Notify** for major versions. Servers: **Notify**. Restart when empty and the pre-update world backup are opt-in server settings, **off by default in every mode**.
2. **Pre-join prompt** (new, on by default, its own client setting `[AutoUpdate] PromptBeforeJoin`). When the player picks a server and an installed mod has an update, offer **Update first** / **Join anyway**. Never offer an update past the version that server requires; the version store keeps both. [Pre-join prompt](#pre-join-prompt).
3. **Dependencies.** An update that needs a mod the player does not have asks first.
4. **Server restart when empty** (opt-in). The server applies restart-needed updates at the first moment no players are online, after a quiet period (default 5 minutes empty). Admins online get a notice (`N updates waiting for a restart`) with a **Restart now** action that warns players first. [Restart rule](#restart-rule).
5. **Optional pre-update world backup.** A new backup kind, **pre-update**, with its own small keep count (default 2), so it never evicts manual or scheduled backups. Skipped when any backup is newer than X hours (default 6). One backup per update batch. Shown in the existing Backups list, labeled with the mods it preceded. [Server rollback](#rollback-1).
6. **Badge.** `N updates` on the Mods button and on the title screen.
7. **Update all and admin notices.** An **Update all** button on the Install tab, with a version and changelog summary before confirming; an in-game admin notice when server updates are waiting or were applied.
8. **Mod-file rollback.** Always keep the previous version in the version store, with a **Roll back** action on the mod's page. This also backs the automatic rollback after a failed load. [Client rollback](#rollback).
9. **Keep this version.** A per-mod pin.
10. **Live testing** uses the existing local test index (`[Install] LocalIndexPath`, `tools/make-dummy-package.ps1`) for two versions of a test package, not Thunderstore. Refined the same day: a local Thunderstore stand-in that new versions can be published to (`tools/local-thunderstore`, [test-rig.md](test-rig.md#local-thunderstore-dev-only)), with http allowed only for loopback in a developer tree.
11. **Phase order.** Phase 1 is client update detection (reusing the existing conditional index reads, no new polling), the badge, the Install tab's update list and **Update all** in Notify mode, and the pre-join prompt. No automatic applying yet.

### Still open

Confirmed on 2026-10-09 (the defaults stay as built): the server cadence (a timer every `CheckHours`, default 6, minimum 1, as the one exception to "no timer polling"); Progenitor's own update defaults ([Phase 5 as built](#phase-5-as-built)); Restart when empty requiring `[AutoUpdate] HostRestarts`; Roll back and **Update Progenitor** on a server staying cfg and bridge only for now; the title line without the accent dot and with the one-third lift.

Still open:

- **Client game-start check** (phase 2): one conditional index request per game start when the cached index is older than 6 hours, so a player who never opens the Install tab or joins a server still hears of updates.
- **Server tab rows** for Roll back and **Update Progenitor**: a possible follow-up; today they are bridge actions and the `[AutoUpdate] Progenitor` cfg key.
- **Set-time restarts:** the earlier design's `AtTime` rule (restart at a set server time) is not part of the decision of 2026-10-09 and is not planned.
