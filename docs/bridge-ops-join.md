Operation reference for the [development bridge](bridge.md), part 4 of 5: message recording, server rules, world backups, the server description and browser, the join screens, and the join admin popup, with their acceptance recipes. Other parts: [core, entities and samples](bridge-ops.md), [players, world and capture](bridge-ops-player.md), [Mods workspace UI](bridge-ops-ui.md), [input, install and session](bridge-ops-client.md). ## `messages_record`

Both sides, main thread (mod compatibility C5). Records a mod's real `ctx.Messages` traffic on this side, sent and received, as replay fixtures for [Progenitor.Testing](modules.md#testing-your-mod-across-versions-mod-compatibility-c5). Core's `ModMessageRecordBridge`, reached by reflection; no plugin or network path reaches it. **Source-checked, built, game-free tested (`ModMessageRecordTests`: the format and its schema, dedupe, every bound, the folder cap, the write queue and its writer thread, the path guard, the argument parsing) and run live 2026-10-10** on the Steam client and the isolated test server with SampleServerLed and SampleClientLed: written > 0, no drops, sender-side schemas, payloads byte-identical to the checked-in fixtures for the same values, recordings replay ([results](mod-compatibility.md#c5-live-test-2026-10-10)). The time, message-count and byte bounds and the folder cap were not reached live.

| Arguments | Result |
|---|---|
| `{"action":"on","mod":"<mod guid>"}`, optional `"seconds"` (default 120, at most 1800), `"maxMessages"` (fixtures written; default 200, at most 5000), `"maxBytes"` (default 1 MiB, at most 16 MiB, and at most what is left under the folder cap). `mod` is required: a GUID, or `"*"` to record every mod deliberately | Starts a session (replacing a running one) and returns its status plus `folderBytes`; a missing `mod` is a bridge error (`args.mod is required for on`); refused (`ok: false`) when the folder already holds the cap |
| `{"action":"off"}` | Stops the session, waits up to 2 s for queued writes, and returns its status |
| `{}` or `{"action":"status"}` | The running or last session: `{side, recording, stoppedBecause (time, messages, bytes, stopped), root, mod, seconds, elapsed, maxMessages, maxBytes, seen, written, duplicates, bytes, queued, dropped, diskCap, messages [{mod, modVersion, message, written}], errors}` |

Files go to `BepInEx/progenitor-dev/messages/<mod>/<mod version>/<message>@v<n>/<sha12>.bin` with a `.json` sidecar (the fixture format). `<mod version>` is the **sender's**: this side's own version for a message it sent, the version in the sender's feature table for one it received (`unknown` when the table does not list it). A message this side sent with a `[ModMessage]` class carries its field schema in the sidecar; a received or hand-written one does not. A payload already on disk counts as a duplicate and is not rewritten. Each fixture costs its payload plus 512 bytes against `maxBytes`.

**Disk cap.** The whole `progenitor-dev/messages` folder may hold at most 64 MiB across sessions (`ModMessageRecorder.DiskCapBytes`): a session's byte budget is cut to what is left, and a new session is refused once the folder is full. Move the fixtures you keep into your test project and delete the folder.

**Off the main thread.** The send and receive paths only add the message to a bounded queue (256 entries); one background writer thread hashes and writes. A message that finds the queue full is dropped and counted (`dropped`), never waited for. The session stops itself at the first exhausted bound and logs `Messages: recording stopped (<why>): N fixture(s) written to <root>` (with the drop count when there were drops); it belongs to the running Core generation, so a Core swap ends it. Recording runs on the send and receive paths only while a session is active.

Acceptance procedure — run 2026-10-10, passed ([results](mod-compatibility.md#c5-live-test-2026-10-10); `.serverled announce` needs an administrator, so the test lowered `AnnounceMinutes` instead):

1. Deploy a sample that exchanges messages (for example `Progenitor.SampleServerLed`) to the isolated test server and the test client; join.
2. Client: `node tools/mcp/call.mjs client messages_record '{"action":"on","mod":"progenitor.sampleserverled","seconds":120}'`. Server: the same with `server`. Also check `{"action":"on"}` alone is refused for the missing `mod`.
3. Exercise the mod (change the sample's preferences on the client; `.serverled announce` as admin).
4. `messages_record {"action":"status"}` on each side: expect `written` > 0, `dropped` 0 and the message names in `messages`. Then `{"action":"off"}`.
5. Copy `BepInEx/progenitor-dev/messages/progenitor.sampleserverled/` from each side into a scratch fixtures folder and run the sample's replay test against it; expect it to pass. Compare the live payloads with the checked-in `source: "test"` fixtures of the same version: the same message and values should give the same SHA-256 (the same bytes), and the sent messages' sidecars should carry the same `schema`.
6. Clean up: remove the sample from both reload folders, and delete `BepInEx/progenitor-dev/messages/` if the fixtures are not kept.

## `server_rules`

Core's `ServerRulesTestBridge`, reached by reflection. Built and game-free tested, not live-verified. Nothing it returns is a password: the password reads only `{set, nextSet}`.

| `{"action":"schedule"}` | server | `atStart, everyHours, keepCount, keepDays, schedule` (the text), `nextDueUtc` (null when off), `lastScheduledUtc`, `job` (or null), `last` (this Core's last backup: `ok, summary, reason, kind, trigger, path, folder, name, bytes, files, attempts, warnings, pruned, startedUtc, finishedUtc`), `status {start\|interval\|manual: {ok, summary, name, by, finishedUtc}}` and `statusPath` (`BepInEx\progenitor-backups.status.json`) |

| `{"action":"open_backup_now"}` | client | Opens the Back up now confirmation as the button does (or the refusal notice); confirm with `mods_ui dialog_choose {"choice":"yes"}`. |

Log lines (server): `WorldRestore: request <id> written: <source> over <save folder>, wipe <mode>, keep <n>[, restart now]`, BACKUPSDLG1 `WorldRestore: the restore request changed (<written|written, restart now|cancelled|countdown ended>; pending <id|none>[, countdown running]): told N admin(s).`, the audit line in `progenitor-settings.log` (row `progenitor/ServerRules/WorldRestore` or `…/KeepBackups`), `WorldRestore: restart now for request <id>: the server stops in 60 s.`; at the next start Bootstrap's `WorldRestore: recovery: …` lines for an interrupted restore, `WorldRestore: <step> ok|FAILED: …`, the result line, `WorldRestore: FAIL CLOSED: …` (the process then exits with code 75), and the `WorldRestore phase0:` lines ([world-restore.md](world-restore.md#phase-0-the-timing-line)). ### Forcing a refused join (JOINFLOW1)

Two ways, on the isolated test server only. Both need the client at the title screen first.

**A. An install window.** The server defers a missing required mod only when the client can fix it during the join: a Thunderstore package the signed catalog names for the row that serves the needed version (as the **server** reads the index), or a kept or turned-off copy the client declares. Set it up with a local index on both sides, as in [the install window recipe](test-rig.md#install-window-from-thunderstore-tofu-and-legacy-cleanup) steps 1–4, then:

1. Move the client's Sample out of its reload folder (the reloader unloads it within a second):
   ```powershell
   New-Item -ItemType Directory -Force <workspace>\_hold | Out-Null
   Move-Item "C:\Program Files (x86)\Steam\steamapps\common\VRising\BepInEx\progenitor-reload\Progenitor.Sample.dll" <workspace>\_hold\
   ```
   The client log shows the Sample unloading. (Check the file name in that folder first; a deploy may have written it under its plugin folder.)
2. `client connect {"address":"127.0.0.1:9976","protocol":"Lidgren"}`. `InstallGraceSeconds` must be above 0 (default 60).
3. Expect, server: `Handshake: <name> deferred for 60 s to fix progenitor.sample on the client (thunderstore) (…)`; client: `ModManifest: install window opened: Mods needed: …`, then `JoinFlow: screens opened (install-window) …`. The Sample row reads `action install`, `thunderstore available`. `not deferred: '<id>' cannot be fixed during the join (…)` means the server has not read the package from its index (check its `LocalIndexPath` and the `read Thunderstore versions` line); `no install window is available for this user` means this connection already spent its window: disconnect and connect again.

**B. A hard refusal** (no install window): set the test server's `[Networking] InstallGraceSeconds = 0` in `<testserver>\server\BepInEx\config\progenitor.cfg`, restart it (`progenitor_test_server` `restart`), do step 1, then connect. Expect, server: `Handshake: <name> failed: Mod mismatch: …` then `ModManifest: deny descriptor for user N: 1 row signed fp=… with the join section` (when a message is set); client: `JoinFlow: screens opened (refused) …`.

Restore afterward: move `Progenitor.Sample.dll` back (and remove a copy a Thunderstore install put in `progenitor-reload`, with its `progenitor-install.json` row), put `InstallGraceSeconds` back (default 60) and restart the test server.
