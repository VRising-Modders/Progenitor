Design spec, M1

Progenitor

One library that sits between BepInEx and a V Rising mod, so the mod author writes gameplay and the library handles hooks, entities, networking, content registration, and the build-test loop.

Owner ExampleTeam Date 2026-09-02 License LGPL-2.1-only Target BepInEx 6 IL2CPP, pack 1.733.2 Status M1 shipped; hosted live test and two-player command check open

Summary

V Rising mods today are built directly on BepInEx plus a handful of small, overlapping helper libraries. Nobody has shipped a framework layer for it: a way to register new content that server and client agree on, a networking channel between the two halves of a mod, a UI toolkit, and any kind of development loop that isn't "rebuild, restart, walk over, look."

Progenitor is that layer, with one deliberate emphasis. The build-test loop is a first-class module, not an afterthought. A running server or client exposes a local debug bridge, and an external MCP server turns that bridge into tools an AI coding session can drive. The intended day-to-day experience is: describe a change, and the session builds it, hot-reloads it into the live game, exercises it, reads the log, and reports back. Milestone 1 landed on 2026-09-02: Core's lifecycle, hooks, entity toolkit, events, commands, networking, prefab registry, persistence, config, localization, and hosted launcher are in the tree and were exercised in-game by samples/Progenitor.Sample (cloned item, chat commands, save-file JSON). Two M1 checks remain: a live private-game launch of the hosted loader, and a two-player check that handled commands are not broadcast.

Dependency rule

A Progenitor mod depends on exactly two things: BepInEx and Progenitor. Progenitor itself depends only on BepInEx, and everything it provides is original code under the GNU Lesser General Public License, version 2.1.

Goals and non-goals

Goals

  • Single dependency. BepInEx is the only thing beneath Progenitor. It cannot be removed because it ships the interop assemblies that make the game's types callable from C#.
  • One package, every supported way of playing. Compatible Progenitor mods support single player, client-hosted games and dedicated servers. Bundled-server setup is managed for the player; a dedicated server retains its own installation folder and state. Planned local mod management defaults to client only. Linking a validated same-machine server adds server-only and explicitly opt-in combined installation; neither registration nor package requirements automatically changes both installations. A client connected elsewhere can still be managed independently. Server controls appear only after configuration and validation. Remote server management is outside this increment. See the package and local-target contract.
  • Content that both sides agree on. A mod registers a new prefab once, and the server and every connected client with the mod know what it is.
  • Own the outputs, not the systems. AI, combat, and other Burst-compiled systems are never rewritten. Progenitor gives mods a clean way to run their own ECS systems that take over the components those vanilla systems act on.
  • Hot reload as the default workflow. Change a line, rebuild, and the running game picks it up in seconds.
  • Machine-drivable. Everything a human does to test a mod can be done through the debug bridge, so an AI session can close the loop without a human in it.
  • Survive game patches cheaply. Hooks resolve by shape where possible, and the framework reports what broke rather than failing silently.

Non-goals

  • Adding new map regions. Terrain, lighting, navigation, and world bounds are baked subscene data. Out of scope permanently.
  • Replacing Burst-compiled simulation. A native detour module is planned as an optional escape hatch, not a foundation.
  • Replacing other chat-command frameworks for mods that already use one. Both can coexist on one server. Progenitor's command module is for Progenitor mods.
  • Working with EasyAntiCheat enabled. Same constraint as every V Rising mod.

Constraints

Runtime
BepInEx 6 IL2CPP on CoreCLR (.NET 6). Il2CppInterop generates the proxy assemblies. Unmanaged ECS systems and Burst jobs are native code and cannot be patched with Harmony.
Topology
Server-authoritative. Gameplay runs in the server process. Clients render and send input. Most modules are server-first; UI and assets are client-only. There are three ways the server process comes to exist, and Progenitor treats them identically: a headless dedicated server, a private game where the client launches the bundled server as a child process, and single player, which is the same child process with one player.
Licensing
Progenitor is licensed under the GNU Lesser General Public License, version 2.1, and is entirely original code. Existing libraries, MIT or GPL, are read for their mechanisms and mistakes and never copied. This keeps the license clean by construction and avoids inheriting anyone's shortcuts.
Distribution
Thunderstore under ExampleTeam, plus NuGet for the build-time reference. Other mod sites optional.
Hot reload rules
A reloadable plugin keeps all state in its Progenitor-owned context, never in statics. It does not inject IL2CPP types (custom MonoBehaviours). It registers every hook, system, and subscription through Progenitor so unload can reverse them.

Architecture

Progenitor ships as one plugin DLL with optional client-only and dev-only DLLs beside it. Mods reference the core assembly at build time and declare a BepInEx dependency on it.

Progenitor.Dev.Mcp separate process, dev machine only

MCP server. Talks to the debug bridge over a local socket and exposes tools to Claude Code or any MCP client. Never installed on a public server.

Progenitor.Dev optional DLL, dev only

Debug bridge: local socket, hot reload trigger, command and exec, entity inspection, structured log tail, status/save/store. Snapshot, restore, and screenshot are later.

Progenitor.Client optional DLL, client only, not yet shipped

UI toolkit over the game's canvases, keybinds and settings panel, asset loading, custom map layers and map replacement, and icon injection. The hosted-game launcher lives in Core, not here: a private-game child process is still a server, and server-side code must not branch on how that process was started.

Progenitor.Content part of core

Prefab registry with client sync (shipped), localization (shipped). Item / unit / ability / building / buff managers, drop tables, and world placement remain M2.

Progenitor.Core the required DLL

Plugin lifecycle and hot reload, ECS hook layer, entity toolkit, event bus, commands, networking and handshake, prefab registry, config, persistence, localization, hosted-game launcher. Patch-resilience report is later.

BepInEx 6 IL2CPP BepInExPack_V_Rising

Loader, HarmonyX, Il2CppInterop proxies. The one external dependency.

Everything above Core is optional. A server-only mod like Satisvampory would take Core and Content. A client-only mod such as a HUD tweak would take Core and Client. A mod declares which side it runs on, and Progenitor activates only that side in each process:

[BepInPlugin("example.satisvampory", "Satisvampory", "1.1.0")]
[BepInDependency("progenitor")]
[ProgenitorSide(Side.Server)]           // Server, Client, or Both
public class Plugin : ProgenitorPlugin<SatisvamporyContext> { ... }

That attribute is what lets one DLL be installed once and be correct everywhere. In the client process a server-side plugin is loaded but dormant. In the server process, dedicated or bundled, it runs.

Core modules

Plugin lifecycle and hot reload Shipped

Mods derive from ProgenitorPlugin<TContext>. The context object owns all mutable state, config, and registrations. Reloadable plugins live in their own folder, outside the BepInEx chainloader. A reload is unload followed by load of the new file. Unload reverses, in order: scheduled tasks, event subscriptions, named system callbacks, ECS hooks, Harmony patches by plugin ID, network message handlers, command registrations, and finally the context is disposed.

Collectible AssemblyLoadContext per plugin is live and verified: a content plugin can be unloaded and reloaded with a player still connected. Compatible Core generations also swap in process through Progenitor.Bootstrap. Bootstrap is the process-lifetime component and requires restarting each affected process when changed. Collection, protocol and allowlist guards can refuse a swap; see the current reload procedure and verification scope.

As built. Collectible is what shipped: each reload DLL is read into a byte copy and loaded in its own collectible ALC; after every Unload (including when it throws) the reloader sweeps EventBus, commands, Harmony id, and owned MainThread work so leftover delegates cannot pin the context. Authors implement OnLoad and do not override Load / Unload. PluginContext is the only surface a plugin needs: facades Events, Hooks, Commands, Content, Save, Net, Handshake, Config, plus Log, Patches, UnsafeHarmony (reading this property opts out of hot swapping), Side / IsServer / IsClient, World, Guid / Name / Version, Owner, and Track(IDisposable) for anything the wrappers miss. [ProgenitorSide] is read from the concrete type; a mismatch logs dormant and creates nothing. ProgenitorPlugin.WhenWorldReady fires at most once. The framework ticks from an injected FrameTicker MonoBehaviour from launch, including the client main menu.

Reload is triggered by the debug bridge, by an admin chat command, or on the client by a keybind. Plugins loaded after the game has already bootstrapped get their world-ready callbacks replayed immediately so a reload behaves like a fresh load.

[BepInPlugin("example.satisvampory", "Satisvampory", "1.1.0")]
[BepInDependency("progenitor")]
[ProgenitorSide(Side.Server)]
public class Plugin : ProgenitorPlugin<SatisvamporyContext>
{
    protected override void OnLoad(SatisvamporyContext ctx)
    {
        ctx.Commands.Register(typeof(SatisCommands)); // static classes cannot be generic type args
        ctx.Systems.Add("order-board", world => { /* After SimulationSystemGroup; M2 */ });
        ctx.Events.On<ChatMessage>(e => ctx.Log.LogInfo(e.Text));
        ctx.Handshake.DeclareSelf();
    }
    // OnUnload is generated: Progenitor reverses every registration above.
}
public sealed class SatisvamporyContext : PluginContext { }

Two things cannot be undone and are documented as such: IL2CPP type injection, and static state. Core injects the few types it needs once (FrameTicker), with stable names, so mods never have to.

Custom systems

ctx.Systems.Add is a named managed callback, not a real ECS system. Core runs it from a single SystemHooks Before or After on a game group type (Unity.Entities.SimulationSystemGroup by default). No new IL2CPP type, no TypeManager row, no World.CreateSystemManaged. Reload is dispose. Sitting next to a vanilla system is AddAfter<TAnchor>, or ctx.Hooks on that system; WorldSystemFilterFlags.ServerSimulation is a TypeManager creation filter, not an update group, and there is no ProjectM.ServerSimulationSystemGroup.

// default: After SimulationSystemGroup, this plugin's side world only
ctx.Systems.Add("order-board", world => { /* … */ });

ctx.Systems.Add("order-board.init", world => { }, new SystemAddOptions
{
    GroupType = typeof(InitializationSystemGroup),
    Phase = SystemPhase.AfterGroup,
    Priority = 10,
});

// sit after a vanilla system (named, owner-tracked; same seam as Hooks.After)
ctx.Systems.AddAfter<ProjectM.DealDamageSystem>("order-board.damage", world => { });

Injected SystemBase subclasses cannot be the reloadable-plugin API: ClassInjector has no unregister, so a collectible unload leaves native vtable trampolines pointing at dead managed methods. An injected class is also missing from TypeManager until Core writes the tables, and [UpdateInGroup] on a C# wrapper does not populate those tables, so injection stays a later Core-only spike if a real SystemState is ever required. This API is the M2 shape; it is not on PluginContext yet.

ECS hook layer Shipped

Prefix and postfix hooks on OnUpdate for managed and unmanaged systems, resolved by system type. The OnUpdate path is simpler than expected and needs no native detours: two Harmony patches, one on SystemBase.Update for managed systems and one on WorldUnmanagedImpl.UnmanagedUpdate for unmanaged ones. Both receive a SystemState pointer, which identifies the system, and both sit before the game's own "enabled and should run" check, so a prefix returning false skips the system entirely. That is what makes "own the outputs" possible: a mod can suppress a vanilla AI system for specific frames and run its own in the postfix.

Hook options: only fire when the system would actually run, and a throttle for hooks that don't need every frame. Also provides "run when these worlds exist" deferral for bootstrapping.

As built. Public names are SystemHooks.Before<T> / After<T> (and non-generic overloads) taking Action<SystemHookContext>, plus WhenWorldExists (singular). SystemHookContext carries World, SystemType, SystemName, and Skip (Before only; nested group updates get a fresh context). HookOptions: OnlyWhenSystemRuns (default true), EveryNFrames. Verified live on ServerBootstrapSystem and Burst MoveEntitySystem. The type must have an IL2CPP class pointer; a missing wrapper throws at register. Do not put ref SystemState in a Harmony signature. WorldReady comes from a per-frame name check, not from GameBootstrap.Start.

ctx.Hooks.Before<BehaviourTreeSystem>(ctx => { /* runs before vanilla AI ticks */ });
ctx.Hooks.After<DealDamageSystem>(ctx => { /* damage events already applied */ });
ctx.Hooks.WhenWorldExists("Server", world => { /* fires now if the world already exists */ });

Harmony cannot marshal by-ref struct parameters. Those entry points use a native detour instead of a Harmony patch: resolve the method pointer from the interop's NativeMethodInfoPtr_* field and apply INativeDetour.CreateAndApply. That is how the client receives custom events on ClientBootstrapSystem.OnReliableEventsReceived; a Harmony prefix there sees a zeroed struct and stalls the client. Read position on entry is 8 bits.

Entity toolkit Shipped

Typed helpers over EntityManager: Read<T>, Write<T>, Has<T>, TryGet<T>, buffer access, and a query builder that caches EntityQuery per plugin and disposes it on unload. Includes a "component monolith" that lists every known component type, used by the inspector and the patch-resilience report.

As built. Public names are ComponentIndex, EntityExtensions (Exists / Has / Read / TryRead / Write / Add / Remove / Describe), Query.Build / Entities (includes disabled entities unless opted out; caller disposes a Build query), Singletons.TryGetEntity / TryGetRawRW (never GetSingleton<T>), and PrefabLookup. Buffer access and the component monolith are omitted on purpose. Read/Write require C# unmanaged; interop structs with bool fields such as User go through GetComponentData<User>. Zero-sized ECS tags use the parameterless Add<T> / Remove<T>.

Event bus Shipped

Progenitor installs a fixed set of hooks once and republishes them as typed events. Mods subscribe instead of patching, so two mods reacting to the same moment never fight over one Harmony patch. The hook targets below are the moments mods most often need.

As built. EventBus.On<T>(handler, priority, owner) returns IDisposable; PluginEvents.On<T> records the owner. Higher priority runs first. An exception in one handler is logged and does not stop the others. Shipped events are WorldReady, PlayerConnected, PlayerDisconnected, and ChatMessage; Plugin.Frame is the tick. The rest stay the M2 list. Chat Harmony priority is 300 (ahead of another chat-command framework, typically at 200). Commands subscribe at bus priority 500 and cancel what they handle.

Commands Shipped foundation

UI-first authoring direction. Encourage Progenitor's client UI as the primary entry point for everyday player actions and settings when the client runtime is installed. Keep commands supported for shortcuts, administration, automation and applicable server-only workflows with unmodified clients. UI and command entry points should call the same underlying operation with the same server-side authorization. Author examples should demonstrate this shared behavior. This guidance does not require client installation for server-only mods, a separate screen for every command, or treating hidden/disabled UI controls as permission enforcement.

Command routing MVP — implemented offline; independently reviewed; coexistence with other chat-command frameworks unverified. Optional root-level shortcuts plus a qualified fallback under a configurable framework root (default p) and stable mod identifier. Administrators can disable, rename or assign shortcuts. Progenitor detects its own registration conflicts without silent replacement or load-order winners; unresolved shortcuts are disabled while valid qualified routes remain available. Both forms retain the same authorization and parsing behavior. Owned unload and swap must remove stale registrations without affecting other owners. Leave unowned commands available to other handlers; never fall through after a denied or invalid owned invocation. Keep server commands authoritative and client-local scope explicit. Live coexistence with another chat-command framework has not run. Not in a candidate.

Other chat-command frameworks remain optional, and mods built on one need not migrate. MVP coexistence still requires explicit alias configuration and a focused acceptance pass against another chat-command framework installed beside Progenitor. That pass includes overlapping commands, both help paths, exactly-once execution and reload cleanup. Patch priority alone is not proof of compatibility. Cross-framework conflict checks are unavailable, not passed. Future work also includes unified help views and autocomplete. See the roadmap.

Attribute-based chat commands with argument parsing, overloading, groups, remainder parameters, generated help, and a middleware pipeline for permissions and cooldowns. Written fresh, with the familiar attribute-based conventions. Planned beyond that: converters are registered per plugin and removed on unload, help output is localized, and command execution is async-safe so a command can await a network round trip without blocking the server tick.

Coexistence with a separately installed chat-command framework needs one deliberate choice. Such a framework may reply "command not found" and destroy the message for any dot-prefixed text it doesn't recognize, which would swallow Progenitor commands. Progenitor's chat hook therefore runs at a higher Harmony priority, handles its own commands, and lets everything else fall through untouched.

One resilience note: the chat patch reads the system's entity query through a compiler-generated field name that changes when the game is rebuilt. Progenitor resolves the query by component signature instead, so this seam stops breaking on patches.

As built. PluginCommands.Register<T> / Register(Type) / Register(object) / RegisterAssembly. A C# static class cannot be a generic type argument, so those go through Register(typeof(SampleCommands)). Attributes shipped: [Command], [CommandGroup], [Remainder]. Prefix default ".". Argument types are a closed set (string, int, long, float, double, bool). Per-plugin converters, localized help, and async execution did not ship; built-ins are .help / .h and .progenitor / .prog. Open: two-player check that a handled command is canceled and not broadcast to others.

Networking Shipped

Mods search. Search installed mod names and setting labels, sections and help text together. Group editable matches by mod while preserving setting scope and permissions. Keep keyboard focus in search while typing; provide links to open the mod and reveal a matched setting. Clearing restores the prior page and scroll position.

Planned: mod discovery and package capabilities (M4.4 / M3.11). The package contract defines Mods, Install mods and Configuration workspace tabs, explicit per-side hot-load/replacement/removal declarations, and dependency/runtime checks that determine the final restart requirement. The player MCP shares catalog search, descriptions and the approved installation plan with the UI. Catalog access grants no server authority; missing metadata never enables hot loading. Not implemented or live-verified.

Planned: coordinated mod deactivation (M4.4). An operator can request that an eligible server mod and its server-managed client functionality deactivate through Progenitor while player connections and the Dev bridge remain available. This is not implemented by ordinary catalog updates or hot reload. The authoritative design requires capability/ownership checks, cooperative quiescence, per-client acknowledgments, dependency ordering, disabled-state enforcement and recovery. Unsupported or unsafe cases refuse before teardown; no automatic kick, restart or forced unload. Each supported mod/resource class requires the specified qualification tests; arbitrary native cleanup is not claimed crash-proof.

A custom message channel riding on the game's existing netcode, with a version handshake at connect. Handshake compares the server's Progenitor mod list against the client's and produces a specific rejection message ("Server requires Satisvampory 1.1.0, you have 1.0.83") instead of a silent desync. Also carries config sync, so a server-defined config reaches clients for mods that render it.

Where client mods come from (decided 2026-10-05). Only from Thunderstore. A server never sends mod files to a client: it publishes a signed catalog naming the Thunderstore package for each mod it needs, and the player installs from the join screens or the Install tab after a per-server confirmation. The first verified catalog from an address pins its operator key (trust on first use); a later key change is flagged and never re-pinned. A refused join may be held open for a short install window when everything missing can be fixed on the client (a Thunderstore package the server confirmed serves the needed version, a kept or turned-off copy, or a pause). The earlier server-to-client transfer and consent panel were removed; what older builds installed from a server is deleted at client start. Source-checked and game-free tested; not live-verified. Rationale: client-mod-policy.md; details: mod-manifest.md.

The idea: reserve one network event ID and route that ID to Progenitor's message registry, with messages as blittable structs or custom serializers, plus a message version byte, a size guard, and per-plugin registration that unloads cleanly. Spike 1 proved the server-to-client send on the current game build. The chat-channel fallback is unused.

The server builds an events packet itself and sends it with ServerBootstrapSystem.SendPacketToUser, passing User.Index and the connected-index flag off. The client receives with a native detour on ClientBootstrapSystem.OnReliableEventsReceived, because Harmony cannot marshal by-ref struct parameters. Read position on entry is 8 bits, so the event id sits byte-aligned after the packet type. One custom event per packet: when the id is ours, consuming means setting the read position to the bit length; otherwise the trampoline runs.

As built. Public API is CustomEvents.SendToUser / SendToAll / SendToServer, OnReceive / OnReceiveFromClient, and TryRead<T> over an unmanaged struct (or a raw span). Max payload CustomEvents.MaxPayloadBytes (15 KiB). Typed [NetMessage] with strings did not ship; config sync is still later. Handshake: Require / Provide / DeclareSelf, at most Handshake.MaxMods (16) ASCII entries (guid 63 bytes, version 23). A mismatch is logged, sent as a result packet, then PlayerControl.Disconnect after 2 s so the result lands first. Comparison walks Required and ignores extra answer rows; a wire Count outside [0, MaxMods] is malformed. Unload drops the row by guid. Client-to-server receive is a native detour on OnDataReceivedServer (the whole packet unread); DeserializeReliableEventsPacketServer is never called on this build.

Config and persistence Shipped

Config is BepInEx ConfigEntry under the hood with a typed wrapper and file-watch hot reload. Persistence gives each mod a key-value store that is written alongside the world save and loaded when the world is ready, so mod data lives and dies with the save it belongs to.

As built (config). ConfigHelper.Bind is ConfigFile.Bind plus a disk watch (BepInEx only reloads when asked). Watches are refcounted per path, debounced 1 s, and marshaled onto the main thread. PluginContext.Config.Bind is a thin bind over this plugin's GUID.cfg and does not start a watch; call ConfigHelper.Watch(ctx.Config.File) for live reloads.

As built (persistence). ModSave.Store / ctx.Save is per-mod JSON beside the world's AutoSave_N.save.gz files, in a progenitor subfolder (<persistentDataPath>\Saves\v4\<saveName>\progenitor\<modGuid>.json on this build). Server only; the client is a silent no-op. Load on server WorldReady. Save is a Harmony postfix on TriggerPersistenceSaveSystem.TriggerSave (the one-shot entry; OnUpdate every frame is the wrong seam) plus a flush on PlayerDisconnected. Writes go to .tmp then move. A store created before the save folder is known is pending: in-memory dirty keys are merged over the disk JSON once the folder resolves (disk is the base; overlay keys win), so an OnLoad Set cannot skip the load and wipe the file.

Castles

Experimental planning tool: Castle blueprints reads the current heart allowance and samples ground for offline room candidates. Coverage limits eligible free ground while preserving existing structures and supplied access reservations. Candidates remain unapproved for construction; native placement, player traversal, progression and material payment require separate qualification. This tool does not expose a player construction API.

Not in M1. A consumer mod that draws a castle, checks where something can go, or builds on a plot needs the same server-side reads of territories, tiles, and buildings. That is framework work, not mod work. Requirement hand-off: docs/research/castle-module.md. Home is Castles/ under Progenitor.Core; placement is a separate gated API, not mixed into the reader. Distinct from Content world placement (camps and arenas on the map).

Priority order. Later items must not delay the earlier ones.

  1. Castle reader (server, pure reads). Plot: territory index to block set, bounds, heart entity, owner, clan, level, raided state. Tiles: floor present, floor type (treasury and others), room id, wall, door. Buildings on the plot: entity, prefab, tile footprint, rotation, interact tiles, kind (container, station, decor, heart). Deterministic ordering: buildings sorted by network id, tiles in row-major order. The client world already has the standing plot's outline; remote plots are the consumer's own protocol, so the client API is a thin subset of the standing plot.
  2. Occupancy query (server). Can footprint F at rotation R sit on tile T, by the same rules the game's build mode uses. Must be verified against real placements before a consumer trusts it: a finder that disagrees with vanilla will propose spots the game refuses.
  3. Placement and dismantle (server). Gated on spike 3. Place a prefab at a tile and rotation on behalf of a player, paying vanilla cost from a given inventory set; dismantle with the vanilla refund. Until the spike passes, this API does not ship.
  4. Unit movement lives in the Units module, not here. A consumer that applies a layout in batch never needs it. Must not gate the reads.
foreach (var plot in ctx.Castles.Plots) { }
var plot = ctx.Castles.PlotAt(entity);
var tiles = ctx.Castles.Tiles(plot);            // row-major
var buildings = ctx.Castles.Buildings(plot);    // by network id
bool ok = ctx.Castles.CanPlace(prefab, tile, rotation);
ctx.Castles.Place(...);                         // gated; spike 3
ctx.Castles.Dismantle(...);                     // gated; spike 3

Units

Not in M1. Split of responsibilities: Progenitor spawns units and exposes behavior; the calling mod defines the NPC (which prefab it clones, display name, appearance, what it does at each step). Progenitor does not ship any NPC design of its own. A consumer mod that needs a vendor, a guide, a builder, or any other live NPC uses this module. Requirement hand-off: the Units module section of docs/research/castle-module.md. Home is Units/ under Progenitor.Core. Distinct from the Content unit manager (stats, blood type, abilities on a prefab) and from Castles (plot and tile reads). This module must not gate the castle reads.

Server side. Spawn a unit from a prefab at a position (on a plot or anywhere), owned by a mod, with a display name; despawn. A servant-like prefab is the expected clone base. Reload-safe: units owned by a mod despawn on its unload.

  • Flags. Non-combatant, invulnerable, not interactable, not counted as a servant, saved or not as the mod chooses.
  • Movement. Walk to a tile using the game's own pathing, with arrived and unreachable callbacks. Gated on the unit-behavior research and a spike.
  • Behavior access. The game's unit behavior and AI state hooks (idle, move, play animation, face target, wait) as hookable steps a mod can sequence. If the game's behavior-tree or state-machine assets are addressable, expose read and selection of those scripts; otherwise the hook set is the minimum. Same research and spike gate as movement.

Events on the bus: UnitSpawned, UnitArrived, UnitUnreachable, UnitDespawned.

var unit = ctx.Units.Spawn(prefab, position, opts)
    .Named("...")
    .Flags(...);
unit.MoveTo(tile, onArrived, onUnreachable);
unit.Behaviour.Play(...);

Roadmap: spawn, flags, and the four events are an M2 candidate. Movement and behavior access are gated on the unit-behavior research and a spike. Interop rules

  • Never pass a ValueType-derived interop wrapper as a generic argument (a struct with reference fields, e.g. PrefabLookupKey): the interop marshals an object pointer instead of unboxed bytes.
  • Never call generic interop methods over game value types unless the instantiation is known to exist (hard crash otherwise): EntityQuery.GetSingleton<T>, NativeList<T>.Add, NativeHashMap<K,V>.Add, TypeManager.GetTypeIndex<T>, GetSystemTypeIndex<T> over an ISystem struct. Use non-generic APIs and raw layouts.
  • Treat interop results on such calls as unverified until confirmed natively.
  • Harmony cannot patch IL2CPP methods that have by-ref struct parameters. Pointer parameters are fine. Use Il2CppNative.MethodPointerByPrefix plus INativeDetour.
  • Default entity queries skip disabled entities (offline players). Include them explicitly.
  • TypeManager.GetTypeInfo(typeIndex).TypeSize often reads 0 through the interop; take sizes from the interop struct's own layout.
  • Interop structs with bool fields (e.g. User) are not C# unmanaged; use GetComponentData<User>, not Read<T> / Write<T>.
  • Compile against the game's own BepInEx\core\*.dll, not the BepInEx NuGet packages.
  • Do not call native functions with a guessed convention. Observe-only detours and raw reads are safe; direct native calls are last resort.

Hardening

Adversarial reviews of M1 found classes of bugs that are now policy, not one-off patches:

  • Ownership checks on GUIDs. A prefab apply or unapply only mutates clones this process created. A wire NewGuid that disagrees with PrefabGUID.CalculateGuidHash(id) is refused. Spawnable names that already map to a vanilla GUID are refused. Client PrfU / PrfK ignore entries a local plugin owns.
  • Bounded packet parsing. Handshake Count is clamped to [0, MaxMods]; a value outside that range is malformed. Comparison walks the server's Required list and ignores extra answer rows. Guid and version lengths are validated before they hit the wire.
  • Item-key table never shrinks. Unregister leaves the ItemKeyLookup row. Compact-shifting a middle entry remaps every later inventory slot and breaks join-time count+hash. A GUID that was appended and then unregistered is kept as a tombstone and sent to later joiners as a PrfK placeholder.
  • Staging fenced to the game root. Hosted staging writes only under a bundled-server folder that sits strictly inside the Steam install. It refuses the game root itself, the client's BepInEx tree, anything outside that root, and C:\VRisingServer. A real directory is recursive-deleted only if it already carries Core's staging marker.
  • One in-flight bridge op. The debug bridge rejects a second main-thread request while one is running (the 20 s socket wait does not cancel Unity work). Line length and concurrent connections are capped.
  • Reloader cleanup after Unload. After every plugin Unload, including when it throws, Core sweeps EventBus, commands, Harmony id, and owned MainThread work so leftover delegates cannot pin a collectible ALC or run after the assembly is gone.

Prefab registry Shipped

The foundation of everything else in this section. Spike 2 passed; see the gating spikes. A mod defines a new prefab by cloning a vanilla prefab entity and overriding components. Progenitor assigns a stable PrefabGUID derived from the mod ID and a name, registers it on both sides, and pushes the definition to each connecting client so the client registers the same GUID with the same visual base.

Registration, in order, on both sides:

  1. Clone the prefab entity and patch components.
  2. Insert into the prefab collection's three maps and the spawnable-name dictionary.
  3. Add item data to ItemHashLookupMap.
  4. Append to the ItemKeyLookup item key table by raw container access. It is a singleton on an unmanaged system, so the query needs IncludeSystems. Inventory slots travel as an index into this table, not as a GUID.
  5. On the client, insert managed data (icon, name) through il2cpp_runtime_invoke with the unboxed key, because the interop mis-marshals ValueType-derived wrapper keys passed as generic arguments.

On the server, run all of this in a prefix of LoadPersistenceSystemV2.DeserializeLoadFile. Send definitions to a connecting client in a postfix of ServerBootstrapSystem.OnUserConnected so they precede the join-time table validation.

As built. Public surface is PrefabRegistry.DefineItem(id) and ctx.Content.DefineItem(id) (no owner on Register; this plugin is the owner). Hosted games without a dedicated server Unverified live

Most players of a server-side mod never run a dedicated server. They press "Private Game" or "Single Player." When they do, the client starts the bundled VRisingServer.exe as a child process, and that process has no mod loader. The fix is to copy BepInEx into the server folder before each launch and share the plugin folder across. Done naively that has rough edges: NTFS only, a first launch that times out while the server builds its interop cache, and config files that get overwritten on every launch.

Progenitor builds this into Core (installed only in the client process) so there is nothing extra to install, and fixes the rough edges. Server-side plugin code still does not branch on dedicated vs hosted; the child is a server process.

As built. HostedServerLauncher.Install Harmony-prefixes StunProcess.Start (and the PInvoke / MONO variants) for a file name ending in VRisingServer.exe, then Staging.EnsureStaged(serverDir). The prefix is wired and the wait constants are stretched; a live private-game launch — child process loading the same plugins, interop cache generated, join succeeding — is not recorded as verified. Treat the first hosted session as a test; Hosted.DryRun=true logs what would be written without touching disk.

Getting the loader into the bundled server

  • Stage once, verify every launch. On first client start, Progenitor places the loader shim and a doorstop config in the bundled server folder, pointed at a BepInEx_Server state directory beside the client's BepInEx. Later launches only check that the staged files match the client's loader version and re-stage if not. Nothing is rewritten when nothing changed, so a player's server-side config edits survive.
  • Shared plugins, separate state. The server reads plugins from the client's plugin folder, so one install is the truth for both. Its cache, logs, and interop assemblies live in BepInEx_Server. The link is an NTFS junction, which needs no elevated privileges, with a copy-and-watch fallback for filesystems that can't do junctions.
  • No first-launch timeout. The server's interop cache is generated ahead of time, in the background, the first time the client starts with Progenitor installed. A small in-game notice shows progress. Hosting is only offered as ready once the cache exists. As a backstop, the client's connection timeout for the bundled server is extended while a cache build is known to be in progress.
  • Launch hook, not folder polling. The client is patched at the point where it spawns the server process, so staging runs exactly then and can pass the server the paths it needs through environment variables the loader shim reads. A game update that moves the spawn point is caught by the resilience report.
  • Safety fence. Staging writes only under a bundled-server folder that sits strictly inside the Steam game root. It refuses the game root itself, the client's BepInEx tree, anything outside that root, and the live dedicated server at C:\VRisingServer. A leftover real directory is never recursive-deleted unless it already carries Core's staging marker.

As built (staging). There is no sibling BepInEx_Server folder. Staging writes into the bundled server's own BepInEx under the game root. Copies the Doorstop shim (winhttp.dll) and rewrites doorstop_config.ini with absolute client paths. Junctions (else symlink, else copy) core, patchers, unity-libs, plugins, progenitor-reload from the client's BepInEx. config, cache, and interop stay local so the child generates its own interop. Idempotent stamp against the client's BepInEx.Core.dll write time. On first such spawn, stretches ClientBootstrapSystem.TIME_TO_WAIT_FOR_LOCAL_SERVER_STARTUP ×4 and MAX_CONNECT_RETRIES ×2 rather than pre-building the interop cache in the background. Config keys: Hosted.Enabled (default true), Hosted.DryRun (default false).

What a mod author has to do

Nothing. Server-side code targets the server world through the plugin context, and Progenitor resolves which world that is from the process role. A hosted game is the server role in a child process. The same DLL, code path, and config keys apply on a dedicated server. Mod authors never write "if hosted" branches.

What a player has to do

  1. Install the mod through a mod manager. Progenitor comes in as its one dependency.
  2. Start a private game or single player.

That is the whole list. Specifically handled so it stays that short:

  • Config in one place. Design: a hosted server's mod config lives under the client's config folder. As built, config stays local to the child so it can generate its own interop; unifying those folders is still open.
  • Saves stay portable. Mod persistence is keyed to the save it belongs to, wherever that save lives. A hosted world moved to a dedicated server brings its mod data with it.
  • Host is admin. Design: the hosting player is treated as admin for Progenitor commands by default. Not yet a separate hosted policy — ICommandContext.IsAdmin is the game's User admin flag.
  • Friends joining. Someone joining a hosted game gets the same handshake as on a dedicated server: a clear message naming the mod and version they are missing, or a clean connection.
  • Packaging. One Thunderstore package tagged both Client and Server, one manifest dependency. The mod manager handles the rest.

A worked session

The user asks for a boss that summons two adds at half health. The session writes the system, builds the DLL, and calls reload. It calls spawn for the boss near the admin, then set on its health component to 49 percent. It calls query for units with the add's prefab near that position and gets two. It calls logs filtered to errors and gets none. It reports success. The human looks at it once, at the end, if they want to.

Inspector

A local web page served by the MCP process, fed by inspect. Click an entity in a list, see its components update live. Cheap to build once the bridge exists, and it answers the "what does this thing actually have on it" question that eats most modding time.

The gating spikes

Spikes 1 and 2 have passed on the current game build. The spike logs are kept with the maintainers' internal records. The pass conditions below are what was required; the sentences after them are what the runs showed. Spike 3 (server-side castle placement) is not yet run; a fail is a valid result.

Spike 1. Server-to-client transport

Can the server send an arbitrary custom message to one client through the game's netcode? Pass condition: a blittable struct sent from server code arrives in a client handler, on a build with the current game version, without touching chat. Pass. The send returned Sent on every tick with User.Index and the connected-index flag off. A Harmony prefix on the client receive saw a zeroed buffer and stalled the client; a native detour on OnReliableEventsReceived got the real packet, with read position 8 bits on entry. Payload fields arrived intact, matching the server send log line for line.

Spike 2. Prefab with client sync

Can a client be taught about a prefab GUID it did not ship with, cleanly enough that it renders and interacts as a normal item? Pass condition: a cloned item registered under a new GUID on the server and, via a message over the spike 1 transport, on the client: it appears in the inventory with the right icon and name, it can be dropped and picked up, it survives a save and reload, and a client without the mod gets the handshake rejection rather than a crash. Pass. The item appeared with the cloned icon and name, in stacks of the overridden max, and dropped and picked up as a normal item. After a server restart with registration in a prefix of LoadPersistenceSystemV2.DeserializeLoadFile, the offline player's inventory still held the stacks. Unmodded-client rejection is a networking handshake feature and was not tested here.

Outcome

Both passed: Progenitor is the framework described here. Transport is the reliable-events path, not the chat fallback. Prefab sync works, so Content stays the full registry-plus-managers design rather than shrinking to server-side clones of vanilla-visual prefabs.

Spike 3. Server-side placement

Can the server place a building on a plot through the game's own build path so that it lands on the grid, pays the vanilla cost from a given inventory set, obeys territory and room rules, replicates to connected clients, and survives save and reload? Same for dismantle with the vanilla refund. Pass condition on the test server: place a Large Chest at a chosen tile and rotation for a given player; a connected client sees it; it is still there after a restart; the same call is refused where vanilla would refuse (occupied tile, off-territory, wrong floor); dismantle refunds. Candidate seams, in order: inject the build event a client sends, on behalf of the player; call the placement system directly. Both need the native analysis on the build-mode and placement systems and the debug bridge to try them. By-ref struct parameters and generic calls over game value types are the usual killers. Not run. Fail is a valid result: consumers ship survey mode (mark spots, the player places) and drop server-driven build.

Open decisions

  • MCP server language. Decided: Node (tools/mcp/server.mjs). The bridge stays C# in-process.
  • Command compatibility. Decided: attribute-based commands ([Command], [CommandGroup], [Remainder]). Static command classes register via Register(Type).
  • Public from day one, or after M1. M1 is done privately. Still leaning public repo at M2.
  • Where Progenitor lives. Decided: this repo, mods as submodule-free consumers.
  • Exec sandboxing. Decided: not in-process compile inside the game. progenitor_exec builds a throwaway plugin, hot-loads it on one side, and unloads it. Dev DLL stays off public servers.
  • Custom systems as injected SystemBase. Decided against for reloadable plugins. M2 ships named callbacks on SystemHooks; injection is a later Core-only spike if a real SystemState is required.
