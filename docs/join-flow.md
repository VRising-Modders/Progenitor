When a player joins a Progenitor server, they see the server's message first, then a mods page, and can move between the two. These screens replace the read-only refusal panel ("Can't join …", `ModManifestDenyPanel`), which stays as their fallback when they cannot be drawn. The data reaches the client inside the signed mod catalog ([mod-manifest.md](mod-manifest.md#the-join-section-joinflow1)).

**Before the join (AUTOUPDATE1).** When an installed mod has an update the server accepts, a join is held for one prompt (**Update first** / **Join anyway** / **Cancel**) before `GameHelper.LaunchGame` runs; the server's requirements are remembered from its last handshake. Built and game-free tested: [auto-update.md](auto-update.md#pre-join-prompt). With Automatic mode (AUTOUPDATE2) an update already applied at the title screen is not offered, nor a version that failed to load.

## The screens

All three are drawn in the game's popup look: the dialog chrome (opaque frame, dim backdrop), the steel popup buttons and the game serif. Every text an admin or a catalog supplies (the message, mod names, reasons) is drawn in cells whose text the runtime escapes, so it cannot carry markup; the dialog title and subtitle (which name the server) are escaped with `UiRichText.Literal`. **Escape** is Back where a page has one, else Close.

The first screen of a join whose server has a message.

- **Continue:** when every required mod already matches, it finishes the join (in the world it just closes; inside an install window the join continues by itself). Otherwise it opens the mods page.
- **View mods:** the mods page, whatever its decision. Not drawn when Continue leads to the mods page anyway. Source-checked and game-free tested (`JoinFlowTests`, `JoinFlowStage2ClientTests`); not live-verified. The same is on Progenitor's page: under **Server settings**, section **When players join**, the row **This server's mods** with the button **View mods** (enabled while joined and a catalog arrived this join).
- **Leave** (only before the world; removed in the world and in previews 2026-10-06): in the world, the game's own leave (the production `ExitGame` view, the path the bridge's `disconnect` uses). On the refusal screen the client is already disconnected, so the screens only close; the game's Back button returns to the menu.
- **Don't show again until it changes:** recorded in this client's seen state for the server ([below](#when-each-page-shows)); the message then stays away, resets included, until the admins edit it.
- **Reopening it:** in the modes that skip the message, the player can open it again from the mods page (**← Server message**, whenever the server has one) and, at any time in the game, from **Progenitor's** page in the Mods menu: under **Server settings**, section **When players join**, its first row **Server message**, button **Show** (for every player; grayed until a message arrived this join, and again after leaving the server).

#### Links in the message

Status (JOINLINKS1): source-checked, built (Debug and Release) and game-free tested (`JoinMessageLinksTests`, `JoinFlowPanelTests`).

**Live (2026-10-04, Steam client 3840x1080 joined to the isolated test server, Core 2026.10.60.1 from branch commit d0062d5c).** The test message was `Discord: discord.gg/nightgarden (rules at https://example.com/rules). Also www.example.org/guide. Not links: v1.2.3, file.dll, 12:30, <color=red>red</color> <link="x">x</link>.` Results:
- **Links found:** exactly three. The rules URL lost its closing `)`, and both scheme-less forms were given `https://`.
- **Decoys:** none of the decoys became links. The typed tags were drawn as literal text.
- **Look:** links drew pale blue and underlined.
- **Real mouse click:** a click on `discord.gg/nightgarden` opened the dialog for link 0, so the TMP hit test works. **Cancel**, also clicked with the mouse, closed it with nothing opened.
- **Bridge:** `link_click 1` showed `https://example.com/rules` in full, and **Copy link** worked. **Open in browser** in dry-run mode recorded that URL and closed the dialog.

Not live-verified: **Open in browser** without dry-run (it would launch a browser), Escape on the dialog, and links in the long-message reader block.

**What becomes a link** (`UiLinks.Find`): `http://` or `https://` followed by non-space characters; a `www.` host; a bare `host.tld/path` whose host has a dot and an alphabetic TLD of 2–24 letters, followed by `/` (`discord.gg/nightgarden`). Version numbers (`1.2.3`), times (`12:30`), file names (`file.dll`) and a bare `example.com` are not. Trailing `.,;:!?` and an unbalanced closing `)` or `]` are left out of the link. A candidate longer than 2048 characters, or holding a control or bidi character (U+200E/F, U+202A–202E, U+2066–2069), stays plain text. Only `http` and `https` ever open; a link without a scheme opens as `https://…`.

**Drawing.** The link is drawn exactly as the admins wrote it, pale blue and underlined; the rest of the message keeps the same escaping as before, so `<color>`, `<link>`, `<sprite>` and every other tag an admin types still shows literally. The live countdown keeps its links (they are found again on every redraw).

**Clicking a link** replaces the message page with **Open this link?** in the same popup:

| Part | What it shows |
|---|---|
| Body | `<server name>'s admins wrote this link. It opens in your web browser.` |
| URL | The full normalized URL that will open, on its own lines, pale blue, wrapping, never cut |
| Status | `Copied.` after **Copy link** |
| Buttons | **Cancel**, **Copy link** (copies the normalized URL; the dialog stays), **Open in browser** (`Application.OpenURL` with that URL, then back to the message page) |

**Escape** and **Cancel** return to the message page. The dialog shows the URL that opens, not the link's words, so a link cannot pretend to go somewhere else. Admins see one more sentence in the **Message** setting's help: `Links (https://…) become clickable for players.` The message travels as plain text, so servers need no change. Bridge: `join_ui link_click`, `link_button`, `link_dry_run` ([dev loop](bridge-ops-join.md#join_ui)).

**Versions in the world are current.** A row's status is `Handshake.Compare`'s verdict with the server's version rule (`Exact`, `Minor`, `None`), so a row never needs attention for something the handshake accepts. In the world the required versions come from the signed section's `versions` (what the server's handshake requires now; an overlay's catalog version pin does not change them) and this client's from its loaded plugins, so a hot swap on either side is reflected the next time the page is built; a refusal and an install window use the join's own tables.

**Version matching (mod compatibility C3, 2026-10-10; game-free tested, not live-verified).** When the join's catalog carries the server's Version matching (the extended form a C3 client gets, also on a refusal's narrowed catalog), the verdict is the server's own judgment, not the request row's attribute rule: `Handshake.Compare` runs with `VersionMatching.ClientContextFor`, which rebuilds the server's judge from the catalog's `matching`, each row's `match` (an admin's per-mod rule) and `peers`, and this client's own effective ranges. So a newer copy the client's declared range accepts (or an older one inside the server's range) is ready, not `you're ahead` with **Tell the admin**; under Exact version for all, Same minor for all or a per-mod rule the same pair still needs attention. Without such a catalog (an older server) the request rows' rules decide, as before. See [mod-compatibility.md, C3 as built](mod-compatibility.md#c3-as-built).

#### A refusal for Progenitor Core

A server can refuse a client for its Progenitor rather than for any mod. Two cases:

- **Out of date.** The server needs a capability that only a newer Progenitor has, such as an item synchronization feature its content uses. The fix is updating Progenitor on the client.
- **Server setup.** The server adds more custom items per join than normal clients accept, because its admins raised `Networking.MaxSyncedPrefabsPerJoin`. No player should edit a config file to join, so this is for the admins to fix.

No mod row fails in either case, so before 2026-10-13 the screens read `All ready` over a green list and the player was then kicked with no reason on screen. Two later wordings named the missing feature or the setting, which players could not act on. The screens now use the approved wording (2026-10-13), and the technical detail goes only to the log and the readback.

| Part | Out of date | Server setup |
|---|---|---|
| Headline (message page summary and above the mods page's red band, orange) | `Your Progenitor is out of date` | `This server's setup isn't compatible with your game` |
| Body | `This server needs Progenitor 2026.10.195. You have 2026.10.191. Update Progenitor, then join again.` From an older server that does not name its version: `This server needs a newer Progenitor. You have 2026.10.191. …` | `Its admins need to fix a Progenitor setting before you can join. Let them know.` |
| Button | **Update Progenitor** (below), when the self-update can fix it | none |
| Log and readback only | `JoinFlow: refused for Progenitor itself: missing catalog-v2 equipment-stat synchronization; server Progenitor 2026.10.195, this client 2026.10.191` | `… item limit 1024 (Networking.MaxSyncedPrefabsPerJoin) …` |

Never `All ready.` Each mod row keeps its own readiness and the band still reads `2 of 2 ready`. The join is not ready (`NeedAttention` counts the refusal), so the mods page is due, its **Close** never turns into **Continue**, and no **Join now** is offered.

**Update Progenitor.** It starts Progenitor's own self-update, the same one as the Install tab's **Update** (`SelfUpdates.Begin`, by click): the offered release is downloaded and checked now and put in place at the title screen (the apply window). The button is offered only when all of these hold:

- the refusal is the out-of-date kind;
- the self-update offers a release a click may install here (`Clickable`, not held for a server, no update running);
- that release is newer than this client's Progenitor and at least the server's version, when the refusal named it.

It is the main button on both pages: on the message page after **Continue**, which steps back to a secondary button; on the mods page after **Close**. A press shows `Downloading Progenitor 2026.10.196. It's installed when you're back at the title screen. Then join again.` and the button goes for the rest of the join. When the update cannot start, the answer says why (`Progenitor couldn't be updated here (…). Update it from the Mods menu, then join again.`) and the button stays. A development build, a mod-manager install, a hand install with changed files, or no newer release on the index offers no button; the body's own sentence still says what to do. Log: `JoinFlow: Update Progenitor <version>: started|refused (<reason>)`. A release that changes Bootstrap still needs a restart, as from the Install tab.

**Where the server's version comes from.** The server sends its feature table, which carries its Progenitor version, only after an accepted join, so on a refusal the kick reason is the client's only record. The server writes its version into each problem (`Handshake.Compare.CoreCapabilityProblem`, `ItemBudgetProblem`):

- `Needs Progenitor 2026.10.195 or newer (catalog-v2 equipment-stat synchronization). Update Progenitor Core on the client.`
- `Needs Progenitor set to accept 1024 custom items (this server runs 2026.10.195). Set Networking.MaxSyncedPrefabsPerJoin to 1024 on a current Progenitor client.`

The client reads them with `JoinCoreRefusal.Parse` and fills in its own version. Older servers' wordings (`This server requires … Update Progenitor Core on the client.`, `This server uses an extended item budget. …`) are still read, without the server's version. New server checks of this kind must use those helpers. A problem cut short by the kick reason's length limit is not claimed.

Rows the signed join data names with a Thunderstore `package` (`Owner-Name`) and a version install from Thunderstore: required rows with **Install**, **Update** or **Use version X**, and checked recommended rows. A row's action button or **Install N mods** starts them.

**The exact version.** When the screens open, the client reads the version list of every package the join names, from the same Thunderstore index the Install tab reads (`https://thunderstore.io/c/v-rising/api/v1/package/`, reused for 10 minutes, then checked with a conditional, compressed request that costs a 304 while the index is unchanged ([Thunderstore traffic](mods-menu.md#thunderstore-traffic-tstraffic1)); when the fetch fails, the Install tab's cached `BepInEx/progenitor-cache/index.json`), with the configured local index (`[Install] LocalIndexPath`) in front of it. The version is chosen under the mod's version rule, as the handshake judges it: **Exact** takes only the version the server requires (the same string, or the same numbers part by part: `1.2` is `1.2.0`, a BepInEx `1.2.0.0` is Thunderstore's `1.2.0`; `1.2.0.4` is not `1.2.0`); **Minor** takes that version when it is listed, else the newest listed with the same `major.minor`, and the row's readback `install.reason` says which (`installed 1.2.7 (the server accepts any 1.2.x; 1.2.6 is not listed)`); **None** takes that version when listed, else the newest. A version the rule does not accept is never installed in its place; an inactive (removed) version counts as gone. While the lists are not read, the rows keep the stage 1 actions; once read, a gone version turns the row into Ask the admin with the plain sentence above.

**One install, the Install tab's.** Each row runs the Install tab's machinery, not a second downloader: a catalog service built for the batch like the Install tab's (the client root, the same admission pipeline), the version's entry put in place of the newest, `DownloadAndInspectAsync` (the `[Install] MaxDownloadMB` cap, 128 MB by default, refused before any request when the listing is larger; mod-manager apps refused), `PlanWithDependenciesAsync` for the client (its dependencies from the same index) and `ExecuteWithDependencies` on the game's main thread. The trusted hotLoadable admission decides where it lands: a package that declares `hotLoadable: true`, passes inspection and is one clean `ProgenitorPlugin` is written to `progenitor-reload/` and loads now (the row reads **Loaded** once the reloader reports the plugin, within 10 s); anything else is written to `progenitor-pending/` and loads at the next start (**After restart**). Either way the write is ledgered in `progenitor-install.json` as the Install tab's is.

**Refusals**, shown on the row: `Refused` where the button was and `Refused: <reason>` leading its line; a refused recommended row loses its switch. A refusal is a rule, so the row is not counted by **Install N mods** and not offered again until the next join attempt (another server or a changed list). A failure (a download that broke, a write that failed) keeps its button and counts again (`Failed: <reason>`).

| Rule | Row says |
|---|---|
| `[Mods] UseThunderstore` off | `Thunderstore is turned off in Mods > Configuration.` |
| Exact version gone / package not listed | `Owner-Name 1.1.0 is no longer on Thunderstore (it has 1.3.0).` / `Owner-Name is not on Thunderstore's V Rising list.` |
| `NotThunderstore`: a fetched listing whose download is not an `https` URL on `thunderstore.io` or one of its hosts (the local test index is allowed) | `Its download is not on Thunderstore, so it is not installed from here.` |
| NSFW (the author's `has_nsfw_content`) while `[Mods] ShowNsfwContent` is off | `Its author flagged it NSFW. Turn on Show NSFW content in Mods > Configuration to install it.` |
| Mod-manager app (`NonModPackages`) / over the size cap | the Install tab's sentence (`Mod manager app, not a game mod` / `the download exceeded the size ceiling (…)`) |
| `SideMismatch`: the package declares (or its `[BepInProcess]` loads in) the server only | `It is a server-only mod; it does not install on your game.` |
| The package's plugin is not the mod the server named, or (for a required row) its plugin cannot be read | `Owner-Name holds <plugin id>, not <named id> that the server named.` / `Owner-Name does not show which plugin it holds, so it cannot stand in for <named id>.` |
| Update or Use version over a copy another tool installed (MANAGED1 "Managed elsewhere") | `Installed by <tool>; update it there.` (`another tool` when unknown) |
| Inspection or plan refused | the Install tab's reason |
| A fetched zip whose size is not the listing's | `Failed: size mismatch: …` |

**The batch.** One press is one batch: every row at once, at most two downloading and installing at a time. Every row's exact version is put in place before any row runs, so a dependency that is also a row resolves to the server's version; plans and writes go one at a time, and a row whose package an earlier row already wrote as a dependency downloads it again and ends as the catalog's `already present`. A failure on one row never stops the others. Each row shows its state where its button was: `Queued`, `Checking…`, `Downloading 62%` (`Downloading…` when the size is unknown), `Installing…`, then `Loaded` (green), `After restart` (pale blue), or `Refused`. Once it ended, the row's tag follows what the install did (`applies now` when it loaded, `needs restart` when it waits for the next start), not the catalog's prediction. The batch belongs to the join, not to the screens: closing the screens does not stop it, and when it ends with the screens closed (and no client world: the disconnect screen or the menu), its result reopens on its own. A new join attempt forgets a finished batch, so pressing Install again after a failed rejoin repeats it (an install over the same bytes is the catalog's idempotent `already pending`). A Core hot swap stops rows that have not started writing.

**Use version X.** When this client is ahead of the server and Thunderstore still serves the server's exact version, the row offers **Use version 1.2.0**. Stage 4: the newer copy is **kept** (parked in the version store, [section 9](#9-keeping-both-versions-stage-4)) right before the server's version is planned, never replaced: when the reloader can unload it now it leaves `progenitor-reload` at once and the install waits (up to 5 s) for the plugin to unload, so the plan sees a fresh install the hot route may load this session (tag `applies now` when the catalog says the mod hot-loads); otherwise it stays loaded with a `.uninstall` marker and the server's version takes the restart route. The row's line reads `Use server's 1.2.0 · your 1.3.0 is kept for other servers`, and the confirmation says `<name>: 1.2.0 for this server; your 1.3.0 is kept for other servers.` A copy that cannot be kept (another tool's, loaded from `BepInEx/plugins`) keeps the stage 2 sentence with the reason (`<name>: your newer 1.3.0 is replaced by 1.2.0. <reason>`) and a warning tone; a keep that fails at install time refuses the row (`Can't install: your 1.3.0 could not be kept for other servers (…), so it was not replaced.`). Without the version on Thunderstore the row stays **Tell the admin**.

| Intro | `Install N mods from Thunderstore that <server> lists?` |

| Key changed | Only when this address's catalog is signed by another key than the one pinned: a plain line (normal tone, no band), `This server's key changed since <date the old key was first seen>; it was <old fingerprint>.` (2026-10-05; source-checked and game-free tested, not live-verified) |
| Warning | the Use version sentence ([above](#4-installing-from-thunderstore-stage-2)): kept for other servers, or replaced with the reason |
| Buttons | **Back** (and Escape): nothing is installed, `Nothing was installed.`; **Install**: the batch starts — unless a catalog for another address or key landed while the prompt was open, which shows it again with the current facts and `The server's offer changed while this was open. Check it again before you download.` |

The red risk band (`Mods run with the same access as the game. …`) was removed 2026-10-05 on request: the title already says the mods come from Thunderstore. The page lays out from its rows, so nothing is reserved where it was: the facts are followed by the key-change line or the warning when there is one, then the buttons. The `join_ui` readback's `tsTrust.risk` field is gone and `tsTrust.keyChanged` carries the key-change line (empty when the key is the pinned one).

**Where it is recorded.** In `progenitor-trusted-operators.json`: a top-level `thunderstoreAcks` list, one row per host and key (`host`, `spki`, `fp`, `at`, `packages` as `Owner-Name@version`). It needs no pin. Since 2026-10-05 this confirmation is the only install decision a server's catalog leads to: the operator pin is automatic ([trust on first use](mod-manifest.md#trust-on-first-use-2026-10-05)) and installs nothing. A batch whose packages this host and key all confirmed before (a retry, or the rest after a restart) starts without asking; a new package, another version, another key or another address asks again. At most 64 packages per row and 200 rows (the oldest dropped). A file without the list is byte-identical to an older Core's; an older Core rewriting the file drops it, and the next batch asks again. `join_ui forget_trust` clears it (the operator's pin stays).

### 6. After installing: Join now, or Restart and rejoin (stage 2)

When a batch ends, `JoinAfterInstallPolicy` decides:

| Outcome | Shown |
|---|---|
| A required row needing attention is not satisfied (failed, refused, or nothing here can fix it) | the mods page, with the batch line (`Loaded 1 mod. 1 mod loads after a restart. Not installed: Maps (…).`) |
| Every required row satisfied, all loaded now | on a refused join, **Ready to join**: `Everything this server needs is installed and loaded. Join it now; no restart needed.` · **Later** / **Join now**. Still in the world: finished in place (below); inside an install window: `Installed and loaded; the join continues by itself.` |
| Any required row or checked recommended row loads only at the next start | **Restart needed**: `Some mods load only when V Rising starts. Restart now and we'll reconnect you to this server.` · **Later** / **Restart and rejoin** |

**Finished in place (INPLACE1, 2026-10-07; source-checked, built and game-free tested in `JoinFlowStage2ClientTests`, not live-verified).** Standing rule (user, 2026-10-07): a player who can fix the problem where they are is never sent to the join screen, a rejoin or a restart. When the fix completes while this client is still in the server's world (the world is up and the handshake answered ok; the server only warned or paused, and the screens were opened as a refusal's), nothing reconnects. This covers a batch that loaded everything, **Turn on** (once the mod is declared), **Use kept X** on the now route (once the kept copy is declared) and **Pause for this server**. The client answers the handshake again on the same connection (`Handshake.ReDeclareSelf`; the mod report follows the answer when the server asks for one), so the server's re-check sees the fix. When no answer can go out, the report alone is sent. The Result page reads **Installed** with `Sent to <server>: <names> is installed now. You stay where you are; no rejoin or restart needed.` (`… is turned on now.`, `… is in use now.`, `… is paused for this server now.`) and one **Done** button that closes the screens. If nothing reached the server, the body says so: `… installed and loaded, but <server> could not be told on this connection, so its warning may stay until it checks your mods again. You stay where you are.` Only a real refusal, kick or disconnect (no client world, or a handshake that did not answer ok) offers **Join now**, which reconnects by the loopback rule of [section 8](#8-rejoining-server-stage-2). An install window keeps its own re-answer. Log: `JoinFlow: finished in place after <what> on <server>; re-answered=true; no rejoin`. The batch line names its source: `JoinFlow: Thunderstore batch done: …`, `JoinFlow: local test source batch done: …` or `JoinFlow: Thunderstore and local test source batch done: …`, with ` (finished in place)` when it did. Readback: `join_ui read` → `result.finishMode` (`in-place`, `rejoin` for Join now, `restart`, `none`) and `result.inPlaceSent` (only for in-place). **The answer goes only when it passes** (review 2026-10-07). The server judges a re-answer from a player it already accepted like a first answer, and kicks on a mismatch. So before answering again the client runs that same check on the reply it would send now (`Handshake.PreflightReAnswer`: its live declared mods packed as the reply, judged against the rows the server asked). The batch's own Join-now decision also reads the live declared mods, not the snapshot from when the catalog arrived. Only a passing check answers again. Otherwise nothing is answered: only the mod report goes (the server re-judges the client mod policy from it), and the page says what still mismatches instead of "you stay": `<names> is installed and loaded, but <server> would still refuse this client's mods: <reason>; <reason>. It was not answered again, since a failing answer would disconnect you. Fix the rest from the join window or Install Mods.` (at most three reasons, then `and N more`). When the request is not known in full (none recorded, or it filled every slot) it reads `… this client can't confirm its mods now match what <server> checks, so it did not answer <server> again (a failing answer would disconnect you). <Server> sees the change when you next join.` Log `JoinFlow: fixed in place after <what> on <server>, but did not answer again: …`. Readback `result.inPlaceProblems`. This covers every in-place path, including Use kept, which used to answer without checking the other required mods. If the player closed the join screens before the fix finished, the same sentence appears as a notice in the world (the mod pause notice's popup, title `Installed`; log `JoinFlow: the join screens were closed; the in-place result is a notice: …`), so the outcome is never only in the log.

**Join now** reconnects to the same server at once, no restart: from the world it uses the game's own Leave (the `ExitGame` view, as the bridge's `disconnect`); from the disconnect screen it returns to the title view (`ViewLocation.MainMenu`); then, when no client world is left and the title view is on show, it connects to the same address, port and transport the join used (Bootstrap's connect record: `LastConnectAddress`, `LastConnectPort`, `LastConnectProtocol`; or, when that is empty now, the one captured at this join's attempt; never the catalog's host — live 2026-10-05 a fresh process with an empty record dialed the server's public address over `SteamIPv4` instead of the LAN address the player used. With no address this process dialed, Join now is not offered and the page says `Join the server again from the server list.`; the after-restart rejoin keeps its record's stored address) the way the bridge's `connect` does (`ConnectAddress.CreateSteamIPv4` / `CreateLidgrenIPv4`, `GameHelper.LaunchGame`). The page **Joining <server>** shows one status line, `Connecting to <address>… 40%` (`Leaving for the main menu… 5%` first; no body line repeats it, live 2026-10-05), and **Cancel**. Joined (world up, handshake ok): the page closes by itself unless a required mod still needs attention (`JoinShowPolicy.JoinedPageNeeded`; log `JoinFlow: Joined <server>. Nothing to decide; the Joining page closes`), and the in-world screens then decide as for any join; with something to fix it shows `Joined <server>.` with the summary and **Continue** (reported 2026-10-06: a `Joined … Required (0 of 0 ready)` page with only Continue was shown for nothing; game-free tested, not live-verified). This holds for every path that opens it: the Server tab's Last server **Join**, Join now, the after-restart rejoin pickup and a resumed private game (**Resuming <save>**, which always closes once joined). Refused: the refusal's own screens take over (with the summary line). The game's own connect failure ends it at once with the game's reason (`ClientBootstrapSystem.ClientState` is `Error`, reason `DisconnectChangeReason` in words: `Could not reconnect: Connection timed out. Join the server again from the server list.`; a kick waits 3 s for the refusal's own screens; live 2026-10-05 the page waited its full 120 s while the loading screen read `Error: Connection timed out`). Nothing in 30 s on the way to the menu, or 120 s connecting: `Could not reconnect: … Join the server again from the server list.` Only `SteamIPv4` and `Lidgren` joins can be reconnected (a Steam P2P or EOS join is not).

**Later** closes the screens; what was installed stays (pending files load at the next start).

**A private game this client hosts** (Bootstrap's `IsHostingPrivateGame`) gets no rejoin: `Some mods load only when V Rising starts. Restart V Rising, then start your private game again.` with **Close**. A join with no address to reconnect to reads `… Restart V Rising, then join this server again.`

### The last server (SERVEREMPTY1)

**Source-checked, built (Debug and Release) and game-free tested (`ServerTabEmptyStateTests`, `ThreeHomesMenuTests`); not live-verified.** The Server tab's **Last server** row ([mods-menu.md](mods-menu.md#the-server-tab)) needs the last server this client joined. None of the existing records fit: the rejoin record lives at most 10 minutes and is deleted once used, Bootstrap's connect record is per process, and the server profiles carry no transport. So Core writes a small plain record, `BepInEx/config/progenitor-last-server.json` (written atomically): `address`, `port`, `protocol` (`SteamIPv4` or `Lidgren`), `serverName` (may be empty), `needsPassword` (a hint, never the decision: true after a join with a password or a password refusal, false after a join without one; never the password), `joined` (ISO UTC) and `schema` 1. The type has no password field and the reader ignores one in the file; a record with no address, port or known transport reads as none.

- **When.** Checked once a second (every 10 s once written) from the join screens' frame tick: in a client world whose handshake answered ok, or after a server without Progenitor was detected (`ServerModPause`). The address is the one this process dialed (as Join now's), the name the join screens' (`JoinText.ServerLabel`). A private game this client hosts, and a Steam P2P or EOS join, are never written; neither is a join the game names as another `address:port` than the dialed one (Bootstrap's dialed address is never cleared, so a join that did not pass through `LaunchGame` would read as the previous server; log `JoinFlow: last server not written: …`). Rewritten only when the server, its name or its password use changed. Log: `JoinFlow: last server <name> (<address>, <protocol>[, password])`.
- **Join.** `JoinFlowClient.JoinLastServer`: refused while this client hosts a private game or a join is in progress; otherwise the reconnect of [section 6](#6-after-installing-join-now-or-restart-and-rejoin-stage-2) with the record's address, port and transport (the **Joining <server>** page; `JoinFlow: Server tab Join: <name> (<address>)`). **Password (JOINPW1; source-checked, built and game-free tested in `ServerTabEmptyStateTests`, not live-verified).** Join always connects without a password first, whatever `needsPassword` says (live 2026-10-06: a record kept `needsPassword true` from an earlier join and Join opened the game's prompt for a server that no longer had a password). Only when the game's connect fails with `ClientBootstrapSystem.DisconnectChangeReason` `IncorrectPassword` (read as `TryConnectFailure` already reads the reason, after the connect was seen under way) does the reconnect note the refusal (the Joining page reads `The server asked for a password. Opening the game's password prompt.`; log `JoinFlow: reconnect: <address> refused the join without a password; opening the game's password prompt`), set the record's `needsPassword` true (only a record naming that address, port and transport), go back to the title view (the game's Leave, or the title view from the disconnect screen) and open the game's own password prompt there: `GameHelper.LaunchPasswordProtectedGame` (the same by-value `il2cpp_runtime_invoke` call shape as `LaunchGame`; it opens `Join_PasswordView`). The Joining page closes so the prompt shows (`reconnect prompted`) and the game connects when the player confirms; a mod that fills that prompt (RetainedPassword) works as it does from the server list. A prompt the player cancels just ends there: nothing reconnects. Any other failure ends with its reason as before, and the prompt opens at most once per Join. A successful join rewrites `needsPassword` from that join (`LastConnectionData.Password` set or not), so a server that dropped its password reads false after the next join. The `reconnect` readback adds `promptOnPasswordRefusal` and `passwordRefused`. Join now from the join screens follows the same rule since F32 (below).

### 7. Restart and rejoin (stage 2)

1. **The record.** `BepInEx/config/progenitor-rejoin.json` (written atomically): `address`, `port`, `protocol`, `serverName`, `fingerprint`, `needsPassword` (whether the join used a password, read as `ClientBootstrapSystem.LastConnectionData.Password` not being empty — never the password), `created` (ISO UTC), `used`, `dryRun`, `schema` 1, and `rows` (each installed row and each required row: `id`, `name`, `package`, `version`, `required`, `result`: a batch row's phase, else `ready`, `missing`, `server-must-update`, or for a copy you turned off `turned-on` (switched on for the next start; `version` is that copy's) or `turned-off` (still off); a recommended mod turned on for the next start is a row with `required false`, `result turned-on`). The type has no password field and the reader ignores one in the file.
2. **The relauncher** (when Steam runs and handles `steam://`, and Windows PowerShell is present): the inbox `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, run in two steps so the waiting helper does not belong to the game. A short-lived hidden broker (`Process.Start` without the shell, no window, no profile, non-interactive, an inline `-Command` on its command line, which Windows passes as Unicode, so an install path such as `D:\Игры\...` arrives intact) asks Windows to create the helper through `Win32_Process.Create` with a hidden window, prints the helper's process id and exits. The game waits for that answer on a background thread, so no frame blocks, and acts on it at the next frame. When no answer comes within 15 s it kills the broker and its process tree, logs that, and takes the manual path (item 4). A helper the broker created just before it was killed still waits for Steam to report the game idle and for no game process to run, so it never starts a second copy beside a manual start. The helper (an inline `-Command`: no new executable, no script file, no encoded command) waits for **this** process (its id and its start time, so a reused id is never waited on) for up to 180 s, and gives up without starting anything if the game is still running; waits 8 s; then waits up to another 180 s for Steam's own `Running` flag for the game (`HKCU\Software\Valve\Steam\Apps\1604030`) to read an explicit 0. A flag it cannot read never counts as idle, and when the wait runs out it exits without asking Steam. It starts nothing when a process with this game's executable path is already running; asks Steam once through `steam://run/1604030` (as `tools/launch-client.ps1` does); and asks a second time only when no process with that path appeared within 90 s and Steam is not already launching it, so two copies never start. Each step is written to `BepInEx/progenitor-restart.log` (in BepInEx's own folder), including how the helper ended: the game still running (exit 2), the game already running (exit 3), the Steam wait running out (exit 4), the game appearing, and whether it asked Steam a second time or held back because Steam still reported the game launching. The game adds a line when the broker fails or is killed. The helper trims the log when it starts, so it keeps at most the last 200 lines. Every string in the command is single-quoted with every character PowerShell reads as a single quote (`'`, U+2018, U+2019, U+201A, U+201B) doubled, and neither command contains a double quote (the broker builds the helper's quoted command line with `[char]34`), so odd install paths (spaces, `&`, `'`, parentheses) cannot break out of it. The independent helper and the explicit Steam wait were verified live on 2026-10-15 on the build before this port (Steam cleared the old session, accepted one launch, and the new client reached the title screen); the port to current main, the background broker wait, the broker kill on timeout and the Unicode-safe command line are built and game-free tested only (`RelaunchSteamWaitTests` runs the generated helper and broker in Windows PowerShell with stubbed process creation, including a non-ASCII path), and the full install-and-rejoin sequence was not repeated.
3. **The quit.** `Application.Quit` on the main thread as soon as the broker answers (Unity quits at the end of that frame; frames keep running while it is asked), the path that runs the game's quit handlers; Bootstrap promotes the staged files from `progenitor-pending/` at the next start. A second press while quitting answers `already restarting` (one relauncher per process).
4. **Manual.** When Steam is not running, has no `steam://` handler, PowerShell is missing, or the relauncher does not start: the Result page already says `V Rising will close. Start it again and Progenitor will reconnect you.` (or it is added when the start fails), and the game quits after 6 s. The record makes a manual start reconnect too.
5. **Shared with the Mods window (INSTALLRESTART1).** The Install and Mods tabs' pending-restart bar uses the same relauncher, the same rejoin record and the same after-relaunch pickup, and adds two things: a record with `kind hosted` and `save` (resumed through the title screen's Continue on a **Resuming <save>** page), and `progenitor-install-restart.json` for the after-restart line (`Installed: ChatSkin. Rejoined <server>.`). It leaves the world the game's own way before it quits. [mods-menu.md](mods-menu.md#restart-for-pending-installs-installrestart1).

### 8. Rejoining `<server>` (stage 2)

On the next start, once the title view is on show (no client world, `ViewLocation.MainMenu`, the `MainMenuNewView` active), Core reads the record once per Core generation:

| Record | What happens |
|---|---|
| None | nothing |
| Fresh (written at most 10 minutes ago, not more than a minute in the future) and unused | marked `used` on disk first (a crash during the rejoin never loops), then **Rejoining <server>**: the body `V Rising restarted to finish installing.` and one status line `Connecting to <address>… 30%`, the summary from the record (`Required (2 of 3 ready)`: each row `Ready`, `Still missing`, `Server must update`, or `Still turned off` for a turned-on or turned-off copy that this start does not run at its version; `Recommended (1 added)`), and **Cancel** |
| Older than 10 minutes, already used, malformed, or not a transport the rejoin can use | deleted and ignored |
| A dry run's (`dryRun true`) | left for `join_ui rejoin_now`; a start does not use it |

It connects as Join now does; once it ended the page's body is the outcome (`Joined <server>.`, the failure, `Canceled.`), not `Connecting…`. After the join answers the record is deleted: joined with nothing to fix, the page closes by itself (2026-10-06, as in [section 6](#6-after-installing-join-now-or-restart-and-rejoin-stage-2)); joined with a required mod still needing attention, `Joined <server>.` with the summary rebuilt from the join screens' data (the page model of this join) and **Continue** (the in-world screens wait until it closes); refused, the refusal's screens with the line `After the restart: 1 of 2 required mods ready.`; anything else, the failure sentence. **Cancel** before the connect stops it; after it, the client leaves the world the connect reaches.

**A password server** (`needsPassword`; INSTALLRESTART1, 2026-10-06) is dialed through the game's own password prompt, as the Server tab's Last server Join does (`GameHelper.LaunchPasswordProtectedGame`, `JoinFlow: reconnect prompted`); the player or a mod such as RetainedPassword fills it, and the record is deleted. Progenitor never stores the password. (Before 2026-10-06 the page stopped with `This server needs its password, which Progenitor never saves. …`.)

**Rejoin a server that restarts for Progenitor (F22, live 2026-10-07; built and game-free tested in `JoinFlowStage2ClientTests`, not live-verified).** After a server restart for a mod install, the client only got the game's "Communication with server was lost". When the connected server accepts Progenitor's stop (**Stop server to apply**), the connection's end within ten minutes now opens the Result page titled `<server> is restarting`, body `Progenitor rejoins it when it's back (up to 5 minutes).` and the note `Why: Stop server to apply.`, with **Rejoin when it's back** (F31, live 2026-10-08: it used to keep the Ready to join title and body; built and game-free tested, not live-verified). Pressed, it reconnects with the loopback rule; a connect that fails while the server is down shows `Waiting for <server> to come back (attempt N); trying again in a few seconds.` and tries again 10 s later, for up to 5 minutes; **Cancel** stops it. Review 2026-10-07:

- Only a connect that no server answered (a timeout, no connection) is tried again; a refusal ends the wait.
- Any reconnect to another server ends the wait as well.
- The offer is taken back when the stop does not happen (refused, no answer, still running), and is made only when the ended connection is the stopped server's.
- A result page's own server (this one, or a failed rejoin's) belongs to that page: once it closes, Join now dials the join's own server. A restart the admins start without Progenitor is not detected: pending-restart rows alone cannot tell a lost connection from the player's own Leave.

**A password used last time is a hint (F19, live 2026-10-07; built and game-free tested, not live-verified).** The after-restart rejoin of a server joined with a password used to open the game's password prompt at once. A password manager's autofill marks password-free servers too: the prompt opened for a server with no password, was closed, and the player sat at the title screen with nothing said. The rejoin now connects without a password first and opens the game's prompt only when the server refuses for its password, as the Server tab's Last server Join does (JOINPW1). The log reads `…; a password was used last time: the game's prompt opens only if the server asks for one`. If the prompt opens and no join follows within 60 s (the prompt closed, or nothing connected), the Result page reads `Couldn't rejoin <server>: the game's password prompt closed without joining.` with **Join again**, which dials that server again with the loopback rule.

**A restart the player started names itself and rejoins without asking (F37, live 2026-10-08; built and game-free tested in `JoinFlowStage2ClientTests`, not live-verified).** After **Save, stop and start again** on the Install tab (the local dedicated server Progenitor starts again), the restarting page said `Why: Stop server to apply.` and waited for **Rejoin when it's back**. The stop request now carries whether Progenitor starts the server again (`ServerStopRequest.RestartsAgain`, passed to `ServerStopRequest.Accepted`). For that restart the reason is `Why: Save, stop and start again.`, and when the connection ends the rejoin starts by itself: the Rejoin page opens with that reason as its body, retries while the server is down exactly as the pressed button would, and **Cancel** ends the wait. A plain **Stop server to apply** still shows the Result page and asks.

**Every rejoin path connects without a password first (F32, live 2026-10-08; built and game-free tested in `JoinFlowStage2ClientTests`, not live-verified).** F19 covered only the after-restart rejoin: **Join now**, the **Rejoin when it's back** retry and the Result page's **Join again** still stopped with `This server needs its password, which Progenitor never saves. …` (log `…; the server needs its password, which is never stored: not connecting`) for a server with no password, because the session had marked a password as used. Every reconnect (`OpenReconnect`) now sets `PromptOnPasswordRefusal` unless the target already opens the game's prompt: it connects without a password and opens the game's prompt only on `IncorrectPassword` (JOINPW1). "A password was used last time" never blocks a connect; that stop and its log line are gone.

**A server on this PC goes through the loopback address** (LOCALREJOIN1, 2026-10-07; built and game-free tested, not live-verified). Join now and this rejoin used to dial the address the original join used; after the game's Continue that is the server list's public address, so a server on this PC was reached only through the router's NAT loopback, and the reconnect could time out. Now, when the target is this PC's own server, the reconnect dials `127.0.0.1` on the same port and transport first and keeps the original address as a fallback, tried once only when the loopback connect reached no server: the game's `Timeout`, `FailedToEstablishConnection`, `Unknown` or `ClientError`, or no answer in 120 s. Any answer from a server (a kick, a ban, full, wrong version, starting up, a password, blocked) is its reason and ends the reconnect. "This PC's own server" is the configured `[Mods] DedicatedServerPath` folder's server on the folder's own port, as the Install tab's route decides it: the target address is this machine, or (a public address, which no interface carries) the folder's server process runs on this PC, its name is the target's and its operator key (the folder's `BepInEx/config/progenitor-operator.pub`) is the target's. A known operator key that differs is never this PC's server, and a public address whose operator key is unknown keeps the original address. The loopback join keeps the original endpoint as the server's record key (`ConnectHostAlias`): its profile, trust pin, Thunderstore acknowledgments and last-server record carry over, and nothing is pinned again. The alias lives only for that reconnect: it is kept through the reconnect's own join and connection, and cleared by any other join, the end of that connection, or a reconnect that failed or was canceled. The client log says which: `JoinFlow: reconnect target 127.0.0.1:<port> (local server: …; was <address>:<port>, which stays the fallback)`, or `JoinFlow: reconnect target <address>:<port> (<why not>)`, and on a fallback `JoinFlow: reconnect to 127.0.0.1:<port> failed (<reason>); trying <address>:<port> instead`. Ordinary joins (the game's own Continue and server list) are not rewritten: Progenitor has no seam in them. The folder's facts come from the background cache (review 2026-10-07: never a process scan on the main thread). A rejoin whose facts have not arrived yet (right after a start, before the first refresh) dials the original address, the safe default.

When the player is **ahead** of a server (a newer copy of a mod than the server requires), getting the server's version no longer destroys the newer one. The newer copy is **parked**: kept on disk, not loaded. Progenitor loads whichever version the server being joined needs, and leaving swaps the player's own version back — at once when the reloader can, else at the next start.

**The store** (`Install/ModVersionStore.cs`, `ModVersionEngine.cs`):

```
BepInEx/progenitor-versions/
  versions.json                     the manifest (schema 1)
  journal.json                      present only while an operation runs
  <mod id>/<version>/<file>.dll     one kept copy, under the name it had when active
```

Two builds of one version are kept as `<version>~<first 8 hex of the sha256>`. Per mod the manifest holds `preferred` (the version the player last chose, else empty: the newest copy they installed themselves), `active` (the copy the store or the join flow placed: `version`, `file`, `sha256`, `forServer` (the server key, `address:port`, it was placed for; empty for the player's own choice), `source`), `pending` (a swap queued for the next start: `version`, `pendingFile`, `file`, `sha256`, `marked`, `forServer`, `queued`) and `parked` rows: `version`, `dir`, `file`, `sha256`, `size`, `source` (`user`, `thunderstore`, `server`; Core start deletes `server` copies that are not the player's own since 2026-10-05, [mod-manifest.md](mod-manifest.md#legacy-cleanup-at-core-start)), `sourceDetail` (`fp@host`-style server key, or the package), `placement`, `userInstalled`, `parked`, `lastUsed`, the `level` and `rule` it declared, and the `ledger` and `record` rows it took with it (below).

**Bounds.** At most 3 kept copies per mod and 128 MiB in all (`ModVersionLimits`); a copy over 64 MiB is not kept. Over either bound the oldest unused (`lastUsed`) is deleted first, but never the player's own copy (`userInstalled`: one no server flow placed — their install, a deploy, a file dropped in by hand), the preferred version, a copy queued for the next start, or the copy the operation just kept. A mod whose copies are all protected may stay over the count; the player deletes one with `join_ui versions_forget` (`force` for their own).

**What keeps a copy.** Every path that would replace the active copy parks it first:

| Path | When | How |
|---|---|---|
| **Use version X** (stage 2) | right before the plan | now (the plugin unloads and the install may take the hot route), else kept loaded with a `.uninstall` marker (the server's version takes the restart route) |
| `join_ui versions_park` | on demand | as the route decides (`restart:true` forces the marker) |

The install window's **Use server's copy** and the phase 3 server install were two more paths here; both were removed 2026-10-05 with server-sent mod files.

**Which version a server needs** (`ModVersionSelect`). When the server's handshake request arrives, every kept mod it asked about is checked with the handshake's own `Handshake.Compare.Evaluate`: the server's row and version rule (`Exact`, `Minor` or `None`) against this client's answer with the candidate version in place of the active one (the active row's level, rule and declared flag kept). When the active copy fails and a kept copy passes — the preferred version first, then the newest — that copy is the pick. A pick whose route is **now** is swapped in on the next frame, **before** the reply, one mod at a time (each waiting for its displaced plugin to unload, below); the reply waits (at most 8 s in all; the server allows about 20 s) until this client declares the kept versions, then the per-server mod pause runs and the answer goes out, so the join passes with no download. A join that ended meanwhile is not answered. A pick that is not swapped is logged (`JoinFlow: versions: the server needs the kept <id> <v>; not swapped at the handshake (<route>: <reason>)`) and shown on the screens.

**The route** (`ModVersionRoutes.Decide`), checked in this order:

| Facts | Route |
|---|---|
| The active copy is another tool's (MANAGED1) or loaded from `BepInEx/plugins` | refused: `Managed elsewhere: installed by <tool>, so Progenitor does not keep or swap its versions.` / `It is loaded from BepInEx/plugins (managed elsewhere), …` |
| A swap is still being finished (journal), or one is queued for the next start, or the active copy carries a `.uninstall` marker | refused until it ends / until the next start |
| A second copy of the plugin GUID in `progenitor-reload` | refused: `Two copies of it are on disk (…); remove one first. Progenitor never loads two versions of one mod.` |
| A copy waiting in `progenitor-pending` | refused: `A copy of it waits for the next start of V Rising (…); its versions are swapped after that start.` |
| A join between its connect and the handshake answer (outside an install window), for the bridge's and the menus' swaps | refused: `A join is in progress; …` (the handshake's own swap is the one that runs then) |
| A Core swap in flight | refused, try again |
| `ctx.UnsafeHarmony`, a previous Core or plugin generation still alive in the process (Bootstrap's admission snapshot, asked with a candidate stem no plugin uses: asked about the loaded file, its `PriorGenerationPinned` counts the plugin's own live context and read "pinned" for every loaded plugin, live 2026-10-04), an older Bootstrap without the snapshot, or reload plugins that depend on it (named) | **restart**, with that cause as the reason: `kept.keepReason`/`kept.pickReason`, the row's `restart: <reason>` (`can't keep yours: <reason>` when refused), and the window's `your copy cannot be unloaded now (<reason>), …` log line: the kept copy is written to `progenitor-pending/<file>` and the active copy gets a `.uninstall` marker; Bootstrap's start deletes the marked file, then promotes the pending one (existing INSTALL2 and FMAN4 behavior) |
| otherwise | **now** |

**A swap now** keeps the displaced copy first (written into the store and read back) and removes it from `progenitor-reload`. Under the same file name the kept copy then replaces it in place, which is the reloader's own unload-then-load in one scan. Under another file name the kept copy is written only once the displaced plugin has unloaded: the reloader loads a settled new file inside its scan and unloads a removed one only after it, so writing both at once could load the new copy in the scan that still has the old one. The store polls (every 0.1 s, and on every frame of the join screens' tick) until the displaced plugin is gone, asking the reloader itself (Bootstrap's own list of loaded plugins, through the HOT2 admission snapshot): while it holds the plugin nothing is written, whatever the time; after 15 s (20 s from the frame tick) the swap is undone and the displaced copy goes back. With an older Bootstrap that cannot answer, the handshake table decides and the write goes after 3 s (handshake) or 5 s (otherwise), by when the once-a-second scan has run. Then the kept copy is written through a `.part` name under its original file name, hash-checked again and stamped now. Should another copy of the mod appear meanwhile (another install), the swap stops: nothing is written, the displaced copy stays kept. Meanwhile the journal stays (other swaps and keeps answer `busy`), a failed write undoes the swap (the displaced copy goes back), and a crash in between rolls forward at the next start. **Use version X** refuses (`… had not unloaded yet, so <v> was not written beside it. Press it again.`) when the kept plugin is still loaded after 5 s. On a refused join, **Use kept X** under another file name says `<name>: the kept 1.8.2 is being swapped in (the previous copy unloads first)…` and offers **Join now** only once the copy is in place. **Two copies of one plugin GUID are not loaded together** by construction; this is not live-verified. Before any write the kept copy's sha256 is checked against the one recorded when it was kept (`The kept copy of <id> <v> changed on disk (sha256 …, kept as …), so it is not loaded. Install that version again.`) and the reload allowlist decides on its file name and hash exactly as for any reload-folder file (`<id> <v> (<file>) is not allowed by your reload allowlist (<token> in BepInEx/config/progenitor-allow.txt), so it is not loaded.`).

**The journal.** Each park and swap writes `journal.json` first: the manifest before and after, the files it creates, and the one fact that says it committed (a park: the active file is gone, or its marker exists; a swap: the target holds the kept bytes, or the displaced copy is already gone, in which case the target is written from the kept copy and the swap rolls forward). Core start (`Reconcile`) and any failed operation run the recovery: committed → finish (drop the swapped-in copy from the store, update the books, write the new manifest); otherwise undo (delete the files this operation created, write the old manifest). An unreadable journal is moved to `journal.json.unreadable` and nothing is acted on. Start also settles a queued swap (promoted: it becomes the active copy; still in `progenitor-pending`: the start refused it, logged; gone: dropped), drops rows whose kept file is missing, and deletes `.part` leftovers.

**The books.** The install ledger (`BepInEx/progenitor-install.json`) and the legacy server-mods record (`BepInEx/config/progenitor-server-mods.txt`, written only by a Core older than 2026-10-05 and removed by the [legacy cleanup](mod-manifest.md#legacy-cleanup-at-core-start)) describe the **active** files only. Parking a copy takes its ledger row (matched by path) and its record row (matched by file name and id) out of them and keeps them with the parked row; swapping it back puts them back under the path it lands on (a queued swap's ledger row as `pending`). A record row for the mod's id is replaced by the swapped-in copy's. The allowlist is not edited.

**Leaving.** When the client leaves (kick, refusal, walk to the menu), the store waits until nothing of the join runs: no client world, the join screens closed, no Thunderstore batch, no reconnect, no fresh rejoin record. Then every mod whose active copy was placed for a server (`active.forServer`) gets the player's preferred version back, one at a time: now, or queued for the next start (the restart route). A mod whose server copy is not active yet (its own copy carries a `.uninstall` marker, or a copy waits in `progenitor-pending`) keeps waiting for that start rather than forgetting it was placed for a server. **Not at start:** a copy a start promoted for a server (the restart route, Restart and rejoin) stays until a connection ends, so a restart taken to get the server's version is not undone at the title screen; the mod page's Restore and `join_ui versions_restore_all` bring the player's version back on demand. A mod the per-server mod pause holds (paused or resuming) is left to the pause at the handshake.

### 11. The install window (2026-10-05)

**Status: source-checked and game-free tested (`NoServerDistributionTests`, `HandshakeInstallGraceTests`). A refused join is held open (default 60 s, `[Networking] InstallGraceSeconds`, the admins' **Seconds to install needed mods**) only when every failing row can be fixed here, during the join ([mod-manifest.md phase 5](mod-manifest.md#phase-5--the-deferred-kick-and-the-install-window-job-fman18-server-half)):

- a Thunderstore package that the server's signed catalog names for the row and that serves a version the server accepts (the server reads the Thunderstore index itself, with its own `[Install] LocalIndexPath` in front; a package it has not read yet does not count, so the join is refused as before);
- a kept copy that loads now, or a copy turned off in the Mods list that hot-loads, which this client declares in its answer (`progenitor.hs.fix`);
- for the [client mod policy](client-mod-policy.md): a required client mod served on Thunderstore at an accepted version, or a not-allowed hot-loaded mod (Pause for this server).

**The window's finish always reaches the server (A6, live 2026-10-07; built and game-free tested, not live-verified).**

- **The answer still goes when no mod was asked.** A server whose only requirement is its client mod policy asks about no mod. Its window still waits for this client's answer and the mod report that follows it. `Handshake.ReDeclareSelf` used to send nothing when the request's rows were empty (`no recorded server request`), and the window lapsed into a kick. It now answers whenever a request reached this connection (`Handshake.HasRequestToAnswer`), rows or none, and the report follows the answer.
- **The page claims nothing early.** Once everything loaded, the page reads `Installed and loaded; telling the server…` (success tone). It says `Installed and loaded; the join continues by itself.` only once the answer went out. If it did not go out, the Result page reads `<names> is installed and loaded, but <server> could not be told on this connection, so its install window will end this join. Join again: the fix is in place now.` with **Join again**.
- **A refusal or a dropped connection replaces the window's page.** When the server refuses the join the window held, or the connection ends (`JoinFlowClient.EndWindow`), the page becomes the refusal's. It reads `<server> ended this join: <reason>.` and, when everything required is in place now, adds `Everything it requires is in place now, so joining again finishes it.` with **Join again** (the reconnect, with the loopback rule). Otherwise the mods page shows the reason. Log `JoinFlow: the install window's join ended (<reason>); …`.
- **The batch log names its source** (`after the local test source install of …`).
- **The lapse reason no longer sends a player who fixed it back to the screens:** `Mod mismatch: <names> was not confirmed within 60 s (this client did not answer again in time). If it is installed now, join again; if not, install it from the join screens first.`

## When each page shows

Two server-wide admin choices (the settings below) decide it; the client compares the signed section with what it last saw from that server.

**Server message** (`ShowMessage`):

| Choice | Shows |
|---|---|
| When it changes or after a reset (`WhenChanged`, default) | On the first join; when the message text changed; on the first join after each reset time passed (a reset that repeats starts a new period each time; with no reset, changes only). Don't-show-again stops the reset re-shows until the text changes. |
| Every join (`Always`) | On every join; no don't-show-again switch. |
| First join only (`FirstJoin`) | Once, then again only when the text changes. |

**Mods page** (`ShowModsPage`):

| Choice | Shows |
|---|---|
| When needed (`WhenNeeded`, default) | Only when the player has something to do or decide (decided 2026-10-06). Always when something needs attention: a missing or mismatched required mod, a pending install, a refusal, or a not-allowed mod still loaded (`needs-attention`). With every required mod ready: a first visit shows it when the server recommends a mod this client does not have, or a not-allowed mod is listed (`first-join`), else it is skipped (`skipped-ready`); a change since the last visit shows it when a recommended mod that is new or changed is not installed, or a not-allowed mod is listed (`mods-changed`), else it is skipped (`skipped-ready-changed`: for example a required version bump the player already runs). Both skips record the new lists as seen and show nothing else (no notice). |
| Every join (`Always`) | On every join. |

**What counts as a change.** The message hash is SHA-256 of the text as the admins wrote it, line endings normalized to `\n`, tokens unrendered (a ticking countdown is not a change), first 16 hex digits. The mods hash is of the server's lists only, sorted (order is not a change), and never of what this client has installed: required `id = version`, recommended `id = version + reason hash`, and the client mod policy. Until 2026-10-05 it also held the shared ids (`s:` entries); a stored hash that had one no longer matches, so a server that shared mods shows its mods page once as changed after the update (`JoinShowPolicy.ModsSnapshot`). When the page opens for a change, the changed rows are tagged **New** (not in the last visit) or **Changed** (version or reason changed), with the changed line under the title. A refusal knows only the failing rows' sources, so its lists are not recorded as seen.

**Seen state** (client, per server): `BepInEx/config/progenitor-join-seen.json`, one row per server keyed `<operator fingerprint>@<host>` (the address alone without a signed catalog), at most 200 servers (the oldest dropped). A row holds `message` (the hash last shown), `dismissed` (the hash dismissed), `reset` (when the message was last shown, ISO UTC; a reset time that passed after it re-shows the message, so moving the reset anchor is not itself a reset), `mods` (the last seen lists) and `modsHash`, `shownIn` (the world the in-world screens last opened in) and `seen` (last update). A file that does not parse counts as a first visit and is rewritten; a file that cannot be read (locked) is left alone and that join's state is not recorded. Only the in-world screens record the mods lists: a refusal and an install window see a narrowed catalog. A page is recorded only once the screens are on show. Each join is decided once per world: when both pages are skipped, a catalog resend later in the session (an admin's edit, a plugin load) does not open them. The bridge's `join_ui forget_seen` deletes the joined server's row; at the title screen it deletes every row, and with `host` every row for that address. (The title-screen case was verified live on 2026-10-19: `forgotten 2 servers`, and the next join was a first join.)

The readback names the reason for each page: `always`, `first-join`, `message-changed`, `reset-passed`, `mods-changed`, `needs-attention`, `skipped-unchanged`; also `skipped-ready` (a first visit with nothing to do), `skipped-ready-changed` (the lists changed but there is nothing to do or decide; the lists are recorded as seen), `skipped-installed` (after this join's install window showed its screens: a first visit, or a change that concerns only mods this join installed and now runs, such as a required version the player just installed; the lists are recorded as seen; any other change still shows `mods-changed`), `refused` (a refused join shows the message), `shown-this-join` (the install window of this join already showed the message), `dismissed` (the message was dismissed until it changes), `no-message`, and `reopened` (opened from the Show button or the bridge).

### Staged edits: Apply, Discard, Close (JOINDRAFT1)

Requested 2026-10-07: "This should have an apply button at the bottom instead of changes being instant. Show the changes." Every edit in the popup changes a local draft (`JoinAdminDraft`); nothing goes to the server until **Apply**.

- **Rows show the draft.** A staged row carries a small marker at the right of its name line: **Added** (green), **Changed** (amber; a typed reason or another rule), **Removed** (red; the name and reason are struck through and **Undo** takes the place of **×**). The reason fields have no **Save**: the reason is part of the draft. The choices (**Any mods** / **Only approved mods**, **Let them join** / **Refuse them**, the mid-session choice) and the install window show the draft's value. Typing a reason or the window's seconds updates the marker and the Changes list in place, so the field keeps its focus.
- **Changes.** One line per change, in plain words, in the order staged, e.g. `Require Progenitor Hot Demo (0.1.0 or newer), reason 'We <3 hot demo'`, `BasinHoverTips: 1.0.19 or newer → exact 1.0.19`, `Mod rules: Any mods → Only approved mods`, `Unrequire Robe Pack`, `Stop recommending Map Markers`, `Map Markers: reason 'Nice map' → 'Shows markers'`, `Approve Zoom`, `Remove Minimap from the approved list`, `Install window: 60 → 120 seconds`. Each line has **×** (undo). Five lines show, then `+N more`. `No changes` when the draft equals the server's state. An edit that brings a value back to the server's removes its change. Requiring a recommended mod says `; moves it from Recommended` (the server moves it) and marks the recommended row Removed.
- **Apply** sends the whole draft as the existing requests, one after another's answer (the client allows few waiting requests), in this order: removals (they free room under the caps), adds, row edits (reasons, rules), approvals (two or more plain ones as `approve-bulk` through `JoinAdminWire.BulkRequests`), the choices (so **Only approved mods** lands after the approvals it relies on), then the install window. An accepted change leaves the draft; a refused one stays with the server's reason after its line (`… (not applied: At most 16 client mods can be required)`, warning tone). An `approve-bulk` row the server did not add stays with the answer's note. No answer stops the run; what is left stays staged (`not sent: No answer from the server.`). Then one `get` refreshes the state. Edits wait while Apply runs.
- **Footer size (CHANGESFIT1, live 2026-10-07).** The Changes block is as tall as what it shows: a clean draft is the single muted `No changes` line; with changes, a one-line heading (`Changes · 2 changes, not sent yet`) and one 22 px line per change, at most five, then `+N more`. Hidden lines take no room (the runtime skips inactive bottom-pinned rows of a dialog), so the scrolling body gets the rest of the frame: with two changes on a 720 px screen it keeps over 60% of the panel body (`JoinAdminDraftTests`). Before, the unused slots still reserved their height and left the body about 150 px.
- **Discard** returns the draft to the server's state. **Close** (and **Escape** on the main page) with unapplied changes asks **Apply your N changes?** with the changes listed and **Cancel** · **Discard** · **Apply** (Escape there is Cancel; Apply closes when every change was accepted, else stays open on the refusals). Losing the connection closes the popup and drops the draft. **Update on server** on an alert line asks you to apply or discard first, since it closes the popup.
- **Another admin.** Every answer is the draft's new base (`JoinAdminDraft.Rebase`): a change the server now already has is dropped; a value another admin changed keeps yours and says so (`(another admin changed it to 30 seconds)`, amber); an add of a row another admin added too becomes an edit of that row; an edit of a row another admin removed is flagged `another admin removed it` (Apply then shows the server's refusal).
- **Locks and non-admins.** A list or choice the operator locked stages nothing (the lock note in the status line) and its rows stay read-only. The popup is offered only to admins, and a refusal for authorization drops the state, which drops the draft.

### Storage and the request channel

- **Store.** `BepInEx/config/progenitor-join-admin.json` on the server, written atomically (temp file, then replace): `{"schema":2,"recommended":[{"id","package","version","reason"[,"name"]}],"requiredClient":[{"id","package","version","rule","reason"[,"name"]}],"clientPolicy":{"mode":"any|approved","approved":[{"id","package","version","rule"[,"name"]}],"unverified":"allow|refuse","midSession":"warn|disconnect"}}` (CLIENTPOLICY1; a schema 1 file loads with no required client mods, Any mods and Let them join, and is written as schema 2 on the next change. CLIENTPOLICY3 added `midSession` to schema 2 without a schema change: a file without it, or with a word other than `warn` or `disconnect` (skipped with a note), reads as `warn`). A `shared` list from a file written before 2026-10-05 loads and is ignored, and is not written back. A row that breaks a limit or repeats is skipped on load with `JoinAdmin: progenitor-join-admin.json rows skipped: …`; a file that is not JSON (or not schema 1, or over 256 KiB) is renamed `progenitor-join-admin.json.bad-<UTC time>` and the server starts with no choices. A file that cannot be read (another program holds it) is read again on the next access; until then every edit is refused (`The server could not read its saved choices …; try again in a moment.`) and the catalog signs no panel rows. The window stays in `progenitor.cfg`.
- **Requests.** One reserved event id both ways, `'PrJa'` (`0x50724A61`): a version byte, a kind byte (request, answer, hello), a nonce, then UTF-8 JSON, at most 15 KiB. Operations: `get`, `recommend-add`, `recommend-remove`, `recommend-reason`, `window`, and CLIENTPOLICY1's `required-add`, `required-remove`, `required-reason`, `required-rule`, `policy-mode`, `approve-add`, `approve-remove`, `approve-bulk` (at most 64 rows) and `unverified` ([client-mod-policy.md](client-mod-policy.md#stage-1-as-built)), and CLIENTPOLICY3's `mid-session` (`value` `warn` or `disconnect`; audit row `progenitor/JoinAdmin/mid-session`; [stage 3](client-mod-policy.md#stage-3-as-built)); a request may carry `approvedFrom`, the first approved row its answer lists. Each answer carries the whole state (when an answer would not fit, the alert lines, the required-id list and then the readable names are dropped first; the stored rows always fit). `share-add` and `share-remove` were removed 2026-10-05 with server-sent mod files.
- **Authorization, audit and limits** are the server-wide settings rules ([settings-scopes.md](settings-scopes.md)): a completed Progenitor handshake; the sender on the server's admin list (no `adminauth` needed) or `User.IsAdmin`, read off a fresh `User` on the server (nothing in a request names its sender); 10 edits per SteamID per minute, reads 30 per minute on their own budget. Every edit and every refused request (a non-admin's read too) is one line in `BepInEx/progenitor-settings.log` and the BepInEx log (`JoinAdmin audit: … settings accepted by <name> (<steamid>, adminlist) progenitor/JoinAdmin/recommend-add/maps.mod "" -> "maps.mod 1.2.0: …"`). A refusal carries no state, so a non-admin learns nothing (`Only server administrators can change who joins.`).
- **What the server checks.** Recommend: an id that is a valid mod id and/or a package that is a Thunderstore `Owner-Name`, a version of one word (at most 64), a reason of one line (at most 120 characters; empty means the placeholder), not already recommended, not a mod the server requires, at most 16 rows. Remove and reason edits name a stored row (an overlay row is refused: edit the file). Window: a whole number of seconds (a request without one is refused, never read as 0), clamped to 0–300.
- **Catalog.** An accepted change (recommend add, remove or reason) re-signs the catalog at once, and the next frame's catalog scan resends it to every handshake-ok client that does not have it yet (server log `ModManifest: catalog re-signed (join-admin recommend-add); resent to N client(s)`; client log `JoinFlow: the server re-signed its catalog mid-session; the open screens refreshed` or `… no join screens are open`), so an open in-world mods page refreshes within about a second and a player sees it on the next join. A server-message edit (a ConfigSync row) is signed and resent by the scan itself (`(scan)`); the install window's seconds are not part of the catalog. **Fixed after live 2026-10-04:** the direct re-sign used to hide the change from the scan, which compared the stamp before and after its own rebuild, so nothing was resent until a rejoin; every re-sign now leaves a resend pending (`ModManifest.CatalogScan`, game-free tested in `JoinCatalogResendTests`; not live-verified).

### Recommended rows: the panel and the overlay

The signed section's recommended list is the panel's rows first, in their order, then the operator overlay's (`BepInEx/config/progenitor-manifest.json`, below) rows for mods no panel row names (same id or package), up to 16 in all (`JoinAdminPolicy.Merge`). A panel row for the same mod as an overlay row wins (its reason is the one players see); removing it brings the overlay row back. The overlay stays supported as it was in stage 1:

```json
{
  "serverName": "Night Garden",
  "mods": [],
  "recommended": [
    { "id": "maps.mod", "package": "Owner-BroaderMap", "version": "1.2.0", "reason": "The castle map our events use." }
  ]
}
```

At most 16 rows; `id` at most 63 characters, `package` 128, `version` 64, `reason` 200. A row over a cap is skipped with a server log line (`JoinFlow: progenitor-manifest.json recommended row skipped: …`). Recommended rows never become catalog rows and never affect the join check.

On the player's side nothing new is needed: the mods page's recommended section is built from the signed section and the catalog rows, and the [mods-changed check](#when-each-page-shows) already hashes the recommended ids, versions and reasons, so a panel change shows the page again on the next join (under When needed) with `New` / `Changed` tags.

### Shares (removed 2026-10-05)

The "Shared with refused players" list, its picker and the `share-add` / `share-remove` requests are gone: servers no longer send mod files ([client-mod-policy.md](client-mod-policy.md#security)). A refused player now gets the [install window](#11-the-install-window-2026-10-05) when Thunderstore serves what the server needs; name the package in `progenitor-manifest.json` so the catalog row carries it.

### Refused joins

The server keeps a bounded record in `BepInEx/config/progenitor-refused-joins.json`: one row per failing mod of each refused join — the mod id, the version the server required, the version the player had (empty when missing; `?` when what the client sent is not a version), the kind (`missing`, `older`, `newer`, `mismatch`; CLIENTPOLICY1 adds `client-missing`, `client-older`, `client-newer`, `not-approved` and `unchecked`, [client-mod-policy.md](client-mod-policy.md#stage-1-as-built)), the time, and a join number that only groups the rows of one refusal. **No player identity is stored** (no name, SteamID, address or user index). Rows older than 7 days go, and at most 500 are kept (the oldest first).

- **Only mods the server requires.** A mod only the client declares as required ("this server doesn't run it") is not recorded: its id and version are whatever the client sent, and recording them would let any player write text into the admins' alert. The one exception is CLIENTPOLICY1's `not-approved` row, which keeps only a plain id (`[A-Za-z0-9._-]`, at most 63 characters), never the client's name or version.
- **When.** A join is recorded when it is refused: a kick now, or an install window that expires. A window that ends in an accepted join, or a disconnect during it, records nothing.
- **Bounds against flooding.** One record per connection, however many failing answers it sends before the kick; and at most 3 per SteamID per hour (an in-memory throttle; the SteamID is never written), so a player reconnecting in a loop cannot rotate real rows out.
- **Writes.** The file is written at most every 2 seconds and when Core unloads. Log: `JoinAdmin: refused join recorded (N mod row(s))`, or `… not recorded (this player already has 3 this hour)`.

## Data flow

| What | Refused join | Successful join |
|---|---|---|
| Message, reset settings, server time zone | The signed join section on the deny descriptor | The signed join section on the catalog |
| Recommended list | The same section (the admin panel's rows, then the overlay's) | The same section |
| Required list and the client's status | `Handshake.ServerAsked` + this client's `Provided`, through `Handshake.Compare` (snapshotted at the refusal, before the join's end empties them) | The same tables, with each required version taken from the section's `versions` and this client's from its loaded plugins (current after a hot swap) |
| Readable names of required mods | The section's `names` (the server's plugin names) | The same section |
| The client mod policy (CLIENTPOLICY2) | The section on the zero-row deny descriptor: `requiredClient`, `policyMode`, `approved`, and under Only approved `runs`; remembered in the server's profile for the next join | The same section (a mid-session re-sign updates the remembered copy and, CLIENTPOLICY3, re-checks this client's mods: the automatic pause, then a report). The mid-session choice is not signed: the server's own notice says what happens |
| Sources (Thunderstore packages) | The narrowed descriptor's rows (`package`) | The full catalog's rows |
| Admin values for editing | — | ConfigSync's server-message rows |

The section is signed separately from the catalog body and bound to it; clients without join-flow support ignore it and newer ones handle its absence. A JOINFLOW1 server always sends it (its time zone and the two page choices travel even without a message); a client without one shows nothing. Schema, signing and the deny-path rules: [mod-manifest.md](mod-manifest.md#the-join-section-joinflow1).

## Known limits

- Not live-verified: Leave from an install window, the retargeted install window's kept, turn-on and pause fixes (its Thunderstore fix was live-verified 2026-10-05; [recipe](test-rig.md#install-window-from-thunderstore-tofu-and-legacy-cleanup)), and every fix made after the 2026-10-04 run (listed in the status line).
- A message longer than the box draws its countdown when the page is drawn and does not tick.
- The frequency choices are not live-verified; in particular the in-world reset re-show depends on the client clock and the section's zone.
- The client reads the server's time zone from the section; a client that does not know the server's zone id uses a fixed offset (no daylight-saving rules) for the admin picker and the roll-forward.
- Stage 3 is not live-verified. The Players joining row on Progenitor's page needs the server's hello, sent after an ok handshake: a client Core hot-swapped mid-session has none until the next join (or a handshake re-ask), so the row stays hidden until then.
- The remove buttons draw `×` (U+00D7, in the game font) rather than `✕`, which the font lacks.
- Stage 2 is not live-verified at all. In particular unproven in the game: Join now's return to the title view from the "You were kicked" screen (`GoToView(MainMenu)` with no world), the relauncher under Steam (a game Steam started inside a job object that kills its children on exit would also end the relauncher; then the manual start still reconnects), `Application.Quit` promoting the staged files at the next start, the `LastConnectionData.Password` read, `IsHostingPrivateGame` for a private game, and whether an install window re-answers by itself after a Thunderstore hot load.
- The batch and the reconnect live in the Core generation that started them: a Core hot swap during a batch stops its rows that have not started writing, and during a reconnect leaves the join to the game.
- While a batch runs, the mods page is rebuilt at most twice a second for its progress.
- On the manual path the quit waits 6 s so the sentence can be read; a Core hot swap inside those 6 s drops the quit and leaves the record, which a manual start within 10 minutes then uses.
- Stage 4 is not live-verified at all. In particular unproven in the game: a plugin's handshake rows dropping out when the reloader unloads it (the signal a swap under another file name waits for; after 3–5 s it writes anyway), the handshake reply waiting a few seconds for the swap (the server's own deadline is about 20 s), Bootstrap removing a marked copy before it promotes the pending one in the same start, and the leave watch's idle rule on the "You were kicked" screen.
- A Core hot swap while the handshake reply waits for a swap drops that wait (the reply is not carried across generations, unlike the per-server mod pause's); the server then refuses after its deadline and the next join passes, because the kept copy is active by then. A swap waiting for its unload is finished by the next Core's journal recovery (roll forward).
- A copy's provenance is inferred: a copy the store or the join flow placed for a server, or one the legacy server-mods record names, is a server's; everything else is the player's own and is never evicted. An old copy a server flow replaced while it was not ahead is kept as the player's too.
- Only Progenitor's own reload folder is managed. A mod loaded from `BepInEx/plugins` (a mod manager's install, or a plain BepInEx plugin) is never parked or swapped.
