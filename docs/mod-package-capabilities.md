Move the current overview's framework-settings entry to Configuration when the tabs are implemented. Per-mod settings remain under Mods. The join screens are not another tab. (The join-time consent overlay that suspended the workspace was removed 2026-10-05.) Unimplemented installation capabilities must remain visibly unavailable rather than presenting working-looking controls.

Install mods distinguishes **declared hot-swap support** from the installer's final decision. Before a change, show the affected mods and dependencies, affected side, and one of: **Apply now**, **Restart client required**, **Restart server required**, **Restart both required**, or **Unknown / blocked**, with a short reason. Server inventory does not grant a player permission to change server mods.

## Player AI discovery and installation

Local target selection follows the same rules in MCP and the menu: client only, configured local server only, or both. An unqualified install request defaults to the client; it must not silently select a server or expand to both. An explicitly selected target is shown in the plan. A combined plan identifies the configured local server by name and validated installation identity and requires explicit opt-in.

The separate client MCP companion exposes the same catalog as Install mods: search by player intent, list/filter results, and retrieve descriptions, source links, versions, dependencies, supported sides and declared capabilities. Queries return structured, bounded results with pagination and freshness/source information. Catalog descriptions are untrusted content, never instructions or permission to execute code. Describe matches as candidates; a description is not proof that a mod works on the player's game version.

The intended flow is: the player describes a wanted feature; the AI searches, explains a matching mod and its limitations, requests the shared installation plan, then offers to install it. A wish or search request alone is not installation consent. After explicit approval for that plan, the MCP invokes the same supported installation operation as the UI and reports verified completion or the remaining restart/manual step. The player and AI write no code and do not require Dev tools.

Expose structured operation progress, refusal reasons and final readiness through MCP. Bind approval to the exact plan and affected side; changed artifacts or expanded effects cannot reuse stale approval. Personal client installation must respect server compatibility rules. Server changes require the authority defined in [Management authority](#management-authority); access to catalog data grants no administrative authority. Browsing remains usable when installation is unavailable, with the reason returned explicitly. Provider credentials stay in the companion's secure configuration, not tool results or mod descriptions.

Acceptance includes a natural-language feature search through the real MCP, description/details retrieval, matching UI/MCP plans, refusal without installation approval, approved installation through the shared handler, and truthful restart/refusal outcomes. MCP implementation and end-to-end verification remain planned under M3.11 and M4.4.

## Management authority

Two authorities install mods, and the Install tab's one **Server** target picks between them ([mods-menu.md](mods-menu.md#server-installs-one-server-target)):

- **Local folder.** The client and an explicitly linked dedicated-server installation on the same machine. It requires local operating-system access to the selected installation and no game admin status; it works with the server stopped. A connected server counts as that folder's server only when the joined address is this machine and the Stop server check (port plus handshake) passes.
- **Admin-list member of the connected server (decided 2026-10-01).** A player whose SteamID is in a Progenitor dedicated server's own admin list may install, update and uninstall Thunderstore mods on **that** server, right after joining and without `adminauth`. The server reads the SteamID off the sender's user entity (`User.PlatformId`) and checks it against the same `adminlist.txt` the game loads, for every request; a player who is not on that file but ran `adminauth` (`User.IsAdmin`) is authorized too. This is the same trust the game's own admin list carries: only someone with file access to the server can edit it. Nothing about identity or privilege travels in the request. The host can switch it off or narrow it to listed SteamIDs ([Admin remote installs](#admin-remote-installs)).

Never request or store any password for either route. RCON is not used. No separate gameplay admin role is introduced: the game's own admin list is the authority. Chat commands and player MCP requests from other machines do not install anything; the remote route is the Progenitor channel below, with the same plan, admission and staging code as a local install.

Install only trusted mods: their code runs with the affected process's permissions and may access saves, configuration and other files available to it. Hot-swap eligibility does not sandbox code or prove trustworthiness. On the remote route the server's host is trusting its admins with that power; a host who does not should set `[RemoteInstall] Enabled = false` or list the trusted SteamIDs.

## Admin remote installs

Status: **source-checked and game-free tested, not live-verified.** Code: `src/Progenitor.Core/Install/RemoteInstall*.cs`, `ServerRoute.cs`; tests: `RemoteInstallTests.cs`, `ServerRouteTests.cs`, the REMOTEINST1 cases in `InstallListViewTests.cs`.

**Channel.** One reserved custom event id, `'PrRi'` (`CustomEventPolicy.RemoteInstallEventId` = `0x50725269`), carries both directions. Every packet is versioned and tagged with its direction, strings are bounded UTF-8, and a malformed packet is dropped whole. The client declares `Handshake.Capability.RemoteInstall`; the server pushes its status after an ok handshake only to a client that declared it, and the client sends only after a status arrived, so neither side sends the id to a peer without a handler.

| Direction | Message | Content |
|---|---|---|
| Client → server | request | nonce, op (`install`, `update`, `uninstall`, `list`, `cancel`), Thunderstore `Namespace-Name` (an `uninstall` may name `plugin:<guid>` instead, SRVUNINST1), exact `major.minor.patch` version, force flag (uninstall only). Never a URL or file bytes. |
| Server → client | progress | nonce, op, stage (`accepted` → `downloading` → `verifying` → `installing` → `hot-loaded` \| `pending-restart` \| `removed` \| `refused` \| `failed` \| `cancelled`), reason code, short detail. |
| Server → client | status | enabled, authorized (`authorizedBy`: `adminlist` \| `adminauth` \| `none`; the old `admin` flag is the same bit), allowed, Thunderstore reachability (+ cause), the requester's SteamID, and, for an allowed admin only, up to 64 rows (package, version, state, route): the ledger rows, then one `plugin:<guid>` row per plugin the server identified (SRVUNINST1). |

**Checks, in order** (`RemoteInstallPolicy.Check`), each answered with a named refusal: the sender is authorized — on the admin list, or `User.IsAdmin` (`not-admin`); `[RemoteInstall] Enabled` (`disabled`); `AllowedSteamIds` when set (`not-allowed`); package and version syntax (`bad-package`, `bad-version`); a per-admin rate limit of 5 operations per 60 seconds (`rate-limited`); one operation at a time server-wide (`busy`). Then, inside the claimed slot so a refused request never reaches the network: the package is in the server's own fetch of Thunderstore's V Rising community index (`not-found`), the listing is in the V Rising community (`not-v-rising`), the index has exactly the requested version (`version-not-found`, with the version the server sees), the download link is on the Thunderstore host (`not-thunderstore`). F16 (2026-10-07; built and game-free tested in `RemoteInstallServiceTests`, not live-verified): a listing the server's **own** `[Install] LocalIndexPath` carries is the operator's, so it installs for an admin: the community and Thunderstore-host checks and the size comparison are skipped for it, while the version, ledger, inspection, qualification and hot-load admission checks still apply. Only keys that index lists qualify (a client names a key, never a file). With the key empty nothing changes. Its audit line adds `source=local-index`. An allowed admin's status lists what that index offers as rows `local:<key>` with the version it has (at most 32, after the ledger rows and only where they fit; an older client matches no listing to them; a key whose `local:<key>` exceeds the 128-byte UTF-8 wire limit is left out; the server reads that index again only when its file changes, by path, size and write time; review L4/L5, built and game-free tested in `RemoteInstallTests`, not live-verified), and the ledger state fits the op (`already-installed`, `not-installed`).

**Install.** The server builds an `InstallCatalogService` over its own BepInEx root with the local-server target pointing at that root and `thisProcessIsServer` set, and runs the same download, inspection, admission, dependency planning and staging the Install tab uses for a local server. A hot-loadable Progenitor plugin that admission clears (a reviewed qualification record on the server, see [hot-reload.md](hot-reload.md)) is written to `progenitor-reload/` and hot-loaded; the server then waits up to 6 seconds for its reloader to report the plugin and answers `hot-loaded` (or `hot-loaded` with `hot-load-unconfirmed`). Everything else goes to `progenitor-pending/` and answers `pending-restart`. Rows the remote route writes carry `"route": "remote"` in `BepInEx/progenitor-install.json` and are spelled with the Thunderstore key; rows without the field were written by the local folder route. A server with no ledger gets an empty one first, so a remote install is always uninstallable. Network, inspection and planning run off the main thread; the one write step runs on it.

**Uninstall** removes only ledger files, as locally: a hot copy is deleted now (the reloader unloads it), a pending copy is deleted, a promoted copy that loaded at start is marked for the next start. Another ledgered install that depends on it refuses with `has-dependents` unless `force` is set. Dependents come from Thunderstore's index, so while the server cannot load it an uninstall is refused (`unavailable`, detail `the server could not load Thunderstore's package index: <cause>`) unless `force` is set; with `force` it works offline. A package the loaded index does not list (a local or delisted package) is still checked against the other installed packages' own listings (`has-dependents` unless `force`); only an index that could not be loaded refuses as `unavailable`. A ledger row whose file is gone is only an install record: neither side reports it as installed, and an uninstall of it (the bridge's `remote_install uninstall`, or the next remote install of that package, which clears it first) drops it without the index and touches no file; the reconcile pass does not drop such rows on its own, because a file another tool moved must not silently lose its record (SRVUNINST1).

**Uninstall by plugin (SRVUNINST1, 2026-10-07; built and game-free tested, not live-verified).** A server mod the ledger does not list is addressed by its plugin GUID: the package field carries `plugin:<guid>` (no wire field or byte changes; an older server refuses it as `bad-package`, an older client matches no listing to such a row). The server identifies its own copy in the order decided 2026-09-29 and reports the verdict as the row's state: a file its ledger names takes the package uninstall above (the row carries the package's state); a top-level DLL in its `progenitor-reload` that declares the plugin is `hot` and is deleted now, so its reloader unloads it (`ReloadFolderPlugins.Remove`, the Mods page's FWALLOW1 removal), unless that DLL also declares other plugins or the same GUID also loads from `BepInEx/plugins` (then state `none`, refused), and unless a loaded plugin hard-depends on it (`has-dependents`, overridden by `force`); the shared-file refusal is made again in the deleting step itself, and the uninstall identifies the files afresh (the status rows use a cached identification); a removal already waiting is `uninstall-pending`; an ordinary plugin in `BepInEx/plugins` it identifies with certainty (`PluginFileActions.Identify`) is `loaded` and gets the preloader's next-start request in its own `BepInEx/config/progenitor-plugin-actions.json` (answered `pending-restart`); anything else is state `none` and refused `unavailable` with `managed elsewhere: <why>`. Progenitor's own plugins (Core, the dev bridge, the preloader) are never listed or removed. The preloader request needs `Progenitor.Preloader` installed on the server.

**After a change** the server sends the requester its new status, so the Install rows update at once. The handshake is **not** re-run for connected players: the existing re-evaluation would kick an admin whose client lacks a part the new mod requires (the join's install grace is already spent). The server's handshake rows change as the hot-loaded mod registers them, and every client sees them at its next join. **Restart-pending** installs show `Installs at the next server restart` and offer **Save and stop server**, which opens the stop confirmation and sends the graceful Stop server request ([Stop server to apply](mods-menu.md#stop-server-to-apply-f20)); the host or panel must start the server again. There is no auto-restart.

**Network failures** never leave a partial file and never touch the ledger: downloads land in a `.part` staging file that every operation deletes at its end, and a body shorter than its `Content-Length` is rejected. Each failure is named: `thunderstore-unreachable` with the cause (`dns`, `refused`, `timeout`, `tls`, `stalled`, `network`, or `http-<code>` for 403, 407, 429 and 5xx; any failure to fetch the package index counts), `download-failed` (`truncated`, another HTTP status such as `http-404`, the size ceiling, other transfer faults) or `verify-failed` (the package failed inspection, including a hash mismatch, or its size differs from the listing's `file_size`). A reachability cause also updates the reachability the status advertises; an admin's own Cancel never does. A client that hears nothing about a running step for 180 seconds stops showing it as running. The server probes Thunderstore once at start (one bounded GET of the base URL; any HTTP answer counts as reachable) and again on a `list` request at most once a minute, so the row can say `Remote installs unavailable: the server can't reach Thunderstore (<cause>).` before the admin clicks. The admin can cancel a step until the write starts.

**adminauth for the other admin features.** The status also carries `onAdminList` and `adminAuthed` (`User.IsAdmin`) for the receiving player, so the client can offer **Authenticate as admin** where a feature still gates on `IsAdmin` ([mods-menu.md](mods-menu.md#authenticate-as-admin)). That button runs the game's own `adminauth`; the server's `AdminAuthSystem` decides. It is off until checked live (`[Ui] AdminAuthButton`).

**Which admin list.** `<persistentDataPath>/Settings/adminlist.txt` when it exists, else the install's `VRisingServer_Data/StreamingAssets/Settings/adminlist.txt` (`ServerAdminList`). The server knows its own persistentDataPath (the `-persistentDataPath` argument, else the game's value). Read-only research in the game's metadata shows the game's `FileUserList` holding exactly these two (local and default); the local file is the one the game saves, so it wins. One SteamID per line; blank lines and anything that is not a number are ignored. The file is re-read when its write time or size changes, checked once per request, so an edit takes effect without a restart. If it cannot be read, only `adminauth`ed players are authorized and the server logs that once. Plain file IO; no native call.

**Server host settings** (`BepInEx/config/progenitor.cfg`, section `[RemoteInstall]`, read when the server's Core loads). Until the section is bound, and whenever it cannot be read, remote installs are **off** (fail closed):

| Key | Default | Meaning |
|---|---|---|
| `Enabled` | `true` | Off answers every request `disabled`; rows show `Server has remote installs off`. |
| `AllowedSteamIds` | empty | Comma- or space-separated SteamID64s. Empty: any in-game admin. Invalid entries are logged and ignored. |
| `LockedInGame` (section `[ServerSettings]`) | empty | Settings that cannot be changed in the game, any admin included ([settings-organization.md](settings-organization.md#locking-settings-in-the-servers-config-file)). `progenitor/JoinAdmin/allowed-steam-ids` locks **Admins who may install mods**, `progenitor/JoinAdmin/remote-install` locks **Remote mod installs**, `operator` locks both and the notice timing, `*` locks every server setting. The page shows a locked row read-only, and the server refuses the edit with an audit line. Read on each use. |
| `AllowedSteamIdsInGame` | `true` | **Deprecated** (use `LockedInGame` above). `false` adds `progenitor/JoinAdmin/allowed-steam-ids` to the lock list and logs a deprecation warning once. |
| `ConnectTimeoutSeconds` | `10` | Connection to Thunderstore. |
| `StallTimeoutSeconds` | `20` | A download that receives no byte for this long fails as `stalled`. |
| `TotalTimeoutSeconds` | `120` | One fetch (the index, or one package) in all. |
| `ThunderstoreBaseUrl` | `https://thunderstore.io` | **Test/diagnostic setting.** The index is `<base>/c/v-rising/api/v1/package/` and downloads must come from that host or a subdomain. Point it at an unreachable https address (for example `https://127.0.0.1:9` or `https://progenitor-test.invalid`) to test how an outbound-blocked host is reported. An `http://` value is refused as `thunderstore-unreachable (config)` rather than fetched. |

**Edited from the game (settings organization stage 5; built, game-free tested, not live-verified).** An admin of the server can change `Enabled` (**Remote mod installs**) and `AllowedSteamIds` (**Admins who may install mods**) on Progenitor's page, under **Server settings** · **Operator** ([mods-menu.md](mods-menu.md#where-progenitors-settings-are-drawn)). The change goes through the admin channel (`'PrJa'` operations `remote-install` and `allowed-steam-ids`), not this channel. It has that channel's authorization (the admin list or `adminauth`; `AllowedSteamIds` itself does not restrict who edits it), rate limit and audit line in `progenitor-settings.log`, with the before and after lists. The server writes this file and reads `[RemoteInstall]` again, so the next request uses the new values. The list grants the right to install mods on this server, so the row says so. Turning remote installs off, or a list change that leaves out the admin making it, asks for confirmation first. The list is SteamID64s only, each once, at most 64; any other token refuses the change.

**Audit log.** One line per finished operation, refusals included, in the BepInEx log and in `BepInEx/progenitor-remote-install.log` (rolled to `.1` past 1 MiB): `RemoteInstall <utc> admin="<character>" steamId=<id> authorizedBy=<adminlist|adminauth|none> op=<op> package=<Namespace-Name> version=<v> result=<stage>[(<reason>)] detail="…" files=[…]`.

**Open question: relaying a package through the client (not implemented).** When the server cannot reach Thunderstore, the admin's client could download the package and send its bytes to the server. Undecided; risks to settle first: (1) trust moves from "the server fetched it from Thunderstore over TLS" to "an admin's client says these bytes are that package" — the server could only verify against a hash it fetched itself, which it cannot when it is offline, so it would be trusting the admin's machine; (2) a compromised or malicious admin client could push arbitrary code, which today requires the package to exist on Thunderstore; (3) 15 KiB event payloads mean a chunked transfer with its own bounds, resume and memory limits on the server's main thread; (4) the audit log would have to record that the bytes came from a client. A middle ground to evaluate: the client relays only packages whose sha256 the server can check against a hash list it obtained earlier while online.

## Local dedicated server management

This section is the **local folder route**: same-machine installations only. Network-share installation roots and remote agents are out of scope. Installing on a connected remote server is the [admin remote install](#admin-remote-installs) route.

Configure the local server folder on **Configuration**. The Install tab's toolbar server picker now chooses the server ([mods-menu.md](mods-menu.md#install-rows-per-side-installsides1)); the older **Default install target** row (`[Install] DefaultTarget`, still loaded, no longer used: Follow the mod's side, Both, My client, Server); there is one **Server** target, and the validated folder is its route whenever the client is not connected or is connected to that server ([mods-menu.md](mods-menu.md#server-installs-one-server-target)). Both is an explicit choice (or a both-sided listing under Follow the mod's side), never a consequence of registering a server. Detection may suggest a folder; it never registers or modifies it automatically. A connected server that is not this folder is managed only through the [admin remote install](#admin-remote-installs) route; otherwise its inventory is shown read-only.

**Admin list helper.** When the validated folder's `adminlist.txt` does not contain this player's SteamID, Configuration → Local server shows `You're not on this server's admin list` and **Add me**, naming the SteamID it will add. The file is the first that exists of: `<persistentDataPath>\Settings\adminlist.txt` (from the running server's command line, then the launch record), `<server>\Settings\adminlist.txt`, `<server>\VRisingServer_Data\StreamingAssets\Settings\adminlist.txt`; with none, it is created at the persistentDataPath location, and with no known persistentDataPath the helper refuses rather than guess. It appends one line, keeps every existing line and the file's line endings, never adds a duplicate, writes atomically and keeps `adminlist.txt.progenitor-bak`. The SteamID is the one a Progenitor server last reported for this player (the remote-install status packet carries it), kept in `BepInEx/progenitor-cache/steamid.txt`; until a Progenitor server has reported it the helper stays hidden. After **Add me**, remote installs work right away (the server re-reads the file per request); the game's admin commands still need `adminauth`. Whether the game's own `AdminAuthSystem` sees an edited file without a restart is **unverified** (the game's metadata shows a `FileUserList` with a 60-second refresh interval and no file watcher), so that note says adminauth may need up to a minute or a restart. Live check pending. The local folder route itself never needs admin; the helper exists so the host's other admin features (admin commands, ConfigSync server edits, Stop server's graceful path) work too. If a previously linked folder becomes unavailable, show that target as unavailable and block its pending changes rather than silently falling back to another folder.

Users may choose their own same-machine dedicated-server installation folder. Product validation must not hard-code a developer's production path as forbidden. Validate installation identity, access and write containment independently of the folder's name. Keep this separate from bundled-server staging, which has a different root boundary, and from agent/test tooling: the project's prohibition on operating `C:\VRisingServer` remains unchanged and applies to our work, not every user's product configuration. Validate on folder Apply and again before installation writes; a refused change preserves the prior valid configuration. Leaving the field empty means no managed local server.

The setup stores a friendly name and validated local installation identity. Verify the resolved folder, expected server executable, installation layout and filesystem access; reject ambiguous client/server roots and paths escaping the registered installation through links. Match a running server by its resolved executable path and instance configuration, never process name alone. A local folder selection is not runtime admin authority: pairing with a running server must also establish authorized local control. A stopped server can use the supported offline installation path without a running-game handshake.

One Install action builds a plan for exactly the selected targets. When Both is selected, it combines the required artifacts into one confirmation; separate installation actions remain fully supported. Package metadata determines placement within that selection, never expands it. A mod requiring both sides can have its client portion installed independently for use with another server; report any peer requirement as pending or unverified instead of forcing a local-server install or claiming end-to-end readiness. Conversely, local-server-only installation never changes the client. The currently connected server and the configured local server are distinct identities, even when the player is connected elsewhere. Runtime activation still follows compatibility checks for the current connection; stage for later if immediate activation is incompatible. The Mods tab shows Client / Server / Both badges and optional side filters, while configuration, saves, caches and installation roots remain separate.

Preflight every affected target and dependency before modifying either installation. One confirmation covers the named targets, exact changes and restart requirements. Stage and verify all required artifacts before activation; serialize operations per installation. Combined installation is not a promise of atomic runtime rollback across processes. If activation fails midway, report each side's actual state, preserve recovery information and stop dependent activation; never declare the combined installation complete. Stopped-server results say installed/pending startup, not runtime-ready. Running-server changes use supported Progenitor lifecycle operations; a folder copy alone is not a hot swap. Restarts require explicit authorization and are never a silent consequence of Install.

Acceptance covers no configured server (controls absent), validated separate-folder setup, unavailable/incorrect folders, all three target selections, client-only installation of a both-side mod while connected to another server with no local-server writes, server-only installation with no client writes, explicit Both opt-in, a failed preflight leaving both unchanged, a partial activation failure with accurate recovery status, and stopped versus running-server behavior. All live tests use an authorized isolated installation; registering production locations for tests is prohibited by project rules.

## Developer declaration

Define a versioned Progenitor metadata document shipped inside the package, separate from the provider's manifest. Its exact filename and schema must be finalized with a parser and packaging example before advertising authoring support. Required information:

- Schema version, stable plugin id and package version.
- Supported game and Progenitor version ranges.
- Runtime side: client, server or both; network presence/version requirements remain separate.
- Per-side support for initial hot load, replacement and removal. These are distinct capabilities; supporting one does not imply the others.
- Entry assemblies, intended installation paths, and dependencies with version constraints.

A declaration is an author claim, not proof of cleanup or permission to execute. A Progenitor dependency or base class alone must never enable hot loading. No executable discovery hooks are allowed: package inspection must not load its assemblies into the game.

## Installation decision

1. Resolve the exact package versions and complete dependency changes for each affected side. Identify each artifact by content hash; package id/version alone cannot bind a decision to bytes.
2. Validate metadata and package layout against the supported schema, running game/framework and installation paths. Missing, contradictory or unsupported metadata means no hot loading. Use restart-required only when the normal restart installation path is supported; otherwise return unknown/blocked.
3. Check every changed dependency and the currently loaded generation's ability to unload. Bootstrap, loader/core replacements that require restart, native injection and unsupported patching override an author's hot-swap declaration. Compatible reloadable Core updates follow the existing reload contract.
4. Obtain the running framework's eligibility decision for the requested operation. Unsafe runtime registrations, active work that cannot quiesce or an incompatible peer may refuse an otherwise declared capability. Coordinated changes on both sides require the applicable handshake and lifecycle support; metadata does not implement that coordination.
5. Present the complete plan and obtain the applicable local consent or server authorization. Recheck hashes, loaded generations, permissions and connection identity before execution. A changed plan requires renewed review when its effects or restart requirements change.
6. Execute through Progenitor's supported installer/reloader. Report completion only after loaded-image and readiness checks. Refusal must preserve the running generation; an unexpected failure must report actual state and follow the existing recovery contract. Never silently restart, disconnect or force an unsafe unload.

The existing server-manifest `hotLoadable` flag remains a legacy declaration input. It cannot override package checks, dependency requirements or a runtime refusal. UI and future player/admin MCP entry points consume the same structured plan and reasons; neither independently guesses restart behavior. Cache discovery separately from installation decisions and keep network/package inspection off the game main thread.

## Implemented admission model (ADMIT1) and the executor gap

Status: **source-checked and unit-tested offline; not live-verified.** This maps the decision above onto what `src/Progenitor.Core/Install/Admission/` implements. Everything is `internal`; no public API was added.

Plain data only. | The compatibility-rewritten (effective) image is not yet part of the key; the Bootstrap increment must add it. |

## Share mod links in game chat

**Status: the token, the share controls and the link resolver are source-checked, built and game-free tested (`tests/Progenitor.Tests/ModLinkTests.cs`); not live-verified. Drawing tokens as clickable links in received chat lines is not built yet** (stage 3 of [chat.md](chat.md#planned-not-implemented)). Players can share a mod from the manager into game chat. A recipient clicks the mod link to open that mod in the in-game manager: the installed detail page when present, otherwise its catalog detail page under Install Mods.

**Token.** A mod link is plain chat text: `[mod:Namespace-Name]` or `[mod:Namespace-Name@1.2.3]`, the Thunderstore package full name with an optional version (`Progenitor.Chat.ModLinkToken`). The namespace and the name are each 1 to 64 characters of `[A-Za-z0-9_]`; the version is 1 to 4 dot-separated groups of digits. Anything else is plain text, and a line yields at most 8 links. Players without Progenitor see the token as written.

**Sharing.** **Share** (a small button over the name, shown while the pointer is on the row) on each Mods list row and Install Mods row, and **Share in chat** in the mod page's header button row and in the Install Mods drawer. It appears only when the mod's package is known: the install ledger's package source, else the Install listing that names the plugin by its manifest id or inspected identity, never a listing matched by name alone. An installed mod's link carries its installed version; an Install Mods listing's link carries no version. In a game, the Mods menu closes and the token goes into the chat input (`ChatWindow.InsertIntoInput`) without sending. At the title screen, or when the chat cannot open, the token is copied to the clipboard with the notice *Copied. Paste it in chat once you're in a game.*

**Opening.** `ModLinks.Open(package, version)` (client) opens the Mods menu if needed and then: the installed mod's page when an installed mod has that package; otherwise, with Thunderstore on and the index loaded, that listing in Install Mods (the tab's search is cleared so it cannot hide the listing). It returns `opened installed`, `opened catalog`, `not found: …`, or `opening` while the menu is still opening (the result follows on a later frame). A notice explains an unknown package, Thunderstore turned off, an index that is not loaded, an invalid link, or a requested version that differs from the installed or newest listed one (the page still opens). Opening never downloads, installs, updates, enables or changes a target or a source.

Links carry a stable provider/package identity and optional version, not just a display name. Resolve through configured catalog providers; opening a link never installs, updates, changes targets, or enables a source. Show a clear unavailable result for missing packages, disabled sources or unavailable requested versions. Treat chat labels and payloads as untrusted data; accept only supported mod-link payloads, never arbitrary commands or file paths. Recipients without Progenitor receive a readable mod reference; clickable behavior requires support on the receiving client. Opening a link never selects a server target; server installation still requires an explicitly configured same-machine installation. Preserve chat input and normal menu/consent behavior.

**Server-mod warning:** a chat link is a recommendation, not verification or approval. Before installing a new or untrusted server mod, verify its source, compatibility and dependencies, preserve a recoverable backup and test on an isolated server. Before uninstalling an existing server mod, verify dependent mods and saved-world data will remain usable. Present this guidance in the linked server-mod detail/install flow; opening a link never authorizes installation or removal. Do not label a package trustworthy merely because its catalog entry or hot-swap checks pass.

Acceptance: share and click installed and uninstalled mods, duplicate display names from different authors, versioned links, missing/disabled/offline sources and malformed links. Verify the intended detail page opens without downloading a package or starting installation; verify input, disconnect and hot-swap cleanup. Native chat link rendering and click routing require feasibility verification.
