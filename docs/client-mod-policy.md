## Why

Today a mod is required only when its author declares `[NetworkCompatibility(ServerMustHave, …)]` and the server runs it ([modules.md](modules.md), Handshake). An admin cannot:

1. **Require a client mod the server does not run**, such as a texture or robe pack, a UI the server's events assume, or an ordinary BepInEx plugin that declares nothing.
2. **Limit which client mods players may bring**, such as a PvP server that wants only cosmetic mods.

## What it is not

**This is house rules, not anti-cheat.** Every check below relies on the client's own report of what it loaded. A modified client can lie, and a client without Progenitor reports nothing at all. The admin panel, this page and the player's join screen say so plainly. Nothing in this feature claims to detect cheats.

## Security

**Mods come only from public listings (decided 2026-10-05; the Progenitor Index added 2026-10-20).** A server never sends mod files to a client, and the client never installs a file a server sent; required and recommended mods are installed from the signed Progenitor Index when it lists the package, otherwise from Thunderstore, in game from the join screens or the Install tab. Why:

- **Accountable authors.** A Thunderstore package has a named owner, a public listing and a version history; a server's copy has none of that.
- **Easy takedown.** A malicious package can be removed from Thunderstore for everyone at once; a copy a server hands out cannot be recalled.
- **No push from operators.** Before this change a server operator could send arbitrary code to joining players behind a consent prompt. Now an operator can only name packages in the signed catalog.
- **Catalog signatures without a prompt.** Trust on first use replaces the consent prompt: the first verified catalog from an address pins its operator key, and a later key change is flagged and never re-pinned ([mod-manifest.md](mod-manifest.md#trust-on-first-use-2026-10-05)). The pin installs nothing.
- **Installs still ask.** Every Thunderstore batch a server's catalog leads to still needs the player's per-server confirmation ([join-flow.md](join-flow.md#5-install-from-thunderstore-stage-2)).

What was removed, the retired packets and the one-time cleanup of server-sent files from older builds: [mod-manifest.md](mod-manifest.md#removed-2026-10-05-server-to-client-mod-files). Source-checked and game-free tested; not live-verified.

## How the server learns a client's mods

The 16-slot handshake can't carry a full mod list, so this adds a separate report.

- **Capability.** The server's handshake hello sets a new bit, `Handshake.Capability.ClientPolicy`, only when the required list is non-empty or the mode is Only approved. Otherwise no report is asked for. (Since stage 3 a stage 3 server's request always carries `PolicyRecheck`, "this server re-checks mid-session", alone when there is no policy; that asks for nothing.)
- **Report.** A client that sees the bit sends one inventory report on a new reserved event id (`'PrCm'`, request/answer framing like `'PrJa'`, at most 15 KiB, chunked when larger). It lists every plugin this process loaded: chainloader plugins, Progenitor plugins (including hot-loaded ones), and preloader patchers. Each entry is `guid`, `name`, `version`, `source` (`chainloader` / `progenitor` / `patcher`), and `package` when the install ledger knows it. File hashes are not sent; they would add nothing a lying client can't fake.
- **Timing.** The report goes right after the handshake answer. The server judges it inside the existing answer deadline (`Networking.HandshakeAnswerTimeoutSeconds`, default 20 s). A client that answered the handshake but sent no report by then counts as "can't be checked".
- **Privacy.** A client only sends its mod list to a server that asked. The join screen's message page shows the line `This server checks your client mods.` when the bit is set.
- **Re-checks (the admins' choice, decided 2026-10-05).** A hot load or unload during the session (the Mods list switch, a Turn on, an install, a reload) sends a fresh report, debounced; a client that knows the policy first pauses what the policy doesn't allow, as at join. The server re-judges every such report, and every player in the world when the admins change the policy. What happens then is the admins' choice, **If a player's mods break the rules while playing**:
  - **Pause the mod and warn them** (the default): a mod the per-server pause can take (a hot-loadable Progenitor mod) is paused for this server; for anything else (a plain BepInEx plugin, `ctx.UnsafeHarmony`) the player gets a notice naming it and saying to turn it off in the Mods list and restart before rejoining. Nobody is disconnected, including for mods that loaded before the policy changed.
  - **Disconnect them**: a notice naming the mods and the seconds left, then a disconnect unless a later report shows them gone (a paused mod counts as gone). Each mod has its own grace: the server's **Seconds to fix a mod** (`[ClientPolicy] DisconnectGraceSeconds`, 60 by default, 10 to 300; [the setting](#disconnect-delay-reqrule5)) for a mod loaded mid-session, and at least 60 s for a mod that was loaded before the admins changed the policy.
  - **A required client mod** the player turns off mid-session is warned about under Warn and counts like a not-allowed mod under Disconnect. A requirement the admins add mid-session is only told: it applies from the next join under either choice.

  Details: [Stage 3 as built](#stage-3-as-built).

### Disconnect delay (REQRULE5)

Requested 2026-10-08: the delay before **Disconnect them** disconnects is a server setting, `[ClientPolicy] DisconnectGraceSeconds` in the server's `progenitor.cfg`: 60 by default, clamped to 10 to 300 (it was a fixed 15). On the Server tab it is **Seconds to fix a mod**, a number row right below **Mods break rules while playing** under **Mods players need** (admin channel operation `disconnect-grace`, one stored value, with the same authorization, rate limit, audit line `.../JoinAdmin/disconnect-grace` and `Clamped to N seconds (10 to 300).` note as every number row). It has its own name so it is not confused with Players without Progenitor's **Seconds before disconnect**. Under **Pause the mod and warn them** the row reads `Not in effect: Mods break rules while playing is Pause the mod and warn them.` A server from before the setting has no such row.

- **Mods loaded before a rule change** get the larger of the setting and 60 s: a rule change must never give players less time than it used to, and a longer setting applies to them too. A separate setting was not worth another row.
- **Every place that prints the seconds** uses the server's value: the radio line and the help (an admin's client reads it from the server's state, else from the rule message, else 15 for a server from before the setting), the save note, the notice (the server sends the seconds left) and the uninstall boxes' `Required by` line (from the rule message; 15 when a server never sent one).

Source-checked, built and game-free tested (`RequiredRuleTests`, `ServerOptionsTests`); not live-verified.

## How a join is judged

On the server, after the handshake rows pass:

1. **Required:** every required row must be in the report and pass its version rule. A miss is `Missing` / `Update needed` / `Newer than allowed`.
2. **Only approved:** every reported mod must be always-approved, on the approved list, or a mod the server runs or requires (passing its version rule). Anything else is `Not allowed on this server`.
3. **Can't be checked:** with no report, or a client without Progenitor (no handshake answer and no report), apply **Players without Progenitor**. With **Let them join**, a client that answered the handshake but sent no report is also let in, and the admin alert counts it. A client without Progenitor and a non-empty required list is refused by rule 1 in either case.
4. **Install window.** When every problem is something the client can fix during the join (a required mod whose row names a Thunderstore package serving an accepted version, or a not-allowed mod the client can pause), the existing deferred kick and install window apply (`Networking.InstallGraceSeconds`; [as built](#rule-4-as-built-2026-10-05)). Otherwise the join is refused with a readable reason: `Mods needed: <names>` / `Mods not allowed on this server: <names>`, cut to fit the 479-character wire message.
5. **Refusals are recorded** in the existing refused-join alert, with new line kinds: `<mod>: players don't have it (required by you)`, `<mod>: not approved (3 joins)`. Each not-approved line gets **Approve**, which adds the mod to the approved list in one click (stage 3; the line then reads `<mod>: approved now (3 joins refused before)`).

## Edge cases

- **Hosted private games:** the host is admin and the policy applies to friends who join. The host's own client is never judged (hosted-child skip, as for the handshake).
- **A required mod the server also runs:** the author's `ServerMustHave` row already covers it. The admin's row adds only the reason and version rule, and the stricter rule wins.
- **Conflicts:** a mod can't be both required and recommended (adding one moves it). Removing it from Approved while it's required is refused (`Required mods are always allowed.`).
- **Many mods:** a client with more than about 120 plugins needs a chunked report. Over the 64 KiB total the report is cut, and the server treats the missing part as "can't be checked".
- **Version strings:** compared with the existing `Handshake.Compare` rules (`Exact`, `Minor`, `None`) plus a new `AtLeast` rule (semantic-version order, with the same fallback as `Minor` for versions that can't be parsed).

**A server plugin that loads mid-session (NOKICK1, 2026-10-17).** The same holds for the mods server plugins require through the handshake (`[NetworkCompatibility(ServerMustHave)]`, `ctx.Handshake.Require`): when one loads while players are connected (hot-loaded from `progenitor-reload`, or with a Core swap), a connected player who lacks it, or runs it at a version this server does not accept, is never disconnected, under either choice. They get this notice (`Now required here; install it from Install Mods before your next join`, with **Open Install Mods** for a mod they have no copy of; `Required here at <version>; you have <version>` for a version mismatch), the mod is masked for them on the server (`ctx.Messages` answers `PeerLacksMod` and `ctx.Peers.Of(user)` reports it absent, so a server part that checks these skips them), and their next join is judged in full. This covers server-initiated changes only: a failing re-answer after the player's own change (a required mod hot-unloaded, their Core swapped to a mismatched version) keeps the existing flow. Details: [modules.md](modules.md) (A server change never disconnects a connected player). Game-free tested (`NoKickOnServerChangeTests`); not live-verified.

Each problem is told once: a later report that still lists it says nothing new, and a mod that goes and comes back is told again (and counts as loaded mid-session, not before the change).

**Each mod keeps its own grace** from when it was first seen: the configured seconds (60 by default; a fixed 15 before REQRULE5) for a mod loaded (or a required one lost) mid-session, the larger of the configured seconds and 60 for a mod you don't allow loaded before the change. A change of the setting applies to mods first seen after it; a countdown already running keeps its deadline. The disconnect is armed for the earliest and moves when that one goes or an earlier one appears; when the mods named have different time left, the notice reads `Fix these in the time shown for each` and each line ends with its seconds. At the deadline only the overdue mods disconnect the player, and the disconnect re-reads the latest report first: a clean report in the last two seconds calls it off (`You won't be disconnected`).

**Design choices.** These are this stage's decisions where the request left room:

- **Mods loaded before a policy change.** Under Warn, the earlier promise holds: nobody is disconnected for them. Under Disconnect, the admins' choice is followed for them too, but with at least 60 s (the configured grace when it is longer), and the notice names them. "Loaded before" means the mod was in the player's last report when the policy changed; a player the server never asked (the policy was off at their join) has everything in their first report counted that way.
- **A required mod missing mid-session.** Only a mod the player had and lost this session (turned off, swapped to a version outside the rule) counts as their doing: a warning under Warn, a disconnect under Disconnect. "Had" means met under that exact row (its key, rule and version): a row the admins add, tighten (a new version or rule), or remove and add again mid-session is told as a requirement added mid-session and never disconnects anyone under either choice, because the player loaded nothing.
- **A join let in without a report** (Let them join, or a report that came after the answer deadline): its first report is the join's baseline, so what it lists counts as loaded before (the 60 s grace under Disconnect), never as a mid-session load, and its required rows as not met yet.
- **Reports go only where they are re-checked.** A client sends mid-session reports only to a server whose request declared `PolicyRecheck`, and stops when a re-signed catalog no longer carries a policy (`ClientPolicy: this server no longer checks client mods …`).
- **The choice is not signed.** The client needs no copy: the server's notice carries the action, the mods and the seconds. Adding a key to the signed join section would have made every CLIENTPOLICY2 client drop the section on a server that chose Disconnect.
- **The disconnect is the game's `Kicked`** (`PlayerControl.Disconnect`), whose screen shows no text ([knowledge note](../knowledge/notes/disconnect-message-not-shown.md)). So the reason goes first: the notice popup and a System chat line two seconds before. A kick in the world leaves the player on the game's own banner (`Communication with server was lost. Reason: You were kicked from the server [Leave Game]`) inside the world until they press Leave Game; the join screens (welcome and mods pages) and Progenitor's popups close when the connection ends so they never cover it. The client shows the disconnect notice again only once it is back at the main menu (no client world, about 1.5 s after), and there it stays until the player closes it. The reason is also the disconnect's data and the server log line, one sentence per cause: `Mods not allowed on this server, loaded during the session: X.`, `Mods this server no longer allows: Y.`, `Required mods turned off during the session: Z.`, `Required mods at a version this server doesn't accept: W (needs 1.2.0 or newer, had 1.1.0).`
- **A client that can't take the notice** (a Core older than this stage, which lacks `Handshake.Capability.PolicyRecheck`) gets the same words as one System chat line; the server can still disconnect it. A client without Progenitor sends no reports and is never re-checked.
- **Debounce.** The client sends at most one report 1.5 s after the loaded set settles, only when it changed (unchanged from stage 1); the server judges a user at most every 2 s, holding one judgment for the latest report.

### The countdown in chat while its notice waits (F41)

Status: source-checked, built, game-free tested (`CountdownChatTests`) and **live-verified 2026-10-08** except the re-arm case (step 7a); results below the procedure heading. Decided 2026-10-08.

A server notice waits while a confirmation box is open on the client ([Parts](#parts), F41), so a player with an install box open could not see a disconnect countdown. While a **Disconnect them** countdown notice waits, the server also says the countdown as a private System chat line to that player:

- **When.** When the notice starts waiting, then at **30** and **10** seconds left (a mark less than 5 s after the first line is skipped; two first lines are at least 5 s apart, and one countdown gets at most 3 of them). When the server re-arms the disconnect while the notice waits, the lines move to the new countdown: a re-arm with a new notice (a new mod, or one with less time) is reported again by the client, and a re-arm without one (one of two missing mods fixed, leaving the other's later deadline) is carried over by the server, which says the new seconds and keeps its own 30 and 10 s marks.
- **Not while it is visible.** A notice that shows at once says nothing in chat. When the box closes and the notice shows, the client tells the server and the lines stop.
- **It stops when fixed.** A report that clears the problem calls the disconnect off; the server says nothing more for that countdown, and the client's waiting notice becomes `You won't be disconnected`.
- **The words.** The notice's own advice for each mod (the same facts as its lines), made where the player is (never the join screen). One fix reads `Reinstall Hot Demo from Install Mods in the Mods menu within 60 s or you'll be disconnected. (The server's notice is waiting behind an open confirmation.)`; anything else `Within 45 s or you'll be disconnected: <one clause per mod>.` The clauses:

  | The client's facts | Clause |
  |---|---|
  | Not installed, Install Mods lists it | `reinstall <mod> from Install Mods in the Mods menu` |
  | Not installed, the local test source has it | `reinstall <mod> from Install Mods (local test source) in the Mods menu` |
  | Not installed, not offered here | `look for <mod> in Install Mods in the Mods menu, or ask the admins where to get it` |
  | Turned off, or not said | `turn <mod> back on in the Mods list` |
  | Paused here for the server | `<mod> is required here; it's installed but paused for this server, and it loads again as soon as the server allows it` |
  | Older than the rule | `update <mod> to 1.2.0 or newer (you have 1.1.0)` |
  | Newer than the rule | `<mod> is newer than this server allows (<rule>); you have <version>` (no claim that Install Mods offers the older version) |
  | Another version | `<mod> is required here at <rule>; you have <version>` |
  | Not allowed, pausable | `turn off <mod> in the Mods list` |
  | Not allowed, can't be paused | `<mod> isn't allowed here and can't be paused; turn it off in the Mods list and restart V Rising` |

  Like every policy chat line it is printable ASCII (at most 400 characters), so the menu path is written out in words.

**How it works.** The client's notice handler (`ClientPolicyNoticeClient.ShowOrHold`) sends `'PrCm'` kind 3 (`ClientPolicyHeldWire`: version, kind, `1` held or `0` no longer held, then optional JSON `{"local":[{"id","state":"turned-off|not-installed|unknown","listed","localTest","paused"}]}` with what it has of the named mods, the facts its notice lines use) when a countdown notice starts waiting and when none waits any more (shown, or replaced by a notice that is not a countdown). Ids are clipped to the report's id limit, and the server matches each mod on the same clipped form. It sends only on an accepted join, and only to a server whose request row declared `Handshake.Capability.CountdownChat` (bit 16384, set with `PolicyRecheck`; an older server would log the message as a bad report packet). The server (`Handshake.OnNoticeHeld`) acts on a player's messages at most once a second (a `no longer held` is still applied, quietly) and only while a disconnect is armed for them; it reads the armed disconnect from the re-check tracker (`ArmedGeneration`, `SecondsLeft`, `ArmedItems`), decides with the game-free `CountdownChatSchedule`, and sends through `Chat.SendTo` (`ChatMessageType.System`), the path every policy chat line uses. Each re-arm of the disconnect (`ApplyRecheck`) moves a waiting schedule to the new countdown (`RearmHeldChat`). A mark's line checks that the same disconnect is still armed and the notice still waits, and says the mark's own number. A malformed message is dropped with a warning. An older client never sends the message, so its countdown is not said in chat.

Logs: client `ClientPolicy: told the server its countdown notice is held behind an open confirmation; sent=True` (and `… is no longer held; sent=True`); server `ClientPolicy: <name>'s countdown notice is held behind an open confirmation` (or `is no longer held`), `ClientPolicy: countdown chat to <name> (held|re-armed|30 s mark|10 s mark, N s left, notice held): sent=True: <line>`. Readback: client `join_admin report` → `countdownChat` (the server declared it), `heldMessagesSent`, `serverNotice.heldForConfirmation`, `serverNotice.heldCountdownReported`; server `join_admin policy` → `users[].recheck.countdownChat {held, messages, throttled, lines, lastLine, secondsSinceLine}`.
